3. 代码级实现（开发用）

独立 Agent 审核并修正修正 1 处　提出问题 3 条　其中高风险 1 条

审核意见：锚点核对无误（UE4 IncrementalDestroyGarbage:1508、XD 块 1609-1734、MaxTimeForFinishDestroy:1607，UE5 IncrementalDestroyGarbage:4913、MaxTimeForFinishDestroy:5007、GAdditionalFinishDestroyTimeGC:4905、LastTimeoutWarningTime:5107、RequiresCookedData 包裹:5090），插入位置与 XD 原位置同构，唯一硬伤是 Elapsed 被放进 while 内。

改接口/改名 改动方式：UE5 同函数 IncrementalDestroyGarbage(:4913) 结构保留但改用 CVar 与 double，插入点变了

代码脉络：宏开启时 IncrementalDestroyGarbage(GarbageCollection.cpp:1508)在移动端把 FinishDestroy 等待拆两段：先 10s 早期告警(1609-1734，遍历 GGCObjectsPendingDestruction 打印每个对象 IsReadyForFinishDestroy)，再由 1691 的 MaxTimeForFinishDestroy=30.0 触发正式超时告警，避免 GC 超时崩溃前日志被冲掉。

不要写死 30.0，改用 UE5 的 CVar 变量，保持与早期告警步长一致

if(bPollTimeLimit && !bFinishDestroyTimeExtended && (FPlatformTime::Seconds() - GCStartTime) > MaxTimeForFinishDestroy ){
 MaxTimeForFinishDestroy = 30.0;
 bFinishDestroyTimeExtended = true; ... }
// UE5 :5096 保持官方
MaxTimeForFinishDestroy = GAdditionalFinishDestroyTimeGC; // gc.AdditionalFinishDestroyTimeGC, 默认 40 (:4905)
// 正式告警在 :5105-5157，用 LastTimeoutWarningTime(:5107) 节流

⚠ UE5 正式告警靠 MaxTimeForFinishDestroy 与 LastTimeoutWarningTime 表达式，勿重复打印

风险评估

原代码风险：移动端原逻辑只在 30s 打一次告警，崩溃前日志可能已被刷掉；10/30s 硬编码不随平台 CVar 调整。

移植风险：在 UE5 重写后的 GC 中插入早期遍历会增加超时期间的日志量（每 10s 遍历全部 pending 对象），移动端 I/O 被放大；仅 IOS/ANDROID 编译。

开发自检

  • gc.TimeoutOnPendingDestroyedObjectGC 下复现超时可见 Early Warning 与对象清单
  • 官方 Spent more than 告警仍正常打印
  • Android/iOS 各跑一次 GC 压测无额外卡顿

结论置信度：medium — UE5 该块被 FPlatformProperties::RequiresCookedData()(:5090) 包住，需确认移动端 cooked 构建下 bPollTimeLimit 可达；EarlyStep 与 AdditionalFinishDestroyTimeGC 需对齐避免与 40s 正式告警错位
