修改草案 · XD_OIT_SORTKEY

OIT（顺序无关透明）支持：为半透明物体生成稳定排序键

部分覆盖 移植 需接入点 仅加接入点 工作量 M风险 中开发者 Peng TianCheng主要模块 Engine

一句话结论：PC 优先用 UE5 OIT；移动端/按组稳定排序键是否保留需按平台评估

背景：新增 OITSortKey.h/.cpp，静态网格/骨骼网格/组件在每帧计算排序键（含屏幕位置/深度），供 OIT 合成使用，解决半透明穿插闪烁。

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：解决角色与其挂点/头发多层半透明随镜头变化而穿插：OITSortKeyManager 每帧以 AnchorSkelMeshComponent 为锚，用 (锚→组件)·相机前向 分 Front/Back，各自按到锚距离排序，再 SetTranslucentSortPriority(Index)；分组版按挂点父组件分组。虽名为 OIT，用的却是普通半透明排序通道，不是 UE5 的 OIT。

上游引入：P4 CL 2558055（2024-08-12，tl_pengtiancheng，TORCHLIGHT-170302）；CL 4005138（2025-09-02）修改 SetTranslucentSortPriority 调用点。

上游历史（是否修过）：p4 annotate：OITSortKey.cpp:3/4/166 → 2558055，:71/:153 → 4005138。UE5 无这套：全 Source grep 无 ETranslucencyBlendLayer（fork 的 Scene.h:102-128 是 XD 另加枚举），只有 ETranslucentSortPolicy（EngineTypes.h:435-448：SortByDistance/ProjectedZ/AlongAxis）、PrimitiveComponent.h:892/1997 的 TranslucencySortPriority，以及原生 OIT（Renderer/Private/OIT/OIT.h:104 AddOITComposePass、OIT.cpp:95 IsOITSortedPixelsSupported）。上游既未提供也未修改该能力。

为什么可以断定不是「故意为之」3 条依据
  • UE5 三种 sort policy 都是按相机距离/Z/固定轴，缺少「以某角色为锚做前后分组」这一维度，属玩法需求而非上游漏做。
  • ETranslucencyBlendLayer / TBL_EmitterTop 在 UE5 全无命中，说明连渲染分层都是 XD 自建，不是改上游。
  • 调用点横跨 World.cpp:470、LevelTick.cpp:1393、SceneComponent.cpp:2038-2054、SkeletalMeshComponent.cpp:804-818，是系统性设计。

调用方契约：注册：StaticMeshComponent.cpp:222-230、SkeletalMeshComponent.cpp:804-818（bNeedOITSort→ComponentsToSortInWorld，bSortAnchor→OITMgr.AnchorSkelMeshComponent）；每帧由 World::Tick（LevelTick.cpp:1393）调 OITMgr.Tick()（cpp:161，CVar r.OITSortKey）→ UpdateOITSortKeyManager（cpp:4）；分组在 SceneComponent.cpp:2038-2054 依 bRequireOIT 建 OITGroups；渲染侧读键 StaticMeshRender.cpp:331/536、SkeletalMesh.cpp:4768。

内层真实语义：正常：仅当 AnchorSkelMeshComponent 非空且 ComponentsToSortInWorld 非空才排序（cpp:6-10），空/无锚直接 return 且不写优先级；异常：取相机时 Index==0 判断在循环内（cpp:15-26）实际只用第一个 PlayerController；失效组件就地 RemoveAt 剔除；Front 按到锚距离升序、Back 降序拼接后写 priority。

代码库惯例：UE 侧同类做法是设一次 TranslucencySortPriority 或切换 TranslucencySortPolicy，而非每帧 TArray.Sort 后逐个 SetTranslucentSortPriority（后者在 UE 里会连锁触发排序键重建）。

为何长期未被发现：默认 r.OITSortKey=0 关闭；只在角色挂大量可拆半透明部件（头发/披风/特效）时才看出穿插，普通关卡与自动测试不覆盖。

XD 侧的做法与意图：CL 2558055（TORCHLIGHT-170302）把 PTC 项目需求引擎化，连编辑器调试（EditorViewportClient.h:547、DebugSkelMeshComponent.cpp:814）一并改。

①照搬到 UE5 的 StaticMeshRender.cpp/SkeletalMesh.cpp mesh batch 处：UE5 的 FPrimitiveSceneProxy/FMeshBatch 排序与 UE4 不同，直接塞 per-section priority 会被 translucent pass 排序覆盖，看似生效实际乱序。②保留每帧 SetTranslucentSortPriority：UE5 下会每帧重建排序键并刷新渲染状态，CPU/RDG 开销放大。③以为 UE5 原生 OIT 可替代：OIT.h:104 是像素级合并，与 XD 的组件/Section 次序语义不同，替换会改变美术表现。

迁移方案（按根因定）

refactor 并去引擎化：把 OITSortKeyManager 移到 Game Module/插件（只保留 USceneComponent 排序数据与 Tick），不再改 World/StaticMeshRender/SkeletalMesh；结果写 TranslucencySortPriority 或 UE5 mesh batch SortKey，必要时再接 OIT（OIT.h:104-105）。若只是相机依赖的前后关系，先试 ETranslucentSortPolicy（EngineTypes.h:435-448）避免自研。

根因级自检用例

  • 有锚+有效组件：相机绕到背后时 Front/Back 次序翻转
  • 无锚（AnchorSkelMeshComponent=null）：不写任何 priority，等价关宏
  • 组件中途销毁：从 ComponentsToSortInWorld/OITGroups 剔除且不崩
  • 同帧多次 Tick/多视口：priority 稳定不抖动
  • r.OITSortKey=0：零开销（不排序、不改 priority）

风险评估

原代码风险：每帧对所有半透明组件排序（TArray.Sort + DistSquared），组件多时 CPU 开销大。

移植风险：UE5 网格渲染入口变化大，移植排序键需重接；编辑器视图相关代码也需一并处理。

开发自检

  • 半透明穿插不再闪烁
  • 移动端半透明排序 CPU 开销可接受

结论置信度：medium — UE5 原生 OIT 能否覆盖 XD 组内稳定排序需求需实测。
