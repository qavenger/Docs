Android 上 OpenGL 崩溃时允许回退到 Vulkan（反之亦可）

未覆盖 移植 需接入点 结构性改动 工作量 M风险 中开发者 Gong Bai Liang主要模块 Core

一句话结论：与 UE5 ES3.2/Vulkan 双 RHI 打包配置联动

可主动舍弃性（UE5 架构更替）

需评估 平台工具链 / SDK 版本适配

判定依据：这类宏是给 UE4 那个年代的编译器/SDK 打补丁；迁移到 UE5 会用新工具链与 SDK 下限，对应的前提大多不复存在，但需确认问题是否在新组合下重现。

舍弃前提：需确认：新工具链/新插件/新 RHI 下该问题是否仍存在

UE5 替代能力：UE5 新工具链下限（Xcode 15+/NDK r2x/MSVC 14.3x）

相关文件：Source/Runtime/Core/Private/Android/AndroidPlatformMisc.cpp Source/Runtime/Core/Public/Android/AndroidPlatformMisc.h

0. 根因溯源（这个宏为什么存在）

平台/工具链绕行

结论：XD 让 GLES 崩溃出口可写故障标志并重启到 Vulkan，避免部分机型反复崩；靠 ForceRenderAPI 写 ForceOpenGLAPI，ShouldUseVulkan 启动时读取。

上游引入：XD fork：GenericPlatformMisc.h:860-863 声明 + GenericPlatformMisc.cpp:758-771 空实现；FAndroidMisc::LogOpenGLFailed AndroidPlatformMisc.cpp:800-819、CheckOpenGLFailedBefore :821-841、ForceRenderAPI :739-777、CheckForcedRenderAPI :779-798；写点 OpenGLShaders.cpp:3508-3527（link 失败）、OpenGLResources.h:646-657（MapBufferRange 失败）；读点 OpenGLShader 决策在 AndroidPlatformMisc.cpp:3075 ShouldUseVulkan 用 CheckForcedRenderAPI()!=OpenGLES。开关 XDBuildMiscConfiguration.cs:229-231（依赖 XD_EXT_PLATFORM_UNWANTED_BEHAVIORS_TAKEOVER）。

上游历史（是否修过）：上游从未有：4.26.0-release 与 UE5 5.8.2 的 Source/Runtime/Core 均无 LogVulkanFailed/CheckVulkanFailedBefore/ForceRenderAPI（git grep 无命中）。属 XD 私有，不存在'上游修没修'。

为什么可以断定不是「故意为之」4 条依据
  • 上游把 link program 失败保留为致命路径（UE5 OpenGLShaders.cpp:421 仍是 UE_LOGF Error 后失败），是'崩溃即暴露'取向，不是漏了回退。
  • 上游 UE5 提供 r.Android.DisableVulkanSupport 与 RHI 命令行覆盖，但没有'持久化故障记忆'概念，自愈不在其设计内。
  • XD 用的 ini 键（/Script/Engine.GameUserSettings 的 OpenGLFailed/ForceOpenGLAPI/VulkanFailed）是私有协议。
  • 若上游认为必要，会做成 RHI 自动重选，而非写盘+重启进程。

调用方契约：写点 OpenGLShaders.cpp:3519/3521、OpenGLResources.h:651 依赖 LogOpenGLFailed 落盘；启动侧 ShouldUseVulkan(AndroidPlatformMisc.cpp:3075) 依赖 CheckForcedRenderAPI()/CheckVulkanFailedBefore()。LogOpenGLFailed 内部调 ForceRenderAPI(Vulkan) 把 ForceOpenGLAPI 置 false（:813）——真正起作用的是 ForceOpenGLAPI=false，OpenGLFailed 只供下次 ForceRenderAPI(OpenGLES) 时清标志(:765)。只移植写点不移植读点等于无效。

内层真实语义：非 Android/非 USE_ANDROID_FILE 平台走 FGenericPlatformMisc 空实现（LogOpenGLFailed 只打 Warning、CheckOpenGLFailedBefore 恒 false，GenericPlatformMisc.cpp:759-770）；预编译分支 link 失败仍 return nullptr（OpenGLShaders.cpp:3498-3506）不走 fallback。

代码库惯例：上游 RHI 选择用 CVar（r.Android.DisableVulkanSupport）+ ShouldUseVulkan 静态缓存，不写盘。

为何长期未被发现：只在特定 GLES 驱动机型+低内存/link 失败时触发；日志表象为 'Failed to link program'；一次 OOM 也会误判并永久钉在 Vulkan（risk_original 已指出）。

XD 侧的做法与意图：Torchlight Android 部分机型 GLES 驱动 glLinkProgram/MapBufferRange 崩溃率高，需自动切 Vulkan 保可用性。

⚠ 在 UE5 把 Fatal 改成 Warning 但不写盘 → 无限崩溃循环；只调 ForceRenderAPI 不写 OpenGLFailed → 与 CheckOpenGLFailedBefore 语义不配套；把 RestartApplication 放在写盘之前（UE4 是 LogOpenGLFailed→Sleep(3)→Restart→再 LogOpenGLFailed 两次写才稳）会丢标志；用全局 GameUserSettings ini 会跨工程/跨设备残留。

迁移方案（按根因定）

首选不移植：改用 UE5 的 r.Android.DisableVulkanSupport/命令行 + 崩溃上报后端按设备下发 RHI 配置（无重启、无残留）。若必须保留：在 UE5 重新引入 FGenericPlatformMisc 的 LogOpenGLFailed/ForceRenderAPI 声明+实现（UE5 已删），改 OpenGLShaders.cpp:421 与 OpenGLDrv/Private/OpenGLResources.h:229 两处出口，并用 CVar/项目私有文件替代 GameUserSettings ini。

根因级自检用例

  • GLES 设备 link 失败：写标志并切 Vulkan，二次启动走 Vulkan。
  • r.Android.DisableVulkanSupport=1：不切，保持 GLES 且只打日志（不误切）。
  • 预编译阶段失败：与 UE4 一致（仍 return nullptr，不触发 fallback）。
  • 非 Android 平台调用 LogOpenGLFailed 不崩（空实现）。
  • 切到 Vulkan 后又检测到 GL 可用：OpenGLFailed 被 ForceRenderAPI(OpenGLES) 清除。

可反馈上游：可作为需求反馈（非 bug）：GLES 驱动 link 失败时引擎缺乏自愈通道，UE5 仅有 CVar 手动关 Vulkan。最小复现：Android GLES 设备低内存触发 glLinkProgram 失败，UE5 直接 Fatal 退出。

⚠ UE5 AndroidPlatformMisc.cpp:2346 ShouldUseVulkan 内需加 CheckOpenGLFailedBefore()==false 短路，否则重启后又选回 GLES 形成循环。

风险评估

原代码风险：崩溃即写 ini + 重启，若误判（如一次 OOM 导致 link 失败）会把设备永久钉在另一个 RHI 上。

移植风险：UE5 Android RHI 选择点与 OpenGL 失败出口行号均变化（OpenGLShaders.cpp:421、AndroidPlatformMisc.cpp:2346/2453），漏 hook 会退化为直接 Fatal 崩溃或无限重启。

开发自检

  • 人为让 GLES 链接失败，确认写 OpenGLFailed 后重启并切到 Vulkan
  • 确认 r.Android.DisableVulkanSupport=1 时不回退、不循环重启

结论置信度：medium — UE5.8 是否仍支持 ES3.2 打包（OpenGLDrv 目录存在但目标平台支持度未核实），以及 ShouldUseVulkan 的缓存点 CachedShouldUseVulkan 是否需一并重置。
