修复 TextBlock/ShapedTextBlock 使用描边效果时 LayerId 错误

未覆盖 常开补丁 引擎内实现 仅加接入点 工作量 S风险 中开发者 Ran Qing Sen主要模块 Slate

一句话结论：作为常开补丁保留（原 CVar s.UseTextBlockLayerIdNewMethod 可保留以便回退）。

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：带描边（Outline）的文字在 STextBlock / FSlateTextRun 绘制时，层级（LayerId）分配与实际占用层数不一致，导致层级错位（遮挡/顺序错误）。XD 的修复方式是引入开关 `s.UseTextBlockLayerIdNewMethod`，在描边文字路径上让层级多占一层并在两处绘制实现中保持一致。UE5 中没有该 CVar（全仓无命中），但两处绘制函数签名与层级传递结构未变（`FSlateTextRun::OnPaint(..., int32 LayerId, ...)` 在 SlateTextRun.cpp:96；`STextBlock::OnPaint` 在 STextBlock.cpp:258，并在 :284/:296/:302/:316 递增/传递 LayerId），因此补丁可原样插入——前提是该层级问题在 UE5 上仍会复现。

上游引入：XD 的 Slate 层级修复（宏 `XD_FIX_BUG_TEXT_BLOCK_ERROR_LAYER_ID_WHEN_USING_OUTLINE`）：UE4 在 `SlateTextRun.cpp:13` 定义 CVar `s.UseTextBlockLayerIdNewMethod`（`GIsUseTextBlockLayerIdNewMethod`），并在 :181-185、:200-204 让描边文字多占一层；`STextBlock.cpp:211-215`、:236-240 做同样处理。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2：①全仓**无** `UseTextBlockLayerIdNewMethod`（该开关未上游化）；②`Source/Runtime/Slate/Private/Framework/Text/SlateTextRun.cpp:96` `int32 FSlateTextRun::OnPaint(const FPaintArgs& PaintArgs, const FTextArgs& TextArgs, const FGeometry& AllottedGeometry, const FSlateRect& MyCullingRect, FSlateWindowElementList& OutDrawElements, int32 LayerId, const FWidgetStyle& InWidgetStyle, bool bParentEnabled) const`（签名一致）；③`Source/Runtime/Slate/Private/Widgets/Text/STextBlock.cpp:258` `int32 STextBlock::OnPaint(...)`，其中 :284 使用 LayerId、:296 `++LayerId;`、:302 继续使用、:316 `LayerId = TextLayoutCache->OnPaint(Args, AllottedGeometry, MyCullingRect, OutDrawElements, LayerId, ...)` —— 即层级递增与传递结构与 UE4 基本一致；④UE5 的描边尺寸处理仍在（SlateTextRun.cpp:36/:42/:47/:71-76 等处使用 OutlineSize）。

为什么可以断定不是「故意为之」2 条依据
  • 上游未采纳该"多占一层"的层级方案（其层级分配逻辑保持原样），属未修复状态（或以其它方式规避）。
  • XD 的补丁是项目侧为消除描边文字层级错位所做的修正。

调用方契约：绘制层级必须与实际占用的层数一致：描边文字多占一层时，相邻元素的层级与遮挡关系必须同步（否则出现遮挡错误或提前剔除）。

内层真实语义：UE4（XD）：用 CVar 控制"描边文字多占一层"，在 SlateTextRun 与 STextBlock 两处保持一致。UE5（上游）：无该开关，层级递增逻辑为默认形式（`++LayerId` 等）。

代码库惯例：上游倾向在层级消费方（如 `TextLayoutCache->OnPaint`）统一处理层级推进；项目侧改动需同时覆盖两处实现以避免不一致。

为何长期未被发现：属"UI 绘制层级"缺陷：不迁移通常不崩，只在带描边文字与相邻元素重叠时表现为遮挡/顺序错误（观感问题，容易被忽略或误判为美术问题）。

XD 侧的做法与意图：XD 的目标是修正带描边文字在 UMG/Slate 中的绘制层级错位（避免描边与相邻元素互相穿插）。

⚠ 四点注意：①**先在 UE5 上复现**该层级问题（Slate 文本绘制有过改动，可能已不复现）；②补丁必须**两处一致**（SlateTextRun 与 STextBlock 同时改），只改一处会导致层级不一致（更严重的错位）；③层级推进以链式返回（如 :316 `LayerId = TextLayoutCache->OnPaint(...)`）——插入时要确保返回值仍被正确传递，否则后续元素层级整体错位；④保留 CVar 开关便于回退（描边层级属于表现敏感项，需要 A/B 与线上开关能力）。

迁移方案（按根因定）

按 port-as-is（先验证）处理：①在 UE5 上构造"描边文字 + 相邻 UI 元素"场景，确认层级问题是否存在；②若存在，在 `SlateTextRun::OnPaint`（:96）与 `STextBlock::OnPaint`（:258）原样插入"描边多占一层"的处理并保留 CVar 开关；③若不存在（上游已通过其它方式规避），删除该宏。

根因级自检用例

  • 描边文字的绘制层级正确（与相邻元素无遮挡错误、无穿插/闪烁）
  • 两处实现（SlateTextRun/STextBlock）层级推进一致（链式返回值正确传递）
  • 不同字体/描边尺寸/DPi 缩放下表现一致
  • 关闭 CVar 时行为回到上游默认（可 A/B 与快速回退）
  • 大段文本/多语言（含 CJK）渲染正常

可反馈上游：可向上游反馈：带描边文字的层级分配在多元素重叠场景下可能出现错位（附最小复现）。

风险评估

原代码风险：层号语义被描边占满后，同一控件内后续元素被压到更下层，表现为描边遮字或其它元素穿插。

移植风险：层号全局语义改变，任何依赖 STextBlock 返回层号做算术的上层 UI（UMG 富文本、自绘滚动条）都可能错位；ElementBatcher 若日后改成描边复用同层，这里会多空一层。

开发自检

  • 带描边+阴影的 TextBlock 与相邻控件层序正确
  • 关闭 CVar 后行为与 UE5 原版一致
  • RichText/SShapedTextBlock 路径同样正确

结论置信度：medium — UE5 是否已在 ElementBatcher 改为单层描边（本批只确认 :1514/:1680 仍是 Layer/Layer+1）；SlateTextRun 的 CVar 名 s.UseTextBlockLayerIdNewMethod 是否与已有 CVar 冲突。
