修改草案 · XD_OPT_STATIC_POINT_LIGHT_SET_HIDDEN_IN_GAME

允许把纯静态点光源设为 HiddenInGame 仍保留其烘焙照明

未覆盖 配置化 可工程化 无需改引擎 工作量 S风险 低开发者 Ran Qing Sen主要模块 Engine

一句话结论：纯项目侧清理流程即可，保留烘焙照明不受影响

背景：静态光不参与运行时渲染，可安全隐藏，减少动态光源列表与光照计算。

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：场景里常放静态点光用于烘焙光照，但它们不应在运行时参与渲染（既无意义又占光源列表/影响性能）。XD 在 `UPointLightComponent::PostLoad` 中对非编辑器构建、且 Mobility 为 Static 的点光调用 `SetHiddenInGame(true)`，使其不进渲染光源列表（同时保留组件与光照数据）。UE5 的 `UPointLightComponent` 结构未变，但**没有** PostLoad 重载（rg 检索 PointLightComponent.cpp/.h 均无命中），因此该改动可在同样位置直接落点。

上游引入：XD 的运行时行为定制（宏=1：UPointLightComponent::PostLoad（PointLightComponent.cpp:256，声明于 PointLightComponent.h:104）在非编辑器构建中对 Mobility==Static 的点光调用 SetHiddenInGame(true)）。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2：`Source/Runtime/Engine/Private/Components/PointLightComponent.cpp` 与 `Source/Runtime/Engine/Classes/Components/PointLightComponent.h` 中 **均无 `PostLoad`**（也没有 `SetHiddenInGame` 的调用点）—— 即上游未采用该行为，类结构本身保持一致（可按 UE4 方式添加 PostLoad 重载）。

为什么可以断定不是「故意为之」2 条依据
  • 上游未在点光组件里做这种"按 Mobility 自动隐藏"的处理（其默认行为是让静态光继续存在于场景中）。
  • XD 的做法属项目侧运行时行为定制（减少无意义光源），不是上游缺陷。

调用方契约：静态光必须仍能参与光照构建/烘焙（编辑器与 cook 路径），只在运行时按需不参与渲染；不能误伤编辑器预览与烘焙流程。

内层真实语义：UE4（XD）：组件 PostLoad 时按 Mobility 判定并隐藏。UE5（上游）：无该逻辑，静态点光保持默认可见性（是否参与渲染由渲染层的可见性/光照路径决定）。

代码库惯例：上游倾向在"渲染层"（光源可见性、重要性计算）处理这类取舍，而不是在组件加载时改可见性；项目侧定制应权衡：组件级改动简单直接，但会影响所有静态点光。

为何长期未被发现：属"运行时性能/场景清理"定制：不迁移不会崩，只表现为静态点光在游戏内仍被渲染（性能与视觉上的轻微差异）；而组件结构未变，容易被当成"上游已处理"而漏掉。

XD 侧的做法与意图：XD 的目标是让大量静态点光在运行时不被渲染（去掉无意义的渲染光源，降低光照开销）。

⚠ 四点注意：①**PostLoad 会在所有加载路径执行**（含编辑器与烘焙）——必须严格区分 `WITH_EDITOR` 与运行时，否则会影响编辑器预览与光照构建（静态光需要参与烘焙）；②"隐藏"与"不参与光照计算"是两件事：`SetHiddenInGame(true)` 影响游戏内可见性，需确认 UE5 中该操作是否同时把光源移出渲染光源列表（不同光照路径/新特性下行为可能不同）；③UE5 的光照体系已变（虚拟阴影贴图/Lumen 等），静态光在新体系下的默认行为与 UE4 不同——迁移前先确认"静态点光在运行时的实际影响"是否仍如 UE4 时期严重；④若项目存在"个别静态点光需要在游戏内可见"的需求，应加例外机制（Tag/开关），不要一刀切。

迁移方案（按根因定）

按 port-as-is 处理：在 UE5 的 `UPointLightComponent` 上添加 `PostLoad` 重载（非编辑器构建下，Mobility==Static → `SetHiddenInGame(true)`）；或评估改为在项目层统一处理（如插件/子类），以减少对引擎的侵入。

根因级自检用例

  • 游戏内静态点光不再渲染（可对比光源数/渲染统计）
  • 光照表现与 UE4 一致（烘焙结果、间接光、阴影不受影响）
  • 编辑器预览与光照构建（cook 阶段烘焙）流程正常
  • 动态（Movable/Stationary）点光行为不受影响
  • （若有例外需求）例外机制生效且可配置

可反馈上游：可向上游提议：为"仅用于烘焙的静态光"提供官方标记（运行时自动不参与渲染）。

3. 代码级实现（开发用）

独立 Agent 审核通过

审核意见：port-as-is 成立。核实：UE4 PointLightComponent.cpp:256/260 PostLoad 与 header:104-107 声明；UE5 PointLightComponent.cpp:236 处为 Serialize 之后、无 PostLoad，header:93 为 Serialize 声明，插入点可行。提醒：UE4 的 PostLoad 同时服务 XD_MOBILE_RENDERING_POINT_LIGHT_DISABLE_DYNAMIC_SHADOW，若该宏也要移植需共用同一 PostLoad，否则两宏不能同时生效。

简单移植 改动方式：UE5 UPointLightComponent 结构未变，仅缺 PostLoad override，照搬即可。

在 Serialize 之后新增实现

void UPointLightComponent::PostLoad()
{
    Super::PostLoad();
#if XD_OPT_STATIC_POINT_LIGHT_SET_HIDDEN_IN_GAME && (!UE_EDITOR)
    if (Mobility == EComponentMobility::Static) this->SetHiddenInGame(true);
#endif
}
void UPointLightComponent::PostLoad()
{
	Super::PostLoad();
#if XD_OPT_STATIC_POINT_LIGHT_SET_HIDDEN_IN_GAME && (!UE_EDITOR)
	if (Mobility == EComponentMobility::Static) { SetHiddenInGame(true); }
#endif
}

⚠ UE5 需 include Components/SceneComponent.h 已由基类链带入；UE5 无 PostInterpChange override。

风险评估

原代码风险：只影响运行时；编辑器里仍显示光，可能造成美术误以为光被删除。

移植风险：低；仅隐藏渲染，可能影响依赖 HiddenInGame 的可见性判断逻辑。

开发自检

  • 非编辑器构建下 Static 点光 HiddenInGame 为真且烘焙照明仍在
  • 编辑器/移动端无编译与行为差异

结论置信度：high
