修改草案 · XD_FIX_BUG_FILTER_OUT_MOBILE_SIMULATOR_VIRTUAL_CONTROLLER

过滤移动模拟器误报的虚拟手柄连接事件（按 ESC 时）

未覆盖 移植 引擎内实现 结构性改动 工作量 M风险 中开发者 Ran Qing Sen主要模块 ApplicationCore

一句话结论：随 Android 输入栈移植，注意与真机手柄事件区分。

0. 根因溯源（这个宏为什么存在）

平台/工具链绕行

结论：Android 模拟器（MuMu/nemuVM）会暴露一个名为 nemuVM 的虚拟 gamepad，UE4 的 FAndroidInputInterface 在校验新设备时将其标记为 Valid 并分配 ControllerId，于是模拟器里按 ESC 会触发手柄连接/输入注入（UE4-4698）。XD 在 UE4 fork 里加 bMobileEmuController 标记：设备校验时按 Name.Contains(TEXT("nemuVM")) 置位并 continue，随后在 SendControllerEvents 主循环与 JoystickAxisEvent 里跳过该设备。UE5 的设备模型改为 TMap<int32, FAndroidInputDeviceInfo> InputDeviceInfoMap + GameControllerDataMap<FInputDeviceId, ...>（AndroidInputInterface.h:382），上游从未引入 nemuVM 过滤（rg 全树 0 命中），因此需要在新模型上重做等价过滤。

上游引入：平台行为引入（非上游代码缺陷）：Android 模拟器自带虚拟手柄设备名 nemuVM。XD 在 UE4 fork 新增处理：Private/Android/AndroidInputInterface.cpp:930-941（新设备校验：Name.Contains("nemuVM") → bMobileEmuController=true 并 continue）、:1199-1203（SendControllerEvents 主循环跳过）、:1524-1528（JoystickAxisEvent 提前 return），标记字段在 Public/Android/AndroidInputInterface.h:167-170。开关/动机：XDBuildFixBugConfiguration.cs:116-117（https://xindong.atlassian.net/browse/UE4-4698，“when user press 'ecs' keyboard with mobile-simulator, android will receive a controller connected event”）。

上游历史（是否修过）：上游从未提供等价能力：UE5 5.8.2 中 rg nemuVM|bMobileEmuController 在 Source/Runtime/ApplicationCore 下 0 命中，即上游未采纳任何按设备名过滤模拟器虚拟手柄的方案。UE5 重构了设备注册模型：设备校验在 SendControllerEvents:1134-1180（AndroidThunkCpp_GetInputDeviceInfo → 去重 Descriptor → InternalDeviceIdMappings.GetOrCreateDeviceId + GameControllerDataMap.Add(:1156-1161)；失败则 DeviceToRemove），事件主循环在 :1285-1293 遍历 InputDeviceInfoMap，摇杆入口 JoystickAxisEvent:1761 通过 GetInputDeviceByDeviceId → GameControllerDataMap 取配置。结论：宏的机制在 UE5 无对应实现，必须重写而非搬运。

为什么可以断定不是「故意为之」4 条依据
  • 模拟器虚拟手柄不是玩家输入，被当作真实 GameController 分配 ControllerId/玩家槽位属于平台噪声，不是设计行为。
  • XD 必须靠硬编码字符串才匹配得上，说明上游既无该设备的语义定义也无“虚拟设备”概念，属绕行而非标准做法。
  • UE4 上游设备校验里没有任何“按来源或名字忽略设备”的开关（只有 MappingState/DeviceType 状态机），可见是缺失能力。
  • XD 同时在事件主循环和摇杆入口两处过滤，说明“设备仍被注册、只是不发事件”是不得已的补丁式处理，而非有意设计。

调用方契约：契约方是 Android 输入设备状态机：设备注册（DeviceState: ToActivate/ToValidate/Valid）→ InternalDeviceIdMappings/GameControllerDataMap（UE5 :1156-1161）→ 每帧 SendControllerEvents 发消息（:1285-1313）→ JoystickAxis/JoystickButton 事件（:1761 起）→ MapControllerToPlayer（:1311 等）分配玩家槽位。若只在事件循环过滤，设备仍占用 InternalDeviceIdMappings/GameControllerDataMap 槽位，可能挤占真机手柄的槽位/玩家索引。

内层真实语义：UE4 宏语义：设备校验阶段命中 nemuVM 即 continue（不设 Valid，但仍留在设备表），事件层再按 bMobileEmuController 跳过 → 模拟器按 ESC 不再产生手柄事件，但设备记录仍在。UE5 无此分支：nemuVM 会被正常注册进 GameControllerDataMap 并获得 FInputDeviceId。

代码库惯例：UE5 设备层惯例是按 FInputDeviceId/descriptor 管理与映射（TInputDeviceMap<FString> InternalDeviceIdMappings，AndroidInputInterface.h:382），过滤应在校验阶段做（决定是否 GetOrCreateDeviceId/Add），而不是只在事件发送处 continue——否则映射表与玩家槽位仍被污染。

为何长期未被发现：影响面仅 Android 模拟器（MuMu/nemuVM）键鼠玩家：按 ESC/键盘时角色被手柄输入带偏、或真机手柄玩家槽位错位；真机不受影响，且报错为“偶发输入异常”而非崩溃，日志里只会看到一条“ControllerConnectionChanged”，容易被忽略。

XD 侧的做法与意图：fork：Public/Android/AndroidInputInterface.h:167-170 新增 bool bMobileEmuController；Private/Android/AndroidInputInterface.cpp:930-941 校验时置位并 continue、:1199-1203 主事件循环跳过、:1524-1528 JoystickAxisEvent 提前 return；开关 XDBuildFixBugConfiguration.cs:117（UE4-4698）。意图：让模拟器虚拟手柄不产生任何手柄输入，规避 ESC 触发连接事件。

⚠ 只在 UE5 的 SendControllerEvents:1285-1293 事件循环里加 nemuVM 过滤是不够的：设备仍会走 :1156-1161 GetOrCreateDeviceId + GameControllerDataMap.Add，占用 InternalDeviceIdMappings 槽位并可能让真机手柄的 MapControllerToPlayer 索引错位（多手柄绑定回归）；⚠ 按 Name.Contains("nemuVM") 硬编码会在模拟器改名/换厂商（MuMu 新版本、雷电、BlueStacks）时立即失效；⚠ 只按名字不看 source/descriptor 会误杀同名真机外设。

迁移方案（按根因定）

在新模型上重做，而不是照搬宏：1) 在设备校验阶段（UE5 SendControllerEvents:1152-1162，DeviceType==GameController 分支）识别模拟器虚拟设备——不只依赖 Name，优先用模拟器特有的描述符/厂商-产品 ID 组合或 AndroidThunkCpp 提供的设备 source 标志，命中则直接 DeviceToRemove.Push(KVPair.Key) 并 UE_LOGF(Warning)，绝不进入 InternalDeviceIdMappings/GameControllerDataMap；2) 事件层（:1285-1293、JoystickAxisEvent:1761）保留一层防御性过滤，但以“设备未在 GameControllerDataMap 中”为条件而非字符串；3) 把设备名/ID 列表做成 ini 可配置（模拟器厂商未来改名不用改引擎）；4) 用 MapControllerToPlayer 回归多人手柄绑定。

根因级自检用例

  • 正常：真机 Android 手柄（含蓝牙多手柄）能被识别、MapControllerToPlayer 槽位正确。
  • 根因场景：MuMu/nemuVM 模拟器内按 ESC 及键盘操作 → 不产生手柄连接/轴值事件。
  • 边界：模拟器改名（模拟不同 nemuVM 字符串/新模拟器）时可通过配置命中，不依赖硬编码单串。
  • 边界：真机外设名偶然含 nemuVM 之类子串时不被误杀（以 descriptor/vendor-product 为准）。
  • 回归：只在事件循环过滤的临时方案不得占用 InternalDeviceIdMappings，真机手柄索引不错位。

可反馈上游：最小复现：Android 模拟器（MuMu/nemuVM）连接键鼠后按 ESC → 收到 ControllerConnectionChanged/手柄输入（UE4-4698）。上游修法建议：在 Android 设备校验层引入“虚拟/模拟器设备”判定（基于 descriptor 或 source，而非名字子串），命中则不注册进 GameControllerDataMap。

审核意见：对 UE5 “固定数组→InputDeviceInfoMap/GameControllerDataMap TMap 重构”的判断准确，refactor 分类正确；但 after 有两处会直接编译失败/丢逻辑，必须修掉再落地。

完全重构 改动方式：UE5 用 TMap<FInputDeviceId,FAndroidGamepadDeviceMapping> 取代固定数组式 DeviceMapping，旧字段与循环均不存在，须按新结构重写过滤点。

代码脉络：UE4 在 AndroidInputInterface.cpp:930-941 校验新设备时按 Name 含 "nemuVM" 标记 bMobileEmuController（字段在 Public/Android/AndroidInputInterface.h:167-170），随后 :1199-1203（SendControllerEvents 主循环）、:1524-1528（JoystickAxisEvent）跳过它。UE5 该文件整体重构为 TMap 结构：InputDeviceInfoMap + GameControllerDataMap（AndroidInputInterface.h:382），设备校验在 SendControllerEvents:1134-1180，事件循环在 :1285-1293 遍历 InputDeviceInfoMap，摇杆入口 JoystickAxisEvent:1761。

风险评估

原代码风险：硬编码 "nemuVM" 字符串匹配，模拟器改名即失效；且过滤只按名字不看 source，真机外设若同名会被误杀。

移植风险：UE5 改为 TMap 后若只在事件循环过滤，设备仍占用 GameControllerIdMapping 槽位，可能导致真机手柄玩家索引错位，需回归多人手柄绑定（MapControllerToPlayer, :1311）。

开发自检

  • 移动模拟器按 ESC 不再触发虚握手柄连接/按键
  • 真机外接手柄连接、索引与震动功能正常
  • 模拟器下摇杆轴事件不再进入引擎

结论置信度：medium — UE5 FAndroidInputDeviceInfo 的 Name 在模拟器上是否仍为 "nemuVM"（可能被 AndroidThunkCpp_GetInputDeviceInfo 换成新名），需真机打印确认；过滤点也可改为在 :1163 创建 DeviceData 时打标记。
