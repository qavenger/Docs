修改草案 · XD_BUG_FIX_GET_VALID_PARTICLE_DATA

Beam 粒子源模块改用 ParticleIndices 获取合法 ParticleData（UE4-6419）

未覆盖 常开补丁 引擎内实现 结构性改动 工作量 S风险 中开发者 Lu Xun主要模块 Engine

一句话结论：Beam 源/目标索引未映射到 ParticleIndices，会取到非法粒子数据

可主动舍弃性（UE5 架构更替）

直接舍弃 Cascade 粒子 → Niagara

判定依据：UE5 特效体系已全面转向 Niagara，Cascade 仅保留兼容维护；项目迁移到 UE5 后特效会重做，针对 Cascade 运行时的定制可在迁移时直接不带过去。

舍弃前提：前提：迁移后在 UE5 用 Niagara 重做特效（不再走 Cascade 运行时）

UE5 替代能力：Niagara（NiagaraSystem / NiagaraComponent / NiagaraDataInterface）

相关文件：Source/Runtime/Engine/Private/Particles/ParticleBeamModules.cpp

0. 根因溯源（这个宏为什么存在）

上游缺陷（需上游修复或长期携带补丁）

结论：XD(UE4-6419) 在 Beam 取 Source/Target 粒子处先经 Emitter->ParticleIndices[LastSelectedParticleIndex] 映射并做范围检查再 GetParticleDirect，避免读到非法/失效粒子数据。

上游引入：上游引入点被历史复制提交掩盖：-S 与 --diff-filter 只命中 261478713775(2016-05-18 Gil Gribb，Dev-Rendering 到 Dev-Main 复制 CL 2981742)，即 4.12/4.13 时代已存在；同函数其它落点(:1953-1957 递增、:1964/:1969 比较赋值)都用 ParticleIndices 映射，只有初始复用上次选中粒子这一处直接用 LastSelectedParticleIndex。

上游历史（是否修过）：未修：5.8.2 ParticleBeamModules.cpp:1926(源)/:2390(目标)不变；ue5-main 同内容同行号，文件迁到 Engine/Plugins/FX/Cascade/Source/CascadeRuntime/Private/Particles/ParticleBeamModules.cpp。4.12~5.8.2 各 tag 均含该写法。

为什么可以断定不是「故意为之」4 条依据
  • ①ParticleIndices 语义即活跃序号到粒子数据下标(ParticleEmitterInstances.h:292-295)，引擎自带 GetParticleDirectIndex(:555-568) 就做该映射
  • ②同文件 :1964 SourceIndex 与 ParticleIndices[Index] 按映射后下标比较，若初始值不映射则比较永远不可靠
  • ③GetParticleDirect 只按 [0,MaxActiveParticles) 判界、不校验活跃性(ParticleEmitterInstances.cpp:2620-2628)，必须传数据下标
  • ④兄弟模块 ParticleTrail2EmitterInstance.cpp:2266/:2285-2287 正是先映射再使用，惯例明确

调用方契约：影响 Beam2 的 Source/Target 取值(PEB2M_Branch/PEB2M_Target，:1915-1921/:2380-2390)，进而影响所有 Beam 的起止位置与粒子索引。

内层真实语义：传活跃序号时 GetParticleDirect 在 [0,MaxActiveParticles) 内返回未激活槽位的非空指针(不校验活跃性)，RelativeTime 判定可能误通过并把垃圾数据当粒子；XD 版越界时置 -1，走重新挑选分支(:1928-1970)，并使 :1964 的比较成为数据下标对数据下标。

代码库惯例：用引擎自带 GetParticleDirectIndex(InIndex)(ParticleEmitterInstances.h:562-568)或照 Trail2 先映射的写法。

为何长期未被发现：只表现为 Beam/分支 Beam/Target 偶发粒子位置跳变或闪烁，不崩不报错；槽位未复用时映射与下标常相同，难稳定复现。

XD 侧的做法与意图：fork :1906-1918(源)/:2395-2407(目标)在 if (SourceEmitter && SourceEmitter->ParticleIndices) 内用下标范围检查后取 ParticleIndices[LastSelectedParticleIndex]，否则 -1；config:534-536 注释加 UE4-6419。

①改用 GetParticleDirectIndex() 时其边界是小于 MaxActiveParticles 而非 ActiveParticles，会把已失效槽位当合法(弱于 XD 的检查)；②只修 Source 漏掉 Target(:2390)；③顺势把 LastSelectedParticleIndex 全当数据下标(如改 :1953 的递增)会破坏活跃序号循环语义并可能越界。

迁移方案（按根因定）

port-as-is：在 UE5 同两处(:1926/:2390)加映射与范围检查；5.9+ 路径迁至 CascadeRuntime 插件，避免 Engine 与插件两份重复修改。回归 Beam、分支 Beam、Target 模式与单粒子/满槽场景。

根因级自检用例

  • 活跃数=1 且 LastSelectedParticleIndex=0 时取到 ParticleIndices[0] 的粒子而非槽位 0 的垃圾数据
  • LastSelectedParticleIndex 不小于 ActiveParticles 时回落重新挑选且不调用超界 GetParticleDirect
  • 槽位复用(ParticleIndices 项与下标不同)时 Beam 起点随该粒子运动不跳变
  • Source 与 Target 两处都生效(各测一次)
  • TargetEmitter 为空时行为与迁移前一致

可反馈上游：用 Beam2(PEB2M_Target/PEB2M_Branch) 让活跃粒子数小于 MaxActiveParticles 且槽位被释放复用，观察 Branch 端点跳到已失效粒子位置；对照 ParticleTrail2EmitterInstance.cpp:2266 的正确做法作为最小复现。

风险评估

原代码风险：LastSelectedParticleIndex 与 ParticleIndices 索引语义不同，直接使用会读到非法粒子数据（Jira UE4-6419）。

移植风险：Beam 源/目标取位逻辑，影响所有 Beam 粒子表现；回归 Beam、分支 Beam、Target 方式。

开发自检

  • Beam 源/目标粒子位置正确
  • LiveParticleIndices 压缩（有死亡粒子）时 Beam 不抖/不闪

结论置信度：high
