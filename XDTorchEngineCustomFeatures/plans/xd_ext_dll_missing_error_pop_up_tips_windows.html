0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：根因是 XD 产品需求：启动器缺 DLL 时给玩家中文引导弹窗，弹窗逻辑在启动器侧；引擎仓库只承载构建期开关（UBT 宏）与本地化文案（BaseEngine.ini），引擎自身不使用。不是上游缺陷，也不是可弃用项。

上游引入：XD 自加；fork 内仅两处：Source/Programs/UnrealBuildTool/Configuration/XDBuildConfiguration/XDBuildMiscConfiguration.cs:171 与 Config/BaseEngine.ini:2573-2578；未做提交级追溯（P3）。

上游历史（是否修过）：已核实 4.26 fork 现状如此；对 D:/Torchlight/frontend/trunk 全树 -l 检索该宏与文案，仅命中上述 2 个文件（无任何 C++ 读取点）。开关经 UEBuildTarget.cs:3839-3855 反射生成全局 #define，消费者在本仓库之外（启动器/前端）。UE5 上游无此 XD 私有符号，无需上游核对。

为什么可以断定不是「故意为之」3 条依据
  • 不是上游缺失：UE5 上游不可能为 XD 提供启动器文案开关，属私有扩展
  • 不是上游缺陷：删掉它不改变任何引擎行为（零读取点），其定位就是给启动器用的构建期开关
  • 文案宿主选在引擎 BaseEngine.ini 是 XD 既有惯例，同族的 PAK/OOM/DX 开关同样处理

调用方契约：实际契约在启动器侧：读 ini 键 LaunchDllMissingErrorTitleTxt/ContentTxt_CN|EN（BaseEngine.ini:2574-2577）；引擎侧零依赖。

内层真实语义：值为 1 时 UBT 会按 XDBuildConfiguration.ConfigurationClasses 反射所有 public static int 字段并生成 #define（UEBuildTarget.cs:3849-3855），但引擎内无人 #if 它；开关本身无失败路径。

代码库惯例：XD 同类开关一律「UBT 宏 + BaseEngine.ini 文案」成对出现：XDBuildMiscConfiguration.cs:167-173 的 OOM/PAK/DX/DLL 四个 *_POP_UP_TIPS_WINDOWS。

为何长期未被发现：引擎内无读取点→无效果→日志/崩溃里都观察不到，只有启动器缺 DLL 场景才会暴露文案缺失。

XD 侧的做法与意图：给启动器缺 DLL 场景提供可操作的引导文案，避免玩家只看到闪退。

⚠ 因「引擎内 grep 无引用」判定为死代码删除，会连带删掉启动器依赖的宏与 ini 键，导致缺 DLL 时静默闪退；⚠ 反向陷阱是只搬 ini 不搬 XDBuildMiscConfiguration.cs 定义，启动器按 UBT 宏编译会直接失败。

迁移方案（按根因定）

port-as-is：整段搬入 UE5 的 XDBuildMiscConfiguration.cs 与 Engine/Config/BaseEngine.ini，宏名与键名保持完全一致；迁移验证确认启动器仍能取到宏、ini 键可读。

根因级自检用例

  • 启动器缺 DLL 时按 locale 弹中文/英文文案（zh 走 _CN）
  • UE5 构建日志出现该 XD 宏定义（UBT 反射生效）
  • ini 四个键在 UE5 BaseEngine.ini 合并后仍未丢失
