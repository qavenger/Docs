修改草案 · XD_TORCHLIGHT_RUNTIME_DEVICE_PROFILE

运行时设备档案（DeviceProfile）切换支持

部分覆盖 接入点 需接入点 仅加接入点 工作量 M风险 中开发者 Yu Hang主要模块 Plugins/AndroidDeviceProfileSelector

一句话结论：优先用 UE5 原生 SetOverrideDeviceProfile/Selector，仅当确需多 DP 合并才加引擎扩展

背景：允许在运行时根据设备/画质档位切换 DeviceProfile，动态调整分辨率、特效等级等。

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：给设备档选择器接口加 XDGetRuntimeDeviceProfileNames/XDGetBaseDeviceProfileNames/XDShouldProcessProfileName(IDeviceProfileSelectorModule.h:28-97)，在 GetPlatformDeviceProfileName(UE4 DPM:784-1008) 里把多个匹配档(除基档外)的 CVars 合并进最终档，并给 DP 树遍历加 MaxStackTraversal 防环、把循环引用检测从 Fatal 降为 Error。

上游引入：P4 副本无 git 历史；UBT 开关 XDBuildProjectFeaturesConfiguration.cs:36 归属 Yu Hang(=1)；实现落点 IDeviceProfileSelectorModule.h:28-97、DeviceProfileManager.cpp:195-197/327-337/370-406(MaxStackTraversal)、454-462(Fatal→Error)、807-1008(合并 CVar)、994(PIE 不走该路径的注释)

上游历史（是否修过）：UE5 5.8.2：IDeviceProfileSelectorModule.h:21 类、:31 只有 GetRuntimeDeviceProfileName；DPM:1631-1656 仅 :1649-1651 单名分支；TestProfileForCircularReferences:976 仍是 UE_LOGF(LogDeviceProfileManager, Fatal)(:985)，XD 的降级未被上游采纳；DP 遍历已改走 FConfigCacheIni/ConfigSystem(:143 GetDPChain、:161-166、:315-321 GetFragmentCVars)。

为什么可以断定不是「故意为之」3 条依据
  • XD* 命名与头文件 Critical 注释是私有约定，非上游 API
  • 上游 5.x 用 UDeviceProfileFragment/FragmentIncludes(DeviceProfileFragment.h:14、DPM:184-185) 解决同类“多来源合并”，路线不同说明上游不认为原逻辑有缺陷
  • DPM:994 注释写明 PIE 预览不走该路径，属运行期流程补丁

调用方契约：平台 DP selector 模块需重载 XDGetRuntimeDeviceProfileNames(引擎内无实现，靠 XD 平台扩展)；唯一消费点 DPM:808，且返回数组最后一个元素必须具备最高优先级(头文件:32 强调)

内层真实语义：0 个匹配→退回 GetRuntimeDeviceProfileName；1 个→直接采用；>1→取最后一个并把前 N-1 个(跳过 BaseDeviceProfileNames，:92-97)的 CVars 合并写入该档，用 XDGetProcessedFinalDeviceProfileNames 去重；成环时只报 Error 继续启动

代码库惯例：上游等价惯例是 Fragment：GDeviceProfilesIni 的 [X DeviceProfileFragment] 段 + CVars/FragmentIncludes，由 GetFragmentCVars(DPM:315)、GetCVarsFromDPFragmentIncludes(:334) 合并

为何长期未被发现：发生在启动极早期，出错表现为画质/分辨率异常或 CVar 组合非法；只有真机多档复现，PC 编辑器无感；Fatal 被降级后成环只剩一条日志

XD 侧的做法与意图：同一设备命中多档(如 Android_High+机型档)时合并 CVars 得到最终档，避免为每种组合手写一个 DP

①在 UE5 照抄 GConfig->GetArray(…, GDeviceProfilesIni) 会绕开 ConfigSystem 的分支变更追踪(DPM:184/:321)，热更回滚后读到过期值；②把 :985 的 Fatal 无脑改 Error 会掩盖真正的 DP 环，应只对合并产生的链降级；③MaxStackTraversal 去掉上限会真死循环。

迁移方案（按根因定）

A(推荐)改用 UE5 原生 UDeviceProfileFragment + FragmentIncludes 表达机型档合并，引擎零改动(需 Android/iOS 各档回归)；B 照抄 XD 扩展点(接口 4 个 inline 默认实现)但 CVar 读取改走 ConfigSystem，且合并结果不写回 DeviceProfiles.ini；C 构建期生成组合档，运行时零逻辑(最稳但内容膨胀)。

根因级自检用例

  • 单匹配时结果与 UE5 原生 GetRuntimeDeviceProfileName 一致
  • 0 匹配退回默认档且不崩
  • 多匹配时 CVar 生效顺序=数组顺序，基档被跳过
  • 虚假环只报 Error；真环仍可定位
  • Android/iOS 各档启动后画质与分辨率符合配置表

可反馈上游：可选：在 BaseDeviceProfiles.ini 建两个叶子 DP 并让 selector 返回两个名字，UE5 只会采用其中一个(DeviceProfileManager.cpp:1649-1651)，即“无法合并多档”；若希望上游支持可据此提需求。

2. 修改步骤（接入点）

  1. 引擎侧只加接入点
    需要的接入点：IDeviceProfileSelectorModule（已有 ModularFeature 扩展点）、UDeviceProfileManager 多档 CVar 聚合入口（如需）（机制：ModularFeature）。引擎改动应最小、稳定、无业务语义。
  2. 插件侧实现完整逻辑
    项目实现 IDeviceProfileSelectorModule 选 DP，运行时用 SetOverrideDeviceProfile；多档合并需引擎在 DeviceProfileManager 加扩展点
  3. 无插件时的行为
    未绑定接入点时应回退到官方默认行为（引擎侧不能假设插件存在）。

风险评估

原代码风险：运行时改写 GDeviceProfilesIni 的 CVars 数组并加锁遍历，可能污染 DeviceProfiles.ini、覆盖热更值；MaxStackTraversal 仅防死循环。

移植风险：改的是启动期 DP 选择路径，出错将导致全局画质/分辨率异常甚至 CVar 组合非法崩溃，需覆盖 Android/iOS 各档设备回归。

开发自检

  • 各画质档设备启动后 ActiveDeviceProfile 与期望一致
  • 循环依赖 DP 只报 Error 不 Fatal 崩溃
  • PIE/PreviewDevice 路径不被 XD 合并逻辑影响

结论置信度：medium — UE5 的 DP CVar 应用已移到 InitializeCVarsForActiveDeviceProfile:855（含 bPushSettings/bIsDeviceProfilePreview/bForceReload 三个参数），合并逻辑的最终插入点需按新流程复核。
