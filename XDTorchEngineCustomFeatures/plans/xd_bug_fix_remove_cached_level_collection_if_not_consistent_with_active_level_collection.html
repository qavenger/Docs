修改草案 · XD_BUG_FIX_REMOVE_CACHED_LEVEL_COLLECTION_IF_NOT_CONSISTENT_WITH_ACTIVE_LEVEL_COLLECTION

当 ULevel::CachedLevelCollection 与 ActiveLevelCollection 不一致时清除缓存（UE4-3863）

部分覆盖 常开补丁 引擎内实现 仅加接入点 工作量 S风险 中开发者 Lu Xun主要模块 Engine

一句话结论：Multiworld 场景需重点验证

0. 根因溯源（这个宏为什么存在）

上游缺失能力（UE5 可能已补）

结论：UWorld::ConditionallyCreateDefaultLevelCollections 仅在 GetCachedLevelCollection()==nullptr 时 AddLevel；若缓存指向另一 DynamicSourceLevels 集合则既不清理也不加入，cook 下产生不一致 World 状态。XD 加 else-if：cook 加载且缓存为 DynamicSourceLevels 且不等于活动集合时先 RemoveLevel 再 AddLevel。

上游引入：上游逻辑自 f08010857989（2016-10-04 John Pollard，Copying Dev-Networking to Main）引入，同一提交即有 'Don't add the persistent level…' 注释与 nullptr 判断。XD 侧 XDBuildFixBugConfiguration.cs:435（Jira UE4-3863），fork World.cpp:1796。

上游历史（是否修过）：未修：5.8.2 World.cpp:2674 仍只在 nullptr 时 AddLevel；ue5-main 同（:2673）。InitWorld 中确有一处清理（World.cpp:2520，3b81cf820158e 2020-09-24 Marcus Wassmer），但条件为 GEngine 有 WorldContext 且非 SeamlessTravel，覆盖不到 cooker 加载路径。

为什么可以断定不是「故意为之」3 条依据
  • 上游注释明确承认 PersistentLevel 可能已在别的集合中，是刻意跳过 AddLevel
  • Epic 另在 InitWorld:2519-2523 主动 RemoveLevel，说明清理被有意放在别处而非此函数
  • XD 的 else-if 只在 GIsCookerLoadingPackage 下生效，属内容/工具链场景而非引擎通用行为

调用方契约：LevelCollections/ActiveLevelCollectionIndex 由 FLevelCollection::AddLevel/RemoveLevel 维护，Level 归属影响 GetActiveLevelCollection、光照场景、流关卡与 cook 结果。

内层真实语义：FLevelCollection::AddLevel(World.cpp:683-692) 有 check(Level->GetCachedLevelCollection()==nullptr)，RemoveLevel(694) 有 check(==this)；因此必须严格先 RemoveLevel 后 AddLevel。

代码库惯例：集合增删统一走 FLevelCollection::AddLevel/RemoveLevel（内部维护 Levels 与 CachedLevelCollection 双向一致），不直接改 CachedLevelCollection。

为何长期未被发现：仅 cook（GIsCookerLoadingPackage）或特定多世界/流关卡组合触发，表现为 DDC/包内容偶发不一致，非崩溃。

XD 侧的做法与意图：fork World.cpp:1796-1802，cook 加载时把 PersistentLevel 从陈旧集合移回活动集合并保证后续引用一致。

直接照抄 UE4 else-if 会踩 UE5 重构差异：ActiveLevelCollectionIndex 由 FindOrAddCollectionByType_Index(2668) 无条件赋值，SetPersistentLevel 在 2669；若目标集合已含该 Level 再 AddLevel 会命中 World.cpp:688 的 check 崩溃。必须先确认 Cached != &LevelCollections[ActiveLevelCollectionIndex] 再 RemoveLevel。

迁移方案（按根因定）

按根因移植并放宽：在 2677 if 后加 else-if，条件 GIsCookerLoadingPackage && Cached->GetType()==DynamicSourceLevels && Cached!=&LevelCollections[ActiveLevelCollectionIndex]；严格 RemoveLevel→AddLevel。评估去掉 GIsCookerLoadingPackage 以覆盖多世界运行期（XD 已指出这是窄修复）。

根因级自检用例

  • cook 加载时缓存指向陈旧 DynamicSourceLevels，最终只属于活动集合且 Cached==活动集合
  • 目标集合已含该 Level 时不触发 check(World.cpp:688)
  • 正常初始化（缓存 nullptr）行为与 UE5 原生一致
  • 非 cook 多世界场景不误移 PersistentLevel
  • cook 产物中 World/LevelCollection 归属确定可重复

可反馈上游：可向 Epic 反馈：ConditionallyCreateDefaultLevelCollections 只处理 nullptr 缓存，建议对 '同类型不同集合' 的陈旧缓存做一致性校正（附 cooker 加载最小复现）。

代码脉络：宏在 UWorld::ConditionallyCreateDefaultLevelCollections(World.cpp:1780) 加 else-if：Cook 加载包时若 PersistentLevel 的 CachedLevelCollection 为 DynamicSourceLevels 且不等于当前 ActiveLevelCollectionIndex，则先 RemoveLevel 再 AddLevel。

步骤 1Runtime/Engine/Private/World.cppUWorld::ConditionallyCreateDefaultLevelCollections, UE5:2655（AddLevel 在 2676）

在 nullptr 判断后加 else-if 修复

if (PersistentLevel->GetCachedLevelCollection() == nullptr)
{
    LevelCollections[ActiveLevelCollectionIndex].AddLevel(PersistentLevel);
}
// UE5 到此结束，不一致的缓存无人清理
if (PersistentLevel->GetCachedLevelCollection() == nullptr)
{
    LevelCollections[ActiveLevelCollectionIndex].AddLevel(PersistentLevel);
}
#if XD_BUG_FIX_REMOVE_CACHED_LEVEL_COLLECTION_IF_NOT_CONSISTENT_WITH_ACTIVE_LEVEL_COLLECTION
else if (GIsCookerLoadingPackage &&
    PersistentLevel->GetCachedLevelCollection()->GetType() == ELevelCollectionType::DynamicSourceLevels &&
    PersistentLevel->GetCachedLevelCollection() != &LevelCollections[ActiveLevelCollectionIndex])
{
    PersistentLevel->GetCachedLevelCollection()->RemoveLevel(PersistentLevel);
    LevelCollections[ActiveLevelCollectionIndex].AddLevel(PersistentLevel);
}
#endif

⚠ 必须是同级 else-if，不能塞进 AddLevel 的 {} 内；GetType() 见 World.h:651。

步骤 2Runtime/Engine/Classes/Engine/Level.hGetCachedLevelCollection (UE5:1200) / FLevelCollection::AddLevel (World.cpp:683-692)

确认访问器与调用顺序

FLevelCollection* GetCachedLevelCollection() const { return CachedLevelCollection; }
// UE5 访问器不变，无需改；但 FLevelCollection::AddLevel 有
// check(Level->GetCachedLevelCollection() == nullptr);  (World.cpp:688)

⚠ UE5 断言更严，顺序颠倒会直接 check 崩。

风险评估

原代码风险：只在 GIsCookerLoadingPackage 下修，运行时(多世界)不一致缓存仍存在，属窄修复。

移植风险：ActiveLevelCollectionIndex 已被 FindOrAdd 改写(2668)，RemoveLevel 后 AddLevel 若集合已含该 Level 会触发 check。

开发自检

  • Cook 含 Level 实例/多 World 场景无 check 崩
  • Cook 后关卡集合归属正确
  • 运行时 MultiWorld 切关正常

结论置信度：medium — UE5 World.cpp:628-699 把不一致改成了 check 断言，需确认上游是否已在别处做了缓存失效。
