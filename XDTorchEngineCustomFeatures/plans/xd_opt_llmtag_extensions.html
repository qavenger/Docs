引擎 LLM Tag 扩展（增加项目自用标签）

UE5 已覆盖 删除 可工程化 无需改引擎 工作量 S风险 低开发者 Wang Xiao Bo主要模块 Engine

一句话结论：改用 UE5 自定义标签 API

0. 根因溯源（这个宏为什么存在）

上游缺失能力（UE5 可能已补）

结论：XD 为了给项目自己的系统（RunnableThread、UpdateReflectionCaptureContent、UpdateDeferredCaptures、TickerTick、WorldTick、ViewportDraw）单独统计内存，把这 6 个标签**无条件并进引擎的 LLM_ENUM_GENERIC_TAGS 枚举**。UE5 的头文件明确写着"不要往这些宏里加，请使用下面的 LLM_DECLARE_TAG 系列宏创建新标签"，并提供了完整的声明/定义 API（LLM_DEFINE_TAG 等），因此应该改用官方 API 而非改引擎枚举。

上游引入：XD 的 LLM 标签扩展（UE4 版在 LowLevelMemTracker.h 的 LLM_ENUM_GENERIC_TAGS 中插入 6 个标签，并在 Ticker.cpp 等实现处使用）。

上游历史（是否修过）：已核实 UE5.8.2 Source/Runtime/Core/Public/HAL/LowLevelMemTracker.h：:168 注释原文 **"Do not add to these macros. Please use the LLM_DECLARE_TAG family of macros below to create new tags."**；:313 也有"Do not add to these macros. Please use the LLM_DECLARE_TAG macros below"的提示（并说明标签数量上限）；:437 `#define LLM_DEFINE_TAG(UniqueNameWithUnderscores, ...) FLLMTagDeclaration UE_JOIN(LLMTagDeclaration_, UniqueNameWithUnderscores)(...)`；:455 说明如何声明由 LLM_DEFINE_TAG 定义的标签（配合 LLM_SCOPE_BYTAG 或按名引用）—— 即上游已提供项目侧声明标签的正规途径。

为什么可以断定不是「故意为之」2 条依据
  • 上游在头文件里用醒目注释反对改枚举，并明确指出替代 API，属有意的边界约束（枚举保留给引擎内置标签）。
  • XD 当年改枚举是当时缺少项目标签机制（上游能力缺失），不是刻意违反约定。

调用方契约：项目自建系统的内存需要在 LLM 中单独归类，便于按系统查看内存占用（否则只能并入通用标签，无法归因）。

内层真实语义：UE4（XD）：直接把项目标签塞进 LLM_ENUM_GENERIC_TAGS（引擎枚举），并更新相关上限/数组。UE5（上游）：项目侧用 LLM_DEFINE_TAG/LLM_DECLARE_TAG 声明标签（不占用引擎枚举），配合 LLM_SCOPE_BYTAG 使用。

代码库惯例：上游要求：新增标签用声明式 API（LLM_DEFINE_TAG 家族），引擎枚举只保留内置标签，避免升级冲突与上限问题。

为何长期未被发现：属"内存可观测性"定制：不迁移不会崩，但项目自建系统的内存会并入通用标签（分析时无法归因）；且改枚举在升级时容易与上游新标签冲突（标签 id 位移/上限冲突）。

XD 侧的做法与意图：XD 的目标是让项目自建系统（线程、反射捕获、Ticker、WorldTick、视口绘制等）的内存占用在 LLM 中单独可见。

⚠ 三条注意：①**不要再改引擎枚举**——上游注释明确反对，且升级时会与新增内置标签冲突（id 位移、上限检查 :313）；②改用 `LLM_DEFINE_TAG` 声明后，使用点要配套 `LLM_SCOPE_BYTAG`（或按名引用），否则标签不生效；③标签数量与命名要符合规范（:421 提到父子标签分隔符在 LLM_DEFINE_TAG 中需用下划线）。

迁移方案（按根因定）

按 upstream-missing → 改用上游 API 处理：删除对 LLM_ENUM_GENERIC_TAGS 的插入，在项目侧（或相应模块）用 `LLM_DEFINE_TAG` 声明这 6 个标签，并在原使用点改用 `LLM_SCOPE_BYTAG` 引用。

根因级自检用例

  • LLM 报告中能看到项目自定义标签（6 个系统各自可归因）
  • 标签数值正常（无溢出/错位，不受引擎内置标签数量变化影响）
  • 引擎升级后标签仍有效（不依赖修改引擎枚举）
  • 性能开销可接受（scope 宏在 LLM 关闭时无负担）

可反馈上游：无需反馈（上游已提供正规 API 且在头文件写明用法）。

3. 代码级实现（开发用）

独立 Agent 审核并修正修正 2 处　提出问题 2 条

审核意见：abandon 方向正确（UE5 提供项目标签区间 ProjectTagStart=150 见 LowLevelMemTracker.h:307、LLM_CUSTOM_TAG_START :316），但 6 处调用点只列了 4 处、且缺 LLM_DEFINE_TAG，是本条两个必修点。

建议舍弃 改动方式：UE5 提供项目标签区间与声明 API，往引擎枚举硬塞标签的做法可被替代。

代码脉络：宏把 ExtRunnableThreadRun/ExtUpdateReflectionCaptureContent/ExtUpdateDeferredCaptures/ExtTikerTick/ExtWorldTick/ExtViewportDraw 6 个标签无条件并进 LLM_ENUM_GENERIC_TAGS（Runtime/Core/Public/HAL/LowLevelMemTracker.h:226-233）；#if XD_OPT_LLMTAG_EXTENSIONS 只控制 6 个调用点：Containers/Ticker.cpp:58、GameEngine.cpp:707、LevelTick.cpp:1389、SceneCaptureComponent.cpp:386、Components/ReflectionCaptureComponent.cpp:1032、Windows/WindowsRunnableThread.cpp:70。

步骤 1Runtime/Core/Public/HAL/LowLevelMemTracker.hLowLevelMemTracker.h:226

不移植这 6 个引擎枚举，改用 UE5 项目标签 API

/* XD_OPT_LLMTAG_EXTENSIONS begin */
macro(ExtTikerTick, "ExtTikerTick", NAME_None, NAME_None, -1)
/* XD_OPT_LLMTAG_EXTENSIONS end */
// 项目模块内(非引擎):
LLM_DECLARE_TAG(ExtTikerTick);
// 调用点:
LLM_SCOPE_BYTAG(ExtTikerTick);

⚠ UE5 保留 ELLMTag::ProjectTagStart=150(LowLevelMemTracker.h:307)、LLM_CUSTOM_TAG_START(:316)

步骤 2Runtime/Core/Private/Containers/Ticker.cppTicker.cpp:58

把 6 处 #if+LLM_SCOPE(ELLMTag::ExtXxx) 换成 BYTAG 声明

#if XD_OPT_LLMTAG_EXTENSIONS
 LLM_SCOPE(ELLMTag::ExtTikerTick);
#endif
// 项目模块 .cpp 中定义一次（缺 LLM_DEFINE_TAG 会链接失败）
LLM_DEFINE_TAG(ExtTikerTick);
// 头文件: LLM_DECLARE_TAG(ExtTikerTick);
// 调用点: LLM_SCOPE_BYTAG(ExtTikerTick);

⚠ 需项目侧 include LowLevelMemTracker.h

风险评估

原代码风险：改引擎枚举会改变 LLM_TAG_COUNT 布局，标签索引与 CSV 表头耦合，越界即崩。

移植风险：标签移出引擎后，6 个调用点须同步迁移，漏一处即丢失该作用域统计。

开发自检

  • -llm 打开后 LLMFULL 能看到 Ext* 各标签
  • 确认未破坏 ELLMTag 枚举顺序/static_assert

结论置信度：high
