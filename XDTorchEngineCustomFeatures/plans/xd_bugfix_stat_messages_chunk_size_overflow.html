修改草案 · XD_BUGFIX_STAT_MESSAGES_CHUNK_SIZE_OVERFLOW

修复 Stat 线程消息块大小溢出崩溃（默认关闭）

未覆盖 删除 引擎内实现 引擎内补丁 工作量 S风险 低开发者 Wang Xiao Bo主要模块 Core

一句话结论：XD 侧默认关闭（值=0），UE5 未采纳该修复但当前未启用，可直接删除；若将来开启需重打补丁

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：宏里是两件互相抵消的事：ChunkedArray.h:68-74 与 :212-217 把 FChunk 改成 MallocZeroed + placement new（消除未初始化 FStatMessage 的读取面），Stats2.h:1080 用 `#if XD_… || 1` 在编辑器强制 64K（绕过 Epic 4.20 起为 TBB 分配器死锁设的 4K）。宏值=0，清零分支根本没编译，而 `|| 1` 让大分块一直生效——现网是「有风险、收益未知」的状态。

上游引入：Epic 编辑器 4K：4.19 无、4.20.0-release 有（d90da4ab1af7，2018-05-23 Marc Audy「Merge to Dev-Main for 4.20 @ 4090813」，Stats2.h:1097 注释「Smaller chunks prevent malloc deadlocks when running in the editor with TBB allocator」）。XD 的清零 + 强制 64K 在 4.26 fork：ChunkedArray.h:68/212、Stats2.h:1080；开关 XDBuildFixBugConfiguration.cs:369 = 0（注释「Fix Stat Thread's crash」）。

上游历史（是否修过）：上游未变：5.8.2 StatsSystemTypes.h:1030 WITH_EDITOR=4*1024（同一句 2018 年注释）、:1032 否则 64K；ChunkedArray.h:72 与 :265 仍是 `Chunks.Add(new FChunk)`（UE5 把 Add 重构为先算 NewNumChunks，语义相同）。即上游既未清零、也未接受 XD 的 64K。

为什么可以断定不是「故意为之」4 条依据
  • FStatMessage 默认构造为空（StatsSystemTypes.h:842 `TStatMessage(){}`）、FChunk 仅含元素数组（ChunkedArray.h:342-346），Epic 从未声明未初始化元素是安全的；
  • XD 自己用 MallocZeroed 说明作者判断这里需要清零——若 64K 真安全，宏内不会带这个补丁；
  • `#if XD_… || 1` 是为保留宏名而留的临时开关写法（注释「XD - We want to use larger chunk as default」），不是配置化设计；
  • 宏=0 却保留 64K 生效，自相矛盾 → 非有意为之的稳定状态。

调用方契约：FStatMessagesArray = TChunkedArray<FStatMessage, MESSAGES_CHUNK_SIZE>（StatsSystemTypes.h:1036）；生产 StatsSystemTypes.h:1243 AddElement→ChunkedArray.h:193-209 就地 new；消费 StatsCommand.cpp:1815-1816 按 Num() 遍历、Stats2.cpp:1000-1018 统计、StatsFile.h:673-676 Reserve 后 placement new。

内层真实语义：宏=1：新 chunk 走 FMemory::MallocZeroed + placement new（placement new 调空构造，清零保留）→ 未写入元素为 0（读到垃圾 enum 变成读 0，是假值但安全）；宏=0：`Chunks.Add(new FChunk)`，未写入元素是脏内存。编辑器分块：XD 64K vs Epic 4K（4K 是 Epic 明确的 TBB malloc 死锁规避）。

代码库惯例：容器默认构造不改变分配方式（ChunkedArray.h:72 / UE5:265）；避免未初始化读的惯例是元素侧显式初始化或 FMemory::Memzero，而不是给容器加平台特判。

为何长期未被发现：stat 线程只在 chunk 边界附近偶尔读到未写入元素，崩溃栈落在消费端且不可复现；宏置 0 后没人再验证，同时编辑器 64K 反而放大 malloc 抖动——正是 Epic 4K 要压的问题。

XD 侧的做法与意图：XDBuildFixBugConfiguration.cs:369 注释「Fix Stat Thread's crash」；ChunkedArray.h 两处清零与 Stats2.h 的 `|| 1` 是同一次排查的产物。

①照搬 MallocZeroed+placement new 会让 TChunkedArray 隐含依赖「元素可零初始化」，而它是泛型容器（AddElement/Emplace 用就地构造），对非 POD 元素是 UB 风险写法；②把 `|| 1` 一起迁到 UE5 StatsSystemTypes.h:1030 会覆盖 Epic 的 4K TBB 死锁规避（重现 4.20 修的问题）；③只迁清零而保留 64K（即 fork 当前状态）等于「为自己引入的风险付内存代价」，且宏为 0 时完全无效。

迁移方案（按根因定）

不迁移。UE5 保持 StatsSystemTypes.h:1026-1034（编辑器 4K/否则 64K）与 ChunkedArray.h:72/:265 的 `new FChunk`。若确要认真对待未初始化读：先在 5.8.2 用 ASAN/MallocZeroed 实验复现崩溃，再考虑给 TStatMessage 加显式零初始化或 FStatPacket 侧显式 Memzero，而不是改全局容器分配。

根因级自检用例

  • 编辑器构建确认 EStatMessagesArrayConstants::MESSAGES_CHUNK_SIZE == 4096（5.8.2 :1030），非编辑器 65536；
  • 新建 FStatMessage chunk 后未写入元素行为与 vanilla 一致（不依赖清零）；
  • 长时间 stat dumpframe（-ms=0.001）无崩溃、无 TBB 分配器死锁；
  • 4K 与 64K 两种分块的 stat 内存占用/帧耗时对比，确认 64K 收益是否真实存在。

风险评估

原代码风险：清零前 FStatMessage 元素为未初始化内存，stat 线程按 64K 目标块读取时可能越界/读脏数据；宏=0 时清零点被关掉而 64K 仍在，风险并未消除。

移植风险：不迁移无影响；若启用需先确认 64K 与 UE5 编辑器 TBB 分配器 deadlock 是否仍在。

开发自检

  • 编辑器下 stat start/stop 反复切换无崩溃
  • release 下统计采集与 DumpStats 正常

结论置信度：high — 64K 与 UE5 编辑器 TBB 分配器是否仍 deadlock 需真机验证
