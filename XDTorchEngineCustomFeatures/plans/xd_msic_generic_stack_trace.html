0. 根因溯源（这个宏为什么存在）

上游缺失能力（UE5 可能已补）

结论：把调用栈变成可序列化字符串，供 CrashSight 上报通道使用：Vulkan/GL fatal 时不再直接退出，而是 Broadcast(标题,消息,栈) 后重启（CL 1117979 描述「截断Vulkan Fatal报错，并用Crash Sight上报并用GLES重启」）。

上游引入：P4 CL 1117979（2022-09-09，tl_fronted_03，AutoMerge SprintUGS→MainLineWithUGS）新增 h:271/280 与 cpp:242 块；CL 2973730（2024-12-02，TORCHLIGHT-187320，gongbailiang）新增/调整 GetStackTraceWCHAR（h:291）。fork=4.26.2（Version.h:57-59），目标 5.8.2。

上游历史（是否修过）：p4 annotate 命中上述两 CL。UE5 侧 git grep 5.8.2-release 与 origin/ue5-main 在 Runtime/Core 均无 GetStackTrace；只有替代原语 GetStack()（GenericPlatformStackWalk.cpp:242）、StackWalkAndDumpEx（.h:284/295）、FDebug::DumpStackTraceToLog（AssertionMacros.cpp:891/897）——返回符号数组或写 ANSICHAR 缓冲，都不是 FString。上游从未实现该 API。

为什么可以断定不是「故意为之」3 条依据
  • 上游同时有 GetStack / StackWalkAndDump / DumpStackTraceToLog 却没有任何字符串栈入口，是能力空缺而非刻意限制。
  • XD 实现自注 'copied from FDebug::DumpStackTraceToLog'，属照官方代码自建，不是改上游。
  • 消费方是 XD 自加通道（CoreDelegates.h:341-345，CL 1113929 2022-09-08），上游没有这种签名的需求。

调用方契约：三处调用全在 XD_EXT_REPORT_ERROR_MSG_VIA_CRASH_TOOLS 下：VulkanUtil.h:13（XD_VK_FATAL_LOG_BEHAVIOR_TAKEOVER 宏体）、OpenGLShaders.cpp:3511、ShaderPipelineCache.cpp:1927；返回值直接进 Broadcast 的 const FString& 形参，空串=空上报。

内层真实语义：失败被吞：ProgramCounterToHumanReadableString 的 bool 返回值被忽略（cpp:242 块内），无 pdb 时该帧退化为模块+偏移；Context==nullptr 时 IgnoreCount+=2 以跳过自身与 CaptureStackBackTrace。WCHAR 版用 std::wstring{Str.begin(),Str.end()} 逐 char 加宽 → 非 ASCII 路径乱码，且 SystemMalloc 的 Size 不含结尾 0。shipping 分支（cpp:295 起）另打裸地址供离线符号化。

代码库惯例：UE 惯例是写缓冲而非返回字符串：FDebug::DumpStackTraceToLog（AssertionMacros.cpp:539/544）同款 SystemMalloc+逐帧拼接；XD 版就是它的 FString 化。

为何长期未被发现：只在 Vulkan/GL fatal、PSO 预编译失败等低频路径触发；现场常无符号（所以 shipping 还要打裸地址），平时没有调用者。

XD 侧的做法与意图：CL 1117979 引入，CL 2973730 因 TORCHLIGHT-187320 专门改实现 → 被当长期基础设施维护，而非一次性补丁。

①照抄 65535+SystemMalloc 深栈路径：内存紧张/OOM 时 SystemMalloc 返回 nullptr，紧接着的 HumanReadableString[0]=0 会二次崩溃，而这条路径恰恰在 OOM 时被调用。②UE5 的 StackWalkAndDumpEx 必须传 EStackWalkFlags::FlagsUsedWhenHandlingEnsure，传 0 会丢掉 ensure/crash 上下文的有效帧。③WCHAR 版 Size 未含 '\0'，调用方 SystemFree 前若构造 FString 会越界读。

迁移方案（按根因定）

按 upstream-missing 移植：声明放回 UE5 GenericPlatformStackWalk.h:295 附近，实现改走 StackWalkAndDumpEx(...,FlagsUsedWhenHandlingEnsure,Context)+FString(ANSI_TO_TCHAR)，弃用 SystemMalloc；UE5 无 CrashExtraMsgReporterWCHAR，可只保留 FString 版让 _WCHAR 变体走 *Stack。备选（更干净）：放进项目/SDK 侧 CrashSight 模块，只用公开 API，不污染 Engine。

根因级自检用例

  • 深栈 >100 帧：不越界且返回非空
  • MaxDepth=0 或 IgnoreCount≥Depth：返回空串且不崩
  • Context!=nullptr（外部线程）：不再额外 +2 偏移
  • Vulkan fatal 主路径：栈非空并能 Broadcast 成功
  • 含中文路径时 WCHAR 版不乱码，调用方释放后无泄漏

可反馈上游：非 bug 属 feature request：FGenericPlatformStackWalk 只有 GetStack()/StackWalkAndDumpEx()，无 FString 入口；任意 RHI fatal 处想直接拿栈字符串写入崩溃上报都必须自拼缓冲。

2. 修改步骤（接入点）

  1. 引擎侧只加接入点
    需要的接入点：FPlatformStackWalk::StackWalkAndDumpEx、ThreadStackWalkAndDump（机制：Delegate）。引擎改动应最小、稳定、无业务语义。
  2. 插件侧实现完整逻辑
    基于 FPlatformStackWalk::StackWalkAndDumpEx 封装，放项目崩溃上报模块
  3. 无插件时的行为
    未绑定接入点时应回退到官方默认行为（引擎侧不能假设插件存在）。

风险评估

原代码风险：MAX_DEPTH=100 固定栈数组+SystemMalloc，崩溃期重入或分配失败可致二次崩溃。

移植风险：UE5 CrashContext/Flags 语义不同，Flags 传错会截断有效栈帧。

开发自检

  • 断言后 GetStackTrace(20,2) 返回非空多行堆栈
  • Shipping 下原始 PC 数组打印到 GLog

结论置信度：medium — UE5.8 EStackWalkFlags 具体枚举值与 CrashContext 版本差异需编译确认
