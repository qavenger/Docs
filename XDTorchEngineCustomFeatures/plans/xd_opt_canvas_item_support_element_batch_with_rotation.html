3. 代码级实现（开发用）

独立 Agent 审核通过提出问题 1 条

审核意见：结构判断准确：UE4 CanvasTypes.h:972-978 GetRenderData、CanvasItem.cpp:418/447/520/548/560、Canvas.cpp:556-594；UE5 FCanvasBatchedElementRenderItem 已独立成 CanvasBatchedElementRenderItem.h（:15 类、IsMatch :76 比较 Transform.GetMatrixCRC、FRenderData 私有 :113、无 GetRenderData），CanvasItem.cpp:421-433 仍 push FinalTransform

完全重构 改动方式：功能等价但渲染代码被重排：FCanvasBatchedElementRenderItem 已从 CanvasTypes.h 移到独立头文件，顶点 API 改为 AddVertexf/FVector4f，必须按 UE5 结构重写。

代码脉络：CanvasTypes.h:972-978 给 FCanvasBatchedElementRenderItem 加 GetRenderData()；CanvasItem.cpp:418-421 改成恒定 PushRelativeTransform(Identity)，:447-548 旋转分支手算四角（FinalTransform.TransformPosition）后写顶点，:560-566 改为无条件 PopTransform；Canvas.cpp:556-594 仅在 DEBUG_CANVAS_ELEMENT_BATCH(=0) 下打批中断日志。原理：UE5 的 IsMatch 比较 Transform 的 CRC（CanvasBatchedElementRenderItem.h:76-84），旋转图元各自 push 变换即断批；把它烘进顶点后可与同材质图元共用批。UE5 仍走旧路径（CanvasItem.cpp:421-433 push、:484-488 pop），顶点 API 已改 AddVertexf/FVector4f（:452）。

风险评估

原代码风险：旋转顶点烘进 Position 会改变烘焙后的相对关系；DEBUG 日志原为 0，实际仅靠顶点手算，边界/DPI 缩放算错会出现图元偏移或抖动。

移植风险：Canvas 合批顺序变化会影响 HUD/调试绘制叠放与命中测试；同一 depth 下旋转与非旋转图元合进一批，若项目依赖“旋转单独成批”的绘制顺序会错位，需 Profile 合批数与视觉回归。

开发自检

  • HUD/Canvas 旋转图元位置与旧版逐像素一致
  • Slate.DrawBatchNum 与 STAT_Canvas_NumBatchesCreated 明显下降且无 z-order 错乱

结论置信度：medium — UE5 新增的 bApplyDPIScale/GlowInfo 等批键与旋转烘顶点共同作用下的顺序保证需实测
