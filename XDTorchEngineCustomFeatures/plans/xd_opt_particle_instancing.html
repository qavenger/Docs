修改草案 · XD_OPT_PARTICLE_INSTANCING

粒子实例化（Particle Instancing）：相同特效合并为一次 DrawCall

未覆盖 保留引擎 引擎内实现 深度侵入 工作量 L风险 高开发者 Gong Bai Liang主要模块 Engine

一句话结论：20 处引用的最大收益项；建议评估改用 Niagara+自定义数据接口/GPU 合并，避免在 UE5 渲染管线上重做实例化

背景：把使用同一粒子资源/材质的粒子系统实例合并提交（含 Shader 侧 Instancing 数据打包），是火炬之光特效性能的核心优化。相关调试宏 XD_OPT_PARTICLE_INSTANCING_DEBUG、Mac 编辑器开关 XD_OPT_PARTICLE_INSTANCING_DISABLE_ON_MAC_EDITOR。

可主动舍弃性（UE5 架构更替）

直接舍弃 Cascade 粒子 → Niagara

判定依据：UE5 特效体系已全面转向 Niagara，Cascade 仅保留兼容维护；项目迁移到 UE5 后特效会重做，针对 Cascade 运行时的定制可在迁移时直接不带过去。

舍弃前提：前提：迁移后在 UE5 用 Niagara 重做特效（不再走 Cascade 运行时）

UE5 替代能力：Niagara（NiagaraSystem / NiagaraComponent / NiagaraDataInterface）

相关文件：Source/Runtime/Engine/Classes/Particles/ParticleEmitter.h Source/Runtime/Engine/Private/Particles/FastParticleSystem/FastParticleSystemRender.cpp Source/Runtime/Engine/Private/Particles/Managers/InstancedParticleManager.cpp

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：XD 做了一套"粒子实例化"渲染优化：在 UPrimitiveSceneProxy 上新增虚函数 `CollectInstancedData`，给粒子发射器加 Instanced 相关标记，并在粒子渲染与场景代理提交路径上按"实例化"方式批量提交粒子（减少 DrawCall/状态切换，是 XD 侧收益最大的一项优化，宏定义处有 20+ 处引用）。UE5 中不存在 `CollectInstancedData`（PrimitiveSceneProxy.h 无此符号）也没有对应的粒子实例化实现，因此这份定制必须基于 UE5 的粒子系统架构（Niagara 为主 + 遗留 Cascade）整体重做。

上游引入：XD 的粒子渲染优化（XDBuildOptConfiguration.cs:141 定义；开启后 UPrimitiveSceneProxy.h:236-238 新增虚函数 CollectInstancedData，ParticleEmitter.h:259-305 给 UParticleEmitter 加 bIn… 标记，粒子渲染/场景代理提交路径按实例化批量处理；共 20+ 处引用）。

上游历史（是否修过）：已核实 UE5.8.2：①`CollectInstancedData` 在 Source/Runtime/Engine/Public/PrimitiveSceneProxy.h 与 Source/Runtime/Renderer/ 下 **均无命中**；②Source/Runtime/Engine/Public/Particles/ 下 `InstancedParticle`/`ParticleInstancing`/`bInstanced` **均无命中** —— 即上游没有对应的粒子实例化机制，XD 的定制无落点。

为什么可以断定不是「故意为之」2 条依据
  • 上游未实现"粒子实例化"属于能力边界（其优化方向为 GPU 粒子/Niagara 的批量模拟与渲染），不是刻意拒绝。
  • XD 的定制是其自研优化（20+ 处引用），需要在 UE5 上重新设计而非移植。

调用方契约：粒子渲染必须保证：语义与上游一致（粒子顺序/混合/排序/光照）、支持各类型粒子（Sprite/Mesh/Ribbon/Beam 等）、且实例化批量提交不能破坏半透明排序与深度写入规则。

内层真实语义：UE4（XD）：场景代理新增 CollectInstancedData 接口，粒子发射器带 Instanced 标记，渲染提交时按实例批量收集并绘制。UE5（上游）：无该接口与机制；粒子渲染走 Niagara（GPU/CPU 模拟 + 其自身的批处理与实例化路径）与遗留 Cascade。

代码库惯例：上游的批处理以 Niagara 的渲染器（如 Mesh/Sprite 渲染器）为单位，通过渲染器自身的数据流与批处理实现，而不是给所有图元代理加通用"实例化收集"接口。

为何长期未被发现：属"DrawCall/粒子渲染性能"优化：不迁移不会崩，只在大规模粒子场景（如战斗/特效密集）表现为 CPU 提交开销；而且宏默认状态与上游实现差异会被"先跑起来"的迁移节奏掩盖。

XD 侧的做法与意图：XD 的目标是降低大量粒子（尤其同材质/同网格的重复粒子）的绘制开销（合并提交、减少状态切换）。

⚠ 四点注意：①**这是最大收益项也是最大工作量项**（20+ 引用、跨渲染提交链路），排期需单独评估，不要按普通宏处理；②**先评估 Niagara 是否已覆盖收益**——UE5 的 Niagara 渲染器本身有批处理/实例化路径，若项目特效已迁到 Niagara，原 Cascade 时代的实例化优化收益可能已由 Niagara 接管（重复实现无收益）；③`CollectInstancedData` 是**场景代理的通用接口**，若强行加回会影响所有图元类型的提交路径（风险面大）；④半透明粒子排序与实例化批量提交存在天然冲突，重做时必须验证排序正确性（否则出现穿插/闪烁）。

迁移方案（按根因定）

按 xd-design/refactor 处理：①先量化收益（统计目标场景的粒子 DrawCall 与 CPU 提交耗时）；②评估 Niagara 渲染器的批处理能力是否已满足（若特效迁 Niagara，优先用官方路径）；③若仍需自研，建议**收敛在粒子渲染器范围内**实现（而非改 PrimitiveSceneProxy 通用接口），并单独验证半透明排序；④按 20+ 引用点逐项列出改造清单，纳入独立工作包排期。

根因级自检用例

  • 粒子渲染语义一致（顺序/混合/排序/光照，尤其半透明粒子无穿插闪烁）
  • 各类粒子类型正常（Sprite/Mesh/Ribbon/Beam 等）
  • 大规模粒子场景 CPU 提交耗时下降（收益可量化，达到或接近 UE4 水平）
  • 不破坏其它图元类型的渲染提交（若改动涉及通用接口）
  • 与 Niagara 共存正常（若项目同时使用 Niagara 与 Cascade）

可反馈上游：可向上游提议：为 Niagara 提供"跨发射器/跨组件的粒子实例化批处理"能力（大规模特效场景收益明显）。

1. UE5 现状与证据

结论依据：UE5 无粒子实例化（grep InstancedParticle/ParticleInstancing 无结果；Niagara 亦无同特效合并 DrawCall 的 Cascade 实例化语义），无 XD 的 InstancedParticleManager/CollectInstancedData

覆盖说明：核心自研优化，UE5 无等价

覆盖度：未覆盖  处置：保留引擎

2. 修改步骤（暂留引擎）

  1. 登记 Feature Card
    记录 owner、影响面、依赖、关闭条件、验证方式与回滚方式；这是当前最高风险的一类（引擎内深度改动）。
  2. 评估替代路径
    优先考虑改用 UE5 原生机制（如 Niagara / Substrate / PSOPrecache / WorldPartition）替代自研实现；替代前保留最小可用补丁。
  3. 设定复查条件
    每个版本复查一次：是否可以降级为插件/配置，或直接删除。
  4. Shader 侧配套
    删除 DerivedDataCache 重编 Shader；同步更新受影响的 shader permutation / ShaderVersion。

风险评估

原代码风险：FInstancedParticleManager 为进程级单例 TMap，SceneVisibility 单线程 Reset/Collect 再并行绘制，帧内若有多视图/多场景会互相污染；ParticleID 由编辑器工具生成，运行时不校验唯一性。

移植风险：改动场景收集与批次合并是最易崩的路径，涉及 Renderer/SceneVisibility、PrimitiveSceneProxy、VertexFactory、Shader 实例化数据打包；改错会导致大面积特效缺失或 GPU crash。

开发自检

  • 相同 ParticleID 的多实例合并为一次 DrawCall（RHI drawcall 计数）
  • 与 Nanite/GPUScene 剔除共存不丢粒子
  • 编辑器 ComputeParticleID 结果稳定

结论置信度：medium — 是否改用 Niagara+自定义数据接口在 GPU 侧合并以规避重做 UE5 实例化，是重大方案取舍，需专项评估。

标签说明

颜色规则：覆盖度=红绿灯 · 工程化=蓝色系 · 侵入=紫色系 · 处置=中性灰。
分级方式：工程化/侵入用「实心 → 底色 → 描边 → 虚线」四级形态表示程度递进（实心最强）。

UE5 覆盖度

UE5 已覆盖UE5.8 原生等价，可直接删除
部分覆盖UE5 有同类能力，只迁差异部分
未覆盖UE5 没有该能力，需迁移或补丁
待确认证据不足，迁移前需人工确认

落地位置（工程化可行性）

可工程化放项目/插件/配置即可，不动引擎
需接入点引擎留少量 Hook，逻辑在工程侧
引擎内实现必须改引擎核心
—处置=删除的行不适用（已删除/不迁移）

引擎改动方式

L0 无需改引擎纯工程/插件/配置即可（对应「可工程化」）
L0 引擎内补丁需改引擎源码，但不必新增扩展点（对应「引擎内实现」）
L1 仅加接入点引擎只需暴露 Delegate / Interface / CVar 等扩展点
L2 结构性改动枚举 slot / 新 Pass / schema 字段
L3 深度侵入核心结构/生命周期/序列化，慎入

迁移处置

删除UE5 已覆盖，直接删
常开补丁确认的 bugfix，作为 fork 常开补丁
配置化改为 CVar / ini / DeviceProfile / 命令行
插件化迁到项目模块 / 编辑器插件
接入点引擎只留 Hook，逻辑在插件
移植代码保留，适配后移植
保留引擎深度绑定，暂留并登记 Feature Card
