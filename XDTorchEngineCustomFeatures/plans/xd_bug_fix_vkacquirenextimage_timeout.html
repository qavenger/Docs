处理 vkAcquireNextImageKHR 返回 VK_TIMEOUT（旧驱动兼容，UE4-2139）

3. 代码级实现（开发用）

独立 Agent 审核并修正修正 1 处　提出问题 2 条

审核意见：after 可用：UE5 EStatus::NotReady=-3 确在 VulkanSwapChain.h:50（grep+read），变量名 SyncIndex/PrevSyncIndex 与 UE5 一致；仅锚点行号需订正。

改接口/改名 改动方式：UE5 AcquireImageIndex/EStatus 结构仍在，只需加一个 VK_TIMEOUT 分支并复用已有 NotReady，另在 viewport 的 status 分发处加对应分支

代码脉络：UE4 在 FVulkanSwapChain::AcquireImageIndex 把 VK_TIMEOUT 映射为 EStatus::TimeOut（Runtime/VulkanRHI/Private/VulkanSwapChain.cpp:774-779，枚举 VulkanSwapChain.h:37 TimeOut=-3），由 DoCheckedSwapChainJob/DoAcquireImageIndex 触发重建交换链并补齐 BackBuffer 视图（VulkanViewport.cpp:244-268,295-305,795-810）。UE5 只处理 OUT_OF_DATE/SURFACE_LOST/NOT_READY（VulkanSwapChain.cpp:748-772），VK_TIMEOUT 会落到 :773 的 checkf 崩溃。

步骤 1Runtime/VulkanRHI/Private/VulkanSwapChain.cppUE4 VulkanSwapChain.cpp:774-779（TimeOut=-3，VulkanSwapChain.h:37）→ UE5 VulkanSwapChain.cpp:738 SURFACE_LOST 之后、:744 VK_NOT_READY 分支附近插入 VK_TIMEOUT 分支；未处理会落到 :764 的 checkf

在 SURFACE_LOST 分支后加 VK_TIMEOUT，复用 UE5 已有 EStatus::NotReady(-3)

if (Result == VK_ERROR_SURFACE_LOST_KHR)

⚠ UE5 重建前多了 CanCreateSwapchainOnDemand() 门槛（:201）与 IsWindowValid 早退（:206），失败会走 dummy backbuffer 而非 Fatal，比 UE4 安全

风险评估

原代码风险：重试+重建交换链会在超时驱动上反复 Flush/Recreate，可能造成抖动或卡顿；该分支仅在异常驱动触发。

移植风险：改动共享 EStatus::NotReady 语义可能影响 UE5 原本对 VK_NOT_READY 的处理路径；影响 Android/PC Vulkan 窗口。

开发自检

  • 打开 TESTING 开关强制 VK_TIMEOUT 时不崩且有 Warning
  • 窗口重建后渲染恢复（无 check(AcquiredImageIndex>=0) 失败）

结论置信度：medium — 复用 NotReady 是否会让 UE5 既有的 VK_NOT_READY 语义混淆，需 Vulkan 同学定夺是否新增 TimeOut=-4
