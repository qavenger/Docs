修改草案 · XD_OPT_LLM_TRACK_GLBOAL_PEAK_MEMORY

LLM 支持记录全局内存分配峰值

部分覆盖 移植 引擎内实现 仅加接入点 工作量 M风险 中开发者 Wang Xiao Bo主要模块 Core

一句话结论：优先用 LLM.TrackPeaks，全局峰值另补补丁

背景：跟踪并输出峰值内存，用于定位内存尖峰与 OOM。

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：UE4 只有 per-tag FramePeakSize，无跨 tag 全局峰值：XD 加 FPeakMemoryCallbcak/SetPeakMemoryCallback（h:469-484），在 UpdateStatsPerFrame 汇总各 tag FramePeakSize 得 PeakMemorySize/PeakAssetMemorySize，按 CVarLLMPeakMemoryWriteInterval 回调（cpp:3231-3260）；UnrealEngine 用 StaticPeakMemoryCallback 存进 UEngine（UnrealEngine.cpp:659-667/:2347-2348、:17097 SetPeakMemory、Engine.h:3229-3235），并经 CoreDelegates.h:241-242 OnPeakMemoryCallback 广播。UE5 无 SetPeakMemoryCallback、无 UEngine PeakMemory 字段与 delegate，只有 per-tag PeakSize（LLM.cpp:5525/6580）。

上游引入：XD 自研：UBT XDBuildOptConfiguration.cs:185(=1)。UE5 origin/ue5-main 未提供。

上游历史（是否修过）：上游未提供也未计划：UE5 LLM 仅保留 LLM.TrackPeaks 与 per-tag PeakSize，无回调式全局峰值。属 XD 需求，宏不能删。

为什么可以断定不是「故意为之」3 条依据
  • 非上游缺陷：Epic 从未承诺跨 tag 汇总回调，per-tag peak 是其设计边界
  • XD 有意把所有接入点集中在同一宏（LLM 头/实现 + UEngine + CoreDelegates）
  • 仅在 !UE_BUILD_SHIPPING 编译（UnrealEngine.cpp:659/2347/17097），是刻意的调试构建限定

调用方契约：消费链 StaticPeakMemoryCallback→GEngine->SetPeakMemory（:660-664）→UEngine::Tick 中 dirty 时 log 并 FCoreDelegates 广播（:17109-17121）；分析/崩溃上报脚本依赖 OnPeakMemoryCallback（CoreDelegates.h:242）。

内层真实语义：失败=FnPeakMemoryCallbcak 为空则不回调（cpp:3250）；正常=按周期回调后清零 PeakMemorySize/PeakAssetMemorySize，且 FramePeakSize 已在上一步清零不可重放（cpp:3236-3241/3253-3258）。

代码库惯例：UE5 统计回调惯例用 delegate（FOnXxx）而非裸函数指针；UE5 UEngine 无同类字段，XD 需自行补。

为何长期未被发现：只在非 Shipping+开 CVar 时生效，峰值不影响逻辑；回调在 LLM 统计线程同步执行，重活会阻塞统计（risk 已注明）。

XD 侧的做法与意图：UE4:471/483 定义回调、:3231 汇总、UnrealEngine 注册，意图=把全局内存峰值推给游戏层做上报/展示。

回调内再调 TickInternal 会与 UpdateLock 死锁；只搬 LLM 侧漏改 Engine.h 会编译失败（risk 已提示）。

迁移方案（按根因定）

方案A：整套移植（LLM 头/实现 + UEngine 字段/SetPeakMemory + CoreDelegates），建议改用 DECLARE_DELEGATE_TwoParams(FOnLLMPeakMemory) 的 UE5 风格；方案B：若仅需日志，用 LLM.TrackPeaks+外部读 per-tag peak 替代，删除跨 tag 回调。

根因级自检用例

  • 开 CVar 且非 Shipping：周期内回调携带正确全局峰值与资产峰值
  • 回调后峰值清零，下一周期不累加旧值
  • Shipping 构建不编译该路径
  • UEngine::Tick 收到 dirty 后广播 OnPeakMemoryCallback 一次

3. 代码级实现（开发用）

独立 Agent 审核并修正修正 2 处　提出问题 2 条

审核意见：abandon/refactor 判断依据成立：UE4 LLM 锚点全部核实（LowLevelMemTracker.h:469/:481、.cpp:3231、UnrealEngine.cpp:660/2347/17097、Engine.h:3229、CoreDelegates.h:239），UE5 已按 UE::LLM/ESizeParams 重写（LLM.cpp:957 LLM.TrackPeaks、:7097 Publish 无 bTrackPeaks），但必须补一个 Engine.h 的显式 step，否则 after 不可用。

完全重构 改动方式：UE5 LLM 已按 UE::LLM/FTagData 重写且 Publish 无 bTrackPeaks，回调须落到新结构。

代码脉络：在 LLM 加全局峰值回调：LowLevelMemTracker.h:469-484 定义 FPeakMemoryCallbcak(:471)/SetPeakMemoryCallback(:483)；LowLevelMemTracker.cpp:3231 在 UpdateStatsPerFrame 汇总各 tag FramePeakSize 得 PeakMemorySize 并按周期回调；UnrealEngine.cpp:660 定义 StaticPeakMemoryCallback、:2347-2348 注册、:17097-17122 UEngine::SetPeakMemory，Engine.h:3227-3235 承载字段，CoreDelegates.h:239-242 有 FOnPeakMemoryCallback。

步骤 2Runtime/Engine/Private/UnrealEngine.cppUnrealEngine.cpp:2668 RecordHMDAnalytics()

LLM(FLowLevelMemTracker::Get().SetPeakMemoryCallback(StaticPeakMemoryCallback));
// 需先在 UE5 Engine.h 增加（UE5 现无 SetPeakMemory/PeakMemory 字段）：
//   void SetPeakMemory(int64 InPeakMemorySize, int64 InAssetPeakMemorySize);
//   int64 PeakMemorySize = 0; int64 AssetPeakMemorySize = 0; bool bPeakMemoryDirty = true;
LLM(FLowLevelMemTracker::Get().SetPeakMemoryCallback(FOnLLMPeakMemory::CreateLambda([](int64 A, int64 B){ if (GEngine) { GEngine->SetPeakMemory(A, B); } })));

⚠ UE5 UEngine 无 SetPeakMemory/PeakMemory 字段，需自行补(Engine.h)

风险评估

原代码风险：回调在 LLM 统计线程同步执行，回调内做重活会阻塞统计；FramePeakSize 清零后不可重放。

移植风险：需同时改 LLM 核心与 UEngine，漏改 Engine.h 会编译失败；周期 CVar 语义可能与 LLM.TrackPeaks 重叠。

开发自检

  • LLM.TrackPeaks=1 时能看到峰值回调
  • 峰值与 DumpLLM 的 PeakMB 一致

结论置信度：medium — UE5 是否已有全局(非 per-tag)峰值等价实现待人工确认。
