修复部分机型（如 Mate20）Vulkan Tile Fast Clear 造成的花屏

待确认 移植 引擎内实现 仅加接入点 工作量 M风险 中开发者 Liu Xing Kui主要模块 Engine

一句话结论：UE5.8 Vulkan 路径重写，需真机复现后再决定去留

0. 根因溯源（这个宏为什么存在）

平台/工具链绕行

结论：XD 在 PLATFORM_ANDROID_VULKAN 下绕过 GetClearBinding()==ClearColor 的 fast clear 分支，统一走 DontLoad_Store + DrawClearQuad 实写清除。

上游引入：fast clear 分支上游引入 f20a48849ea3(2017-07-21,Ben Marsh,4.17 merge)；UE5 Canvas.cpp:1074-1078 仍为 Clear_Store。

上游历史（是否修过）：UE5 5.8.2 Canvas.cpp:1074-1089 仍是 Clear_Store(fast)/DontLoad_Store+DrawClearQuad 两分支，git grep 无 PLATFORM_ANDROID_VULKAN/TileFastClear 规避，上游从未加此 workaround。

为什么可以断定不是「故意为之」3 条依据
  • 硬件/驱动相关花屏，Epic 无对应 Android 设备矩阵覆盖
  • fast clear 是性能优化，若有意保持就不需要 DontLoad 分支
  • UE4 端规避是 XD 为自家机型添加，Epic 仓库无此现象记录

调用方契约：FCanvas::Clear 被所有 Slate/UI 清屏调用（UE5 Canvas.cpp:1062）；返回 void，副作用是 RenderTarget 内容。

内层真实语义：fast clear 分支只 BeginRenderPass(Clear_Store)+EndRenderPass(:1075-1078) 依赖 GPU tile clear；DrawClearQuad 分支真实绘制 quad(:1082-1087)。二者结果应相同，仅路径不同。

代码库惯例：同函数 else 分支已是 DontLoad_Store+DrawClearQuad，规避只是选另一既有分支。

为何长期未被发现：只在特定 tile GPU + 特定 UI 绘制序列下花屏，PC/D3D 与部分 Android 不复现。

XD 侧的做法与意图：UE4 Canvas.cpp:1063-1072 的 #if 分支（DontLoad_Store+DrawClearQuad）。

删 fast clear 分支是全局性能回归（所有平台多一个 quad）；只在 Android Vulkan 改而不给 CVar 会失去线上开关；改 FCanvas 热路径会影响合批/带宽与 iOS，不能顺手全平台禁用。

迁移方案（按根因定）

保留 UE5 双分支，仅在 PLATFORM_ANDROID_VULKAN 内加低开销 CVar 门控（默认关闭 fast clear），或按 GPU family 在 RHI 层判定，不动其它平台。

根因级自检用例

  • Android Vulkan 上 FCanvas::Clear 后 UI 无花屏
  • 非 Android 仍走 fast clear，性能不回退
  • Clear 与 GetClearBinding 一致的 RT 结果正确
  • CVar 开关切换后同一帧序列结果一致

3. 代码级实现（开发用）

独立 Agent 审核并修正修正 1 处　提出问题 2 条　其中高风险 1 条

审核意见：thread/step0 与 UE5 Canvas.cpp 真实代码吻合（Transition+FRHITransitionInfo 替换 TransitionRenderPassTargets、SliceIndex 已在 :1066 捕获），但 step1 的 CVar 位置与分支体是错的，需按文件作用域 CVar + 具体分支重写。

改接口/改名 改动方式：逻辑分支可照搬，但 UE5 用 RHICmdList.Transition(FRHITransitionInfo) 与带 SliceIndex 的 FRHIRenderPassInfo 取代 TransitionRenderPassTargets。

代码脉络：宏在 Canvas.cpp:1063 FCanvas::Clear 内，PLATFORM_ANDROID_VULKAN 时绕开 ERenderTargetActions::Clear_Store 的 tile fast clear，改为 DontLoad_Store 渲染通道 + DrawClearQuad 实写，规避 Mate20 类设备的 tile fast clear 花屏。UE5 Canvas.cpp:1062 FCanvas::Clear 仍保留 Clear_Store 快清与 DontLoad_Store+DrawClearQuad(:1086) 两分支，且无 Android 规避。

风险评估

原代码风险：tile 型 GPU 上 fast clear 与后续 partial load 组合在部分驱动产生花屏，属于硬件/驱动相关缺陷。

移植风险：改动 FCanvas::Clear 热路径，所有 Android Vulkan 工程 UI 清屏都会多画一个 quad，需关注 UI 合批/带宽回退及 iOS 是否也应加开关。

开发自检

  • Mate20（或同代 Mali/G71）真机跑 UI 清屏与 PostProcess 场景对比花屏
  • 统计 r.XD.AllowTileFastClear=0/1 两档的 UI Pass GPU 时间差

结论置信度：medium — UE5.8 是否已在 Vulkan 侧对 fast clear 做 vendor 规避（grep FastClear 无命中），以及 Mate20 机型是否仍在支持列表，需真机复现后定去留。
