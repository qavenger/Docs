修改草案 · XD_BUG_FIX_SHADER_PRINT_CREATE_STRUCTURE_BUFFER_CRASH

修复 PC FD3D11DynamicRHI::RHICreateStructuredBuffer 崩溃

部分覆盖 移植 引擎内实现 结构性改动 工作量 S风险 中开发者 Ran Qing Sen主要模块 Renderer

一句话结论：Shipping/Test 下禁用 ShaderPrint 避免创建结构化缓冲崩溃

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：Shader Print（着色器打印调试功能）在正式包中无意义，且其结构缓冲的创建/初始化曾引发崩溃。XD 的规避方式是两条：①让 `ShaderPrint::IsEnabled()` 在 Shipping/Test 构建下直接返回 false（编译期短路）；②把 `View.ShaderPrintValueBuffer.Initialize` 从 `IsEnabled` 之前挪到之后（避免在未启用时仍初始化缓冲）。UE5 中 `IsEnabled()` 仍无守卫（`ShaderPrint.cpp:301-304` 直接 `return GEnabled != 0;`），但原崩溃路径涉及的 `ShaderPrintValueBuffer` 成员**已不存在**（结构被重写，新增了 `IsEnabled(FShaderPrintData const&)`、`IsDefaultViewEnabled()` 等接口），因此只有"Shipping 守卫"这部分还有落点。

上游引入：XD 的崩溃规避（XDFixBugFeatures:89 定义宏）；生效链：UE4 `Runtime/Renderer/Private/ShaderPrint.cpp:175` 让 `ShaderPrint::IsEnabled()` 在 Shipping/Test 直接 `return false`，并把 `View.ShaderPrintValueBuffer.Initialize` 从 `IsEnabled` 之前挪到之后（同文件 :323/:337）。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2 `Source/Runtime/Renderer/Private/ShaderPrint.cpp`：:301-304 `bool IsEnabled() { return GEnabled != 0; }`（**无 Shipping/Test 守卫**）；:306-309 `void SetEnabled(bool)`；:311 `bool IsValid(FShaderPrintData const&)`；:317-320 `bool IsEnabled(FShaderPrintData const& InShaderPrintData) { return InShaderPrintData.Setup.bEnabled; }`；:327-330 `bool IsDefaultViewEnabled()`；:704/:719 使用点（`bEnabled = IsEnabled();` / `bEnabled = IsEnabled() && IsSupported(...) && View.Family->EngineShowFlags.ShaderPrint;`）；且全文件**无** `ShaderPrintValueBuffer`（该成员在 UE5 已不存在，XD 的重排无落点）。

为什么可以断定不是「故意为之」2 条依据
  • 上游未在 `IsEnabled()` 上加 Shipping 守卫，属其默认行为（正式包也可通过 CVar 启用 shader print）；其结构重写（新增按 FShaderPrintData 判定的接口）替代了原来的 ValueBuffer 初始化路径。
  • XD 的守卫是项目侧取舍（正式包彻底禁用调试功能，减少崩溃面与开销），不是上游缺陷。

调用方契约：（若加守卫）Shipping 包必须完全不创建/初始化 shader print 相关资源；编辑器与调试构建中该功能保持可用。

内层真实语义：UE4（XD）：编译期守卫 + 初始化顺序调整。UE5（上游）：`IsEnabled()` 无守卫；启用状态可按 `FShaderPrintData` 判定（`IsEnabled(FShaderPrintData const&)`、`IsDefaultViewEnabled()`）。

代码库惯例：上游把"是否启用"交给 CVar/数据结构判定（不做编译期裁剪），项目侧若要彻底关闭调试功能需自行加守卫。

为何长期未被发现：属"崩溃规避/正式包精简"：不迁移不会立刻崩（除非命中该路径），只在特定流程（如触发生成结构缓冲）暴露；而 UE5 结构重写后，原崩溃点消失，容易误判为"上游已修、补丁可删"。

XD 侧的做法与意图：XD 的目标是让正式包不因 shader print 相关缓冲创建而崩溃，并省掉其开销。

⚠ 四点注意：①**不要照搬"挪动 ShaderPrintValueBuffer 初始化"**——该成员在 UE5 已不存在（结构重写），照搬无法编译；②加 Shipping 守卫**前先确认 UE5 是否仍存在对应崩溃路径**（新结构的分配/初始化时机已变，可能已无该问题）；③守卫会**永久禁用 Shipping 下的 shader print**（含线上排查手段），需团队确认；④UE5 新增了按数据判定的接口（`IsEnabled(FShaderPrintData const&)`、`IsDefaultViewEnabled()`）——若只是想"默认不启用打印"，优先用上游开关而非编译期守卫。

迁移方案（按根因定）

按 port-as-is（部分）处理：①在 UE5 的 `ShaderPrint::IsEnabled()`（ShaderPrint.cpp:301）加 Shipping/Test 编译期 `return false` 守卫（若团队确认要彻底禁用）；②放弃原 ValueBuffer 重排（成员已不存在），改用 UE5 的新接口/开关控制启用状态；③若在 UE5 上仍能复现崩溃，记录最小复现并反馈上游。

根因级自检用例

  • Shipping 包不创建/初始化 shader print 相关资源（无崩溃、无额外内存开销）
  • 编辑器与 Debug 构建中 shader print 功能正常（调试能力未被误伤）
  • （若曾复现崩溃）修复后该复现步骤不再崩溃
  • 性能无明显变化（守卫仅影响启停判定）

可反馈上游：无需反馈（上游结构已重写）；若仍可复现崩溃则附最小复现反馈。

风险评估

原代码风险：仅编译期短路，无内存风险；副作用是 Shipping 下引擎无法用 ShaderPrint 调试。

移植风险：若 CVar r.ShaderPrint 仍被 Shipping 配置强开，会走 UE5 的 bEnabled 路径重建 buffer，崩溃复现；影响所有 ShaderPrint/GPUScene 等使用 ShaderPrintData 的 pass。

开发自检

  • Shipping/Test 下 r.ShaderPrint=1 仍不创建 structured buffer（不崩）
  • Development 下 ShaderPrint 调试功能完好

结论置信度：high
