修改草案 · XD_FIX_BUG_HTTP_THREAD_INVALID_SLEEP_TIME

修复 FHttpThread 睡眠时间出现负值导致异常

UE5 已覆盖 删除 引擎内实现 引擎内补丁 工作量 S风险 低开发者 Ran Qing Sen主要模块 Online

一句话结论：UE5 已修复。

0. 根因溯源（这个宏为什么存在）

上游已自行修复（该宏可直接删除）

结论：Windows 优化构建下 FHttpThread 主循环算出的循环耗时（InnerLoopEnd - InnerLoopBegin）可能为负数：时间戳取自 FWindowsPlatformTime::Seconds()，但在开启优化时会拿到缺少常数 16777216.0 的值，导致差值异常；负耗时会让后续 sleep 计算失真（忙等/异常休眠）。UE4 时代 XD 用 FMath::Max(0.0, ...) 把内外层耗时都钳到非负；UE5 上游用等价逻辑修好了同一处，XD 的宏因此没有增量。

上游引入：上游时钟读取问题（Windows + 优化 + FWindowsPlatformTime::Seconds 的 16777216.0 偏移），XD 在 UE4.26 fork 的 HttpThread.cpp:126/:139 增加 FMath::Max(0.0, ...) 钳制。

上游历史（是否修过）：已核实 UE5.8.2 Source/Runtime/Online/HTTP/Private/HttpThread.cpp:601-610：`double InnerLoopTime = InnerLoopEnd - InnerLoopBegin;` 之后逐行是 `// On Windows when optimization enabled, seems InnerLoopEnd can get a value without adding the const value 16777216.0 from FWindowsPlatformTime::Seoncds(), it could be caused by https://github.com/openssl/openssl/issues/21522`，接着 `if (InnerLoopTime < 0.0) { InnerLoopTime = 0.0; }` —— 与 XD 的钳制等价，且注释把根因写得更清楚（指向 OpenSSL issue 21522，并说明与 PRAGMA_DISABLE_OPTIMIZATION 配套使用）。

为什么可以断定不是「故意为之」2 条依据
  • 上游不但做了钳制，还专门写了 4 行注释解释"为什么会拿到负值"（时钟基准缺失 16777216.0）并引用 OpenSSL issue —— 明确是有意修复。
  • XD 与上游的修法效果一致（都把负耗时归零），保留宏只会造成同一位置的双份处理。

调用方契约：FHttpThread 的主循环依赖循环耗时计算 sleep 时长（HttpThreadActiveFrameTimeInSeconds 等）；耗时为负会让 sleep 时长失真，表现为 HTTP 线程异常占用 CPU 或响应变慢。

内层真实语义：UE4（XD 宏）：InnerLoopTime / OuterLoopTime 均用 FMath::Max(0.0, diff) 钳到非负。UE5（上游）：仅在 Active 循环（:601-610）对 InnerLoopTime 钳制，Idle 段（:621-623）未钳制，但外层仍以 FMath::Max(IdleFrameTime - OuterLoopTime, ...) 兜底，实际不会出现负 sleep。

代码库惯例：这类"平台计时偶发异常值"的上游惯例是就地钳制 + 注释引用外部 issue（本例正是如此）。

为何长期未被发现：只在 Windows + 优化构建 + 特定时序下偶发；表现为 HTTP 线程行为异常而非崩溃，容易被当成网络问题。

XD 侧的做法与意图：XD 的目标是避免负耗时导致 sleep 计算失真（保持 HTTP 线程节奏稳定）。

⚠ 迁移时不要叠加：若既保留 XD 的 FMath::Max 又保留 UE5 的 if (<0) 钳制，逻辑虽等价但会产生"双份修复"，后续上游更新时容易误判；直接删除宏、只保留上游实现。另注意 UE5 只钳了 Inner，Outer 依赖外层 Max 兜底，不要误以为漏改而再补一处。

迁移方案（按根因定）

删除 XD_FIX_BUG_HTTP_THREAD_INVALID_SLEEP_TIME 宏与其钳制分支，采用 UE5 上游实现；删除后确认 HttpThread 的 Active/Idle 两条路径 sleep 时长均为非负。

根因级自检用例

  • Windows 优化构建（Shipping/Test）下抓 HTTP 线程 CPU 占用：不应出现忙等
  • 连续大量 HTTP 请求时线程节拍稳定（可用 STAT_HTTPThread_ActiveSleep 观察）
  • 空闲态（Idle 段）sleep 时长非负、无异常唤醒
  • 与 XDLivePatch/登录等 HTTP 链路联合回归

可反馈上游：无需反馈（上游已修，且注释已引用 OpenSSL issue 21522）。

⚠ 负面睡眠参数已消除。

开发自检

  • Windows 长时间跑 HTTP 不出现异常休眠

结论置信度：high
