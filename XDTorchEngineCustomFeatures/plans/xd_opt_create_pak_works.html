修改草案 · XD_OPT_CREATE_PAK_WORKS

打包 Pak 过程的性能优化（减少重复工作与拷贝）

部分覆盖 移植 引擎内实现 结构性改动 工作量 M风险 中开发者 Ran Qing Sen主要模块 Core

一句话结论：先逐项比对 XD 的 SKIP_*/USE_CUSTOM_COMPRESS_STRATERGY 与 UE5 现状，只保留 UE5 仍缺的项

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：XD 在 PakFileUtilities 里用一组宏开关改造打包流程：跳过冗余日志（`SKIP_LOG_COMPRESS_PAK_INFO`/`SKIP_LOG_VERIFY_INDEX_MATCH_INFO`）、打印耗时（`LOG_*_COST_TIME`）、自定义压缩策略（`USE_CUSTOM_COMPRESS_STRATERGY`）、以及"提前启动下一文件压缩"（`AHEAD_LAUNCH`）等。UE5 的 pak 写入器已重写：引入 `FMemoryCompressor` 与 `BeginCompressFileToWorkingBuffer`/`EndCompressFileToWorkingBuffer` 的**两段式异步压缩**（Begin 发起、End 收尾），XD 的"提前启动压缩"意图已被上游的异步流程覆盖；其余日志/策略开关在上游没有对应物。

上游引入：XD 的打包流程优化（PakFileUtilities.cpp:44-70 由宏展开出一组开关：SKIP_LOG_COMPRESS_PAK_INFO / SKIP_LOG_VERIFY_INDEX_MATCH_INFO / LOG_*_COST_TIME / USE_CUSTOM_COMPRESS_STRATERGY / AHEAD_LAUNCH 等）。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2 `Source/Developer/PakFileUtilities/Private/PakFileUtilities.cpp`：:142 `class FMemoryCompressor;`（前置声明）、:145-152 "AsyncTask for FMemoryCompressor"、:212 `class FMemoryCompressor`、:216 构造函数（收纳 `UncompressedBuffer/UncompressedSize/Format/CompressionBlockSize/FGraphEventRef InCompressionFinishedEvent`）、:233 析构、:682 `TUniquePtr<FMemoryCompressor> BeginCompressFileToWorkingBuffer(const FPakInputPair& InFile, FName CompressionMethod, const int32 CompressionBlockSize, FGraphEventRef EndCompressionBarrier);`、:683 `bool EndCompressFileToWorkingBuffer(const FPakInputPair& InFile, FName CompressionMethod, const int32 CompressionBlockSize, FMemoryCompressor& MemoryCompressor);` —— 即上游已用 Begin/End 两段式 + 图事件栅栏实现了异步/流水线式压缩；同时 `AHEAD_LAUNCH`/`USE_CUSTOM_COMPRESS_STRATERGY` 等 XD 开关在 UE5 **无命中**。（注：本条目检索时对 XD 大目录的检索曾超时，XD 侧开关列表取自既有勘察记录。）

为什么可以断定不是「故意为之」2 条依据
  • 上游把压缩流程重构为显式 begin/end 两段（用 FGraphEventRef 做完成栅栏），属有意的异步化设计，覆盖了"提前启动压缩"的性能诉求。
  • XD 的日志抑制/耗时统计是项目调试偏好，压缩策略是项目选择，两者上游不会内置（属项目侧需求）。

调用方契约：打包产物必须与不启用定制时完全一致（索引/校验通过），且压缩流程的内存峰值与耗时可控（异步不能叠加导致 OOM）。

内层真实语义：UE4（XD）：用宏组合控制日志、耗时统计、压缩策略与"提前启动"的流水线。UE5（上游）：`FMemoryCompressor` + `BeginCompressFileToWorkingBuffer`/`EndCompressFileToWorkingBuffer` 两段式异步压缩（由 FGraphEventRef 编排依赖）。

代码库惯例：上游把压缩并发编排交给任务/事件栅栏（Begin/End 成对），项目侧定制应在该结构内插入（例如在 Begin 队列上加策略），而不是另起"提前启动"。

为何长期未被发现：属"打包工具性能/可观测性"：不影响运行时；只在打包耗时与日志噪声上体现；而写入器已被重写，按旧结构迁移会与新的异步流程冲突。

XD 侧的做法与意图：XD 的目标是加快打包（压缩流水线化）并减少打包日志噪声/量化耗时。

⚠ 三点注意：①**不要再实现"提前启动压缩"**——UE5 的 Begin/End 两段式已经异步化了压缩，手工提前启动会与上游的缓冲/事件编排竞争（可能造成内存峰值翻倍或产物校验失败）；②若要自定义压缩策略，应通过参数（`CompressionMethod`/`CompressionBlockSize`）与上游的压缩路径实现，绕过 `FMemoryCompressor` 的缓冲管理容易导致内存峰值失控；③日志/耗时统计属于调试手段，注意带开关且不要在正式打包流程中常开（有额外 IO/格式化开销）。

迁移方案（按根因定）

按 refactor 处理：①"提前启动压缩"部分不迁移（上游已有异步两段式）；②若仍需日志抑制/耗时统计，在 UE5 的 `FPakWriterContext`（新写入器上下文）与日志点重新落点，并用 CVar/开关控制；③若需自定义压缩策略，改走上游的压缩方法与块大小参数（或在 `FMemoryCompressor` 路径内扩展），并验证产物校验与内存峰值。

根因级自检用例

  • 打包产物与默认流程一致（pak 校验/挂载正常）
  • 打包耗时与 UE4 启用该优化时相当或更好（流水线收益可量化）
  • 内存峰值正常（异步压缩不叠加导致 OOM）
  • 自定义压缩策略（如启用）产物可正常加载、大小符合预期
  • 日志/耗时统计开关在正式打包流程中默认关闭

可反馈上游：可向上游提议：为 pak 写入提供"压缩并发度/流水线深度"的公开参数（便于大工程调优）。

风险评估

原代码风险：把同时在飞的压缩任务上限从 128 拉到 1024，压缩 buffer 常驻内存大幅上升，属以内存换 IO 的激进取舍。

移植风险：旧补丁无法整段搬运（FCompressedFileBuffer 已拆成 Begin/End 两段 + FMemoryCompressor），重贴常量后需回归 pak 内容一致性与内存峰值。

开发自检

  • 打补丁前后生成的 pak 条目/字节一致（至少同平台可比）
  • cook 峰值内存不超限
  • 重复运行不再出现重复压缩日志（SKIP_LOG_* 生效）

结论置信度：medium — USE_CUSTOM_COMPRESS_STRATERGY 在 UE5 的对应挂点（UE5 已改写预取循环，需人工确认保留哪些）
