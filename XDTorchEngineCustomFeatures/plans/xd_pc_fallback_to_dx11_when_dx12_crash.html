DX12 崩溃时回退 DX11（完整版，带崩溃上报）

部分覆盖 接入点 需接入点 仅加接入点 工作量 M风险 中开发者 Wang Xiao Bo主要模块 Core

一句话结论：复用 UE5 PreferredRHI 机制，崩溃判定放项目侧

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：目的：D3D12 崩溃后下次启动强制 D3D11（反向亦然）。链路：UE_LOG Fatal 命中 LogD3D12RHI/LogD3D11RHI 时置 GIsD3D12RHICrashed（LogMacros.h:209-210，声明 :16-19，定义 CoreGlobals.cpp:389-390）→ WindowsErrorOutputDevice.cpp:92-101 HandleD3D12RHICrashed → WindowsPlatformMisc.cpp:2921-2923 写 GConfig D3DRHIPreference/bCrashedOnD3D12=true → 下次 WindowsDynamicRHI.cpp:13-28 读出，:198-210 置 bForceD3D11=true 强制 D3D11。

上游引入：XD fork（P4，无 git 可考古）。cs:68-69 注释 fallback to dx11 when dx12 crash, fallback to dx12 when dx11 crash, add by PengTianCheng。

上游历史（是否修过）：已核实 UE5 5.8.2 无任何 crash-based RHI 回退：`rg bCrashedOnD3D12 Source/Runtime/RHI Source/Runtime/Core` 0 命中；WindowsDynamicRHI.cpp 只有显式配置回退（:137 IsPreferredRHIAllowed、:143 GConfig RHI/bUsePreferredRHI、:962 ChoosePreferredRHI、:972 读 D3DRHIPreference/PreferredRHI、:826-828 ES31 时写 dx11）；UE5 DynamicRHI.cpp 只在 denylist 弹窗（:82/:235）。上游从未提供等价能力且非缺陷，故不适用「是否修过」。

为什么可以断定不是「故意为之」4 条依据
  • UE5 有意把 RHI 选择交给配置/用户（r.ForcePreferredRHISupport，WindowsDynamicRHI.cpp:130-133），不做崩溃记忆，是产品决策而非遗漏
  • UE5 有 GIsGPUCrashed（WindowsErrorOutputDevice.cpp:25/77、CoreGlobals.cpp:473、ToggleGDebugPUCrashedFlag:492）但只做崩溃标记不落盘，说明上游刻意不持久化
  • XD 用 Fatal 与日志类名字符串强匹配，是自建 hack（LogMacros.h:207/212 有 XD_..._Begin/End 标记）
  • Vulkan/D3D12 崩溃原因多样，自动降级 API 会在 UE5 上放大兼容面，Epic 明确不作为

调用方契约：WindowsDynamicRHI.cpp:198-210 依据上次崩溃置 bForceD3D11 决定下次引擎 API；WindowsPlatformMisc.cpp:2921-2933 是唯一写入点（含 LogD3D12Failed/LogD3D11Failed）；WindowsErrorOutputDevice.cpp:92 是唯一触发点，由 LogMacros.h:209 置位。

内层真实语义：失败路径=凡 LogD3D12RHI 的 Fatal（含非崩溃的致命错误）都置位；正常/空路径=非 Fatal 或其它 Category 不改标志；宏关闭时 UE_LOG 宏体完全无该分支。bCrashedOnD3D12 写 true 后只能靠 LogD3D12Failed(false)（:2933）或人工改 ini 复位。

代码库惯例：UE5 惯例：用 GConfig+WindowsDynamicRHI.cpp 的显式 PreferredRHI（:972-1020），日志用 UE_LOGF（LogMacros.h:199），崩溃上报走 FGenericCrashContext::SetEngineData（UE5 D3D11Util.cpp:133/140）。

为何长期未被发现：只在 Shipping 生效（IsLastCrashCausedbyD3D12 对 Editor/非 Shipping 直接 return false，WindowsDynamicRHI.cpp:16-18），且必须真崩一次 D3D12；日志表象只是普通 Fatal。

XD 侧的做法与意图：用最省事的日志类名匹配 + ini 落盘实现自动降级，避免玩家卡在崩溃循环。

照抄到 UE5 有 4 个坑：①UE5 UE_LOG 体是 static_assert(decltype(Format))+UE_PRIVATE_LOG(...)（LogMacros.h:278-282），#if 不能出现在 #define 体内，必须整宏守卫；②UE5 Fatal 判定已内建 `if constexpr ((Verbosity & VerbosityMask) == Fatal)`（LogMacros.h:341，配合 :101-111 UE_LOG_EXPAND_IS_FATAL），正解是包 BasicFatalLog，而非在 UE_LOG 前插运行时字符串比较（会给全项目每个日志站点加一次 FName 比较）；③UE5 Fatal 分支后有 CA_ASSUME(false)，置位代码放错分支会被 DCE；④XD 在崩溃路径里 GConfig->Flush(false) 有 IO 与重入风险。

迁移方案（按根因定）

方案A（推荐）：不动 Core，项目侧订阅 UE5 原生 RHIGetPanicDelegate()（RHI.h:597）/FCoreDelegates GPU 崩溃回调，回调里写 D3DRHIPreference/PreferredRHI=dx11 + Flush，下次启动由 ChoosePreferredRHI(WindowsDynamicRHI.cpp:962) 生效；方案B：改在 UE5 内建 Fatal 钩子（UE_PRIVATE_LOG/BasicFatalLog，LogMacros.h:337-350）而非改 UE_LOG 宏体。取舍：A 零引擎侵入、不重编全项目日志站点；B 覆盖所有 Fatal 但侵入 Core 并影响所有日志装配。

根因级自检用例

  • 宏=0 时全项目 UE_LOG 站点与 UE5 原版 diff 为 0
  • 注入一次 LogD3D12RHI Fatal 后 GameUserSettings.ini 出现 [D3DRHIPreference] PreferredRHI=dx11
  • 保留该 ini 再启动，日志出现 Found D3DRHIPreference PreferredRHI: dx11 且走 D3D11
  • Editor 下（:16-18 return false）不触发回退
  • 只读磁盘/Fatal 在 RenderThread 时无死锁、无重入崩溃

可反馈上游：UE5 5.8.2 未提供 D3D12 DeviceRemoved 后持久化降级 RHI 的框架钩子（DynamicRHI.cpp/WindowsDynamicRHI.cpp 均无处理点，只有 RHIGetPanicDelegate 与显式 PreferredRHI）。最小复现：Win10+DX12 触发一次 device removed，重启后仍走 DX12。

2. 修改步骤（接入点）

  1. 引擎侧只加接入点
    需要的接入点：[D3DRHIPreference]PreferredRHI、FWindowsPlatformMisc 崩溃记录（机制：Config）。引擎改动应最小、稳定、无业务语义。
  2. 插件侧实现完整逻辑
    崩溃时把 PreferredRHI=dx11 写入 GameUserSettings 并重启（项目模块）
  3. 无插件时的行为
    未绑定接入点时应回退到官方默认行为（引擎侧不能假设插件存在）。

风险评估

原代码风险：用日志类别字符串匹配判断崩溃，任何 LogD3D12RHI 的 Fatal（含非崩溃的致命错误）都会触发回退；崩溃路径里调用 GConfig->Flush(false)，有 IO 与重入风险。

移植风险：改的是 Core 的 UE_LOG 宏与错误输出设备，全项目日志站点都会重编译；GIsD3D12RHICrashed 若声明与引用守卫宏不一致会链接失败。

开发自检

  • DX12 下人为 UE_LOG(LogD3D12RHI, Fatal) 后重启，日志与 GameUserSettings.ini 显示 PreferredRHI=dx11、实际起 DX11
  • 编辑器/GIsEditor 路径下不发生改写（IsPreferredRHIAllowed 在编辑器返回 true，但崩溃检测应先短路）
  • shipping 包全流程日志正常，无因 UE_LOG 宏改动导致的编译或格式化断链

结论置信度：medium — UE4 该宏在引擎里只有注释引用，是否真有项目侧 #if 引用需确认；NO_LOGGING 构建是否在 XD 发行链路中需人工确认。
