修改草案 · XD_BUG_FIX_GENERATE_DETERMINED_STATIC_MESH_TEXCOORDS

修复静态网格导入时 UV 通道不足导致 DDC 不确定

未覆盖 常开补丁 需接入点 结构性改动 工作量 S风险 中开发者 Lu Xun主要模块 Developer/MeshBuilder

一句话结论：影响 DDC/ Cook 确定性，建议作为常开补丁并加资产校验双保险

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：宏改 MeshDescriptionHelper 光图 UV 分支(UE5 名 SetupRenderMeshDescription :34)：Dst 大于 NumIndices 时告警并把 Dst 收敛为 NumIndices、去掉无条件回写，避免错误值被静默写进资产、使首建与后建结果不同。

上游引入：回写逻辑 aa84947dfc01e(2017-12-28 Alexis Matte, Runtime/MeshBuilder/.../MeshDescriptionHelper.cpp:110-121)；SetNumIndices 改 SetNumChannels 见 4884bf9d9a0c(2020-05-28 Richard TalbotWatkin)；越界值来源 MeshUtilities.cpp:704 SrcModel.BuildSettings.DstLightmapIndex = LightMapIndex。XD config:437-439 说明动机。

上游历史（是否修过）：5.8.2 仍上游行为：:111 条件、:114-117 MAX_MESH_TEXTURE_COORDS_MD 钳制、:120 SetNumChannels、:121 回写(blame 仍为 aa84947dfc01e)。该字段确实进 DDC key：StaticMesh.cpp:3652 Ar << BuildSettings.DstLightmapIndex，在 SerializeBuildSettingsForDDC(:3633, 2022-05-31 cf0b27b54720e)内、:3842 调用。

为什么可以断定不是「故意为之」3 条依据
  • ①:121 把光图 UV 放第一个新增通道是有意策略(注释 :119 与 SetNumChannels 一致)
  • ②但 BuildSettings 经非 const 引用指向 StaticMesh->GetSourceModel(0).BuildSettings(:293/:1432)，回写会改资产进而改 DDC key，XD 的确定性诉求成立
  • ③上游对次要 LOD 用局部拷贝(:935 LODBuildSettings)，说明本不想改持久数据，属疏漏

调用方契约：FStaticMeshBuilder 以 &BuildSettings 传入(StaticMeshBuilder.cpp:293/305、1432)；影响 StaticMesh 的 DDC key 与 :125 CreateLightMapUVLayout 的目标通道。

内层真实语义：正常(Dst==NumIndices)两版等价；越界(Dst>NumIndices)XD 先告警收敛再走 MAX 钳制；若 Dst>=MAX，上游先钳到 MAX-1 再 SetNumChannels(MAX)，XD 因先改 Dst 而 SetNumChannels(NumIndices+1)，极端情况通道数不同需回归。

代码库惯例：构建期不改持久资产数据见 StaticMeshBuilder.cpp:935 的局部拷贝；日志用 UE_LOG(LogStaticMesh,...) 带资产名。

为何长期未被发现：只有导入了大于源模型 UV 通道数的光图通道的网格才命中；表象是 DDC 反复失效、两次 cook 不同，日志毫无提示。

XD 侧的做法与意图：fork :79-96 在 >=NumIndices 内再判 >，告警 XD DET Cooking: Bad Destination Lightmap Index ... indetermined cooking results ... resave it to fix up，并去掉 :96-98 的无条件回写。

只删 :121 不补条件修正会留隐患：:125 CreateLightMapUVLayout 会用未收敛的 Dst，偏离把光图 UV 放第一个新通道的上游语义；照抄 UE4 的 SetNumIndices 编译失败(UE5 为 SetNumChannels)。

迁移方案（按根因定）

api-adapt：保留 UE5 :111-121 结构，在 :111 块内插 if (Dst>NumIndices){UE_LOG(Warning);Dst=NumIndices;}，:121 留删皆等价。根因级更优是让调用方传局部副本(如 :935)，彻底不污染资产与 DDC key。

根因级自检用例

  • 正常网格(Dst=NumIndices=1)构建后 BuildSettings 不变且通道与迁移前一致
  • 越界网格(Dst=3,NumIndices=1)出告警、构建成功、结果逐字节一致
  • Dst==NumIndices 时不打日志
  • Dst>=MAX_MESH_TEXTURE_COORDS_MD 时通道不超上限
  • 同网格连续两次构建 DDC key 相同

3. 代码级实现（开发用）

独立 Agent 审核通过

审核意见：全部核实：UE4 MeshDescriptionHelper.cpp:79-98（含 96-98 `#if !XD` 回写）与 UE5:111-121（120 SetNumChannels、121 无条件回写）一致，before/after 与 anchor 准确，SetNumIndices→SetNumChannels 的 api-adapt 判定合理。

改接口/改名 改动方式：函数与逻辑同在，仅 VertexInstanceUVs 接口改名。

代码脉络：宏在 FMeshDescriptionHelper::SetupMeshBuildSettings 生效：MeshDescriptionHelper.cpp:79-98 当 DstLightmapIndex≥NumIndices 时告警并回写，且 96-98 在宏关闭时仍回写 DstLightmapIndex=NumIndices，避免 BuildSettings 写进 DDC 后不确定。

步骤 1Developer/MeshBuilder/Private/MeshDescriptionHelper.cppMeshDescriptionHelper.cpp:111-121（UE5）

删除 121 行无条件回写，改为越界修正+告警

#if !XD_BUG_FIX_GENERATE_DETERMINED_STATIC_MESH_TEXCOORDS
    BuildSettings->DstLightmapIndex = NumIndices;
#endif
// UE5 在 120 行之后
if (BuildSettings->DstLightmapIndex > NumIndices) {
    UE_LOG(LogStaticMesh, Warning, TEXT("XD DET Cooking: Bad DstLightmapIndex[%d] > UV channels[%d], corrected!"), BuildSettings->DstLightmapIndex, NumIndices);
    BuildSettings->DstLightmapIndex = NumIndices;
}

⚠ UE5 121 行仍是回写，仅在 >NumIndices 时修正，勿误改合法值。

步骤 2Developer/MeshBuilder/Private/MeshDescriptionHelper.cppMeshDescriptionHelper.cpp:120（UE5）

API 改名对照

VertexInstanceUVs.SetNumIndices(BuildSettings->DstLightmapIndex + 1);
VertexInstanceUVs.SetNumChannels(BuildSettings->DstLightmapIndex + 1);

⚠ SetNumIndices→SetNumChannels，参数语义一致。

风险评估

原代码风险：BuildSettings 写入 DDC，回写导致 DDC/Cook 不确定。

移植风险：影响所有静态网格导入/构建，改错会破坏 lightmap UV 生成。

开发自检

  • 导入 UV 不足的网格时 DstLightmapIndex 不再被改写，DDC 稳定
  • 连续两次 Cook 该网格结果一致

结论置信度：high
