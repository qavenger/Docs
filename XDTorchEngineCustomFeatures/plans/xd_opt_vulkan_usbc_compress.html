0. 根因溯源（这个宏为什么存在）

上游缺失能力（UE5 可能已补）

结论：XD 为 Vulkan 加了"原生着色器归档/序列化复用"以降低着色器内存与编译开销：在 VulkanShaderFormat 中引入 AnsiAllocator/ShaderCodeArchive、开启 SAVE_MEMORY/REUSE_SERIALIZED_SHADER，并声明 `SupportsShaderArchives()`。UE5 的情况很明确：**上游把该能力做成了正式扩展点**——`IShaderFormat::SupportsShaderArchives()`（基类默认 false）与 `IShaderFormat::CreateShaderArchive(...)`，并由着色器库在写出时按 `bShouldWriteInNativeFormat && Archive->SupportsShaderArchives()` 判定；但**目前只有 Metal 实现**（MetalShaderFormat.cpp:185/:190），Vulkan 没有实现。因此迁移方式不是照搬 UE4 的 Vulkan 内部改动，而是在 UE5 的 VulkanShaderFormat 上实现这两个官方虚函数。

上游引入：XD 的 Vulkan 着色器内存/编译优化（XDBuildOptConfiguration.cs:334 定义；UE4 版：VulkanShaderFormat.cpp:13-17 引入 AnsiAllocator/ShaderCodeArchive 并开 SAVE_MEMORY/REUSE_SERIALIZED_SHADER，:157 声明 SupportsShaderArchives…）。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2：①`Source/Developer/TargetPlatform/Public/Interfaces/IShaderFormat.h:64` `virtual bool SupportsShaderArchives() const { return false; }`；:77 `virtual bool CreateShaderArchive(FString const& LibraryName, ...)`；②全局实现只有 Metal：`Source/Developer/Apple/MetalShaderFormat/Private/MetalShaderFormat.cpp:185` `virtual bool SupportsShaderArchives() const override`、:190 `virtual bool CreateShaderArchive(...)`；③**VulkanShaderFormat 中无 SupportsShaderArchives/CreateShaderArchive**（该目录仅有 VulkanBackend.cpp/.h、VulkanShaderCompiler.cpp、VulkanShaderFormat.cpp 等）；④UE5 的 native-format 写出链路存在：`Runtime/RenderCore/Private/ShaderLibrary/EditorShaderCodeArchive.cpp:103/:105` `SupportsShaderArchives()`（注释说明用于判定是否支持原生着色器库）、:1264 `if (bOK && bNativeFormat && OutLibrary.SupportsShaderArchives())`，以及 `ShaderCodeLibrary.cpp:1789/:1871` `bool bShouldWriteInNativeFormat = bOk && bNativeFormat && ...->SupportsShaderArchives();`（含 PerChunkArchive 分块路径）。另：UE5 全仓无 `RHISupportsNativeShaderArchives`、无 `SAVE_MEMORY/REUSE_SERIALIZED_SHADER`（该组 UE4 内部符号已不存在）。

为什么可以断定不是「故意为之」2 条依据
  • 上游把"原生着色器归档"定义成 IShaderFormat 的虚函数扩展点，并让着色器库按能力判定写出格式，属正式的接口设计。
  • Vulkan 未实现该接口是上游覆盖缺口（Metal 已实现），而非刻意移除能力；XD 的需求因此仍可通过实现官方接口达成。

调用方契约：原生着色器归档必须满足：写出端（cook/打包）与读取端（运行时加载）格式严格对应；与着色器库的库/分块/patch 体系协同；失败时能正确上报（见 patch 缺陷条目）。

内层真实语义：UE4（XD）：在 VulkanShaderFormat 内部直接引入归档与序列化复用逻辑。UE5（上游）：能力被抽象为 IShaderFormat 虚函数（SupportsShaderArchives/CreateShaderArchive），由 FEditorShaderCodeArchive / FShaderCodeLibrary 在写出时按能力选择 native format（含分块与引用资产归档路径）。

代码库惯例：上游要求平台着色器格式通过 IShaderFormat 接口声明能力与实现归档写出（Metal 是范例），项目不应在格式内部另起机制。

为何长期未被发现：属"着色器内存/编译开销"优化：不迁移不会崩，只在 Vulkan（Android/PC）上体现为着色器内存占用与首次加载/复用差异；而 UE4 的内部符号在 UE5 已消失，容易误判为"能力被移除"（实际是接口化并只缺 Vulkan 实现）。

XD 侧的做法与意图：XD 的目标是降低 Vulkan 平台的着色器内存占用与序列化/编译开销（复用已编译着色器、减少内存驻留）。

⚠ 四点注意：①**不要再照搬 UE4 的 VulkanShaderFormat 内部改动**——UE5 的 Vulkan 后端已重写（VulkanBackend.cpp/VulkanShaderCompiler.cpp），旧实现无法编译；正确做法是实现 `SupportsShaderArchives()` 与 `CreateShaderArchive()` 两个虚函数；②实现后要确认与**分块/引用资产归档**路径的配合（ShaderCodeLibrary.cpp:1789 与 :1871 分别是引用资产归档与 PerChunkArchive 两条路径），避免只覆盖其中一条；③**与 patch 库缺陷条目联动**：原生归档写出失败的上报依赖库返回值，若同时使用 XDLivePatch，必须按 `xd_bug_fix_patch_shader_lib_additional_error_bool_flag` 的结论（保持 bError 语义、勿裸改 `&=`）处理，否则失败会被吞掉；④先量化收益：UE5 的通用着色器库已含压缩/分块，Vulkan native archive 的增量收益需实测（避免重复优化）。

迁移方案（按根因定）

按 upstream-missing → 改用上游扩展点：在项目的 VulkanShaderFormat 中实现 `SupportsShaderArchives()`（返回 true，按平台/配置可选）与 `CreateShaderArchive(...)`（把着色器代码写为 Vulkan 原生归档），使上游着色器库的 native-format 路径生效；删除 UE4 式的 VulkanShaderFormat 内部改动；实施前先做收益评估（着色器内存、加载耗时），并与 patch 库的 bError 修复一并验证。

根因级自检用例

  • Vulkan（Android/PC）着色器内存占用下降（与 UE4 启用该优化时对比可量化）
  • 着色器加载/复用正常（首次启动、切换场景、热更后均无缺失或崩溃）
  • 分块与引用资产两条写出路径均正常（无单路径覆盖导致的丢失）
  • patch 流程（XDLivePatch）在原生归档开启时行为正确，失败能被正确上报（联动 bError 修复）
  • 与其它平台（Metal/D3D）行为一致，无回归

可反馈上游：可向上游提议：为 Vulkan 补齐 IShaderFormat 的原生归档实现（Metal 已有，Vulkan 缺失）。

风险评估

原代码风险：自建原生库格式含大块 AnsiAllocator 前置预留（RawShaderCodes.Reserve(1ll<<32)）与自定义头，格式升版即与旧包/热更不兼容；切线逻辑在 cook 期内存峰值很高。

移植风险：改动贯通 ShaderFormat→ShaderCodeArchive→RHI→IoStore/UnrealPak（UE5 ShaderCodeLibrary.cpp:1789-1793 PackageNativeShaderLibrary），失败会导致启动即无 shader 或 pak 校验失败，属最高风险项。

开发自检

  • Vulkan 平台打包后 .uspi/.usp 生成，启动时 RHICreateShaderLibrary 成功且无 shader miss
  • 增量包/热更与 IoStore 勾选组合下均可加载，UnrealPak 无校验错误

结论置信度：low — UE5 是否仍支持 Vulkan 侧 PackageNativeShaderLibrary 的完整链路、以及 .uspi 后缀/切库长度参数在 UE5 的等价 CVar 名，需人工确认后再动手。
