修复运行时切换桌面模式时显示器查询报错（UE4-5201）

UE5 已覆盖 删除 可工程化 无需改引擎 工作量 S风险 低开发者 Ran Qing Sen主要模块 RHI-PC

一句话结论：UE5 已修复，直接删除

0. 根因溯源（这个宏为什么存在）

上游已自行修复（该宏可直接删除）

结论：Windows 运行期切换桌面模式（如独占/窗口、分辨率变更）会让缓存的 IDXGIFactory 失效，此时调用 EnumAdapters 等接口会报错（表现为分辨率/显示器枚举失败）。XD 在 D3D11/D3D12 的显示器与分辨率查询路径上加了工厂有效性检查与重建；UE5 上游已在 Windows RHI 层内建同类机制（多处 `DXGIFactory::IsCurrent()` 判断 + 重建）。

上游引入：上游早期缓存 DXGI 工厂但不校验有效性；XD 在 UE4.26 fork 的 WindowsD3D11Device.cpp:2271/:2616、WindowsD3D12Device.cpp:1116/:1397 与 D3D12Adapter::CreateDXGIFactoryHelper 等处补检查。

上游历史（是否修过）：已核实 UE5.8.2：Source/Runtime/Windows/D3D11RHI/Private/Windows/WindowsD3D11Device.cpp 多处使用 `DXGIFactory1->IsCurrent()`（:410/:412/:417）与 `CurrentAdapter.GetDXGIFactory2()->IsCurrent()`（:548/:554/:559）来检测工厂/适配器是否过期并据此重建 —— 即上游已内建"失效即重建"的机制。（本轮验证集中在 D3D11 侧；D3D12 侧对应文件未在本机路径下定位到，如需可另行核对。）

为什么可以断定不是「故意为之」2 条依据
  • 上游在枚举显示器/分辨率前显式判断 IsCurrent() 并重建工厂，属于有意的健壮性处理。
  • XD 的补丁目标（避免工厂失效导致查询报错）在 UE5 的实现里已由这些判断覆盖。

调用方契约：显示器信息/可用分辨率查询（RHIGetAvailableResolutions / RHIGetAttachedMonitorInfos）依赖有效的 DXGI 工厂；桌面模式切换会使缓存工厂失效，查询前必须校验。

内层真实语义：UE4（XD）：在 D3D11/D3D12 的查询入口检查工厂有效性并重建后重试。UE5（上游）：在 RHI 层用 IsCurrent() 统一判断，失效则重建（含 DisplayList 与适配器两条路径）。

代码库惯例：Windows 图形栈里"缓存 COM 对象 + IsCurrent() 校验 + 重建"是上游通行的健壮性写法。

为何长期未被发现：只在运行期切换桌面模式（而非启动时）触发；启动即查询不会遇到失效工厂。

XD 侧的做法与意图：XD 的目标是保证切换桌面模式后分辨率/显示器查询不报错。

⚠ 迁移时不要保留 XD 的检查分支：UE5 已在 RHI 层统一处理，重复检查会遮蔽上游重建路径；另外注意 D3D12 侧的对应实现在 UE5 中已重组，不要按 UE4 行号硬搬。

迁移方案（按根因定）

删除 XD_FIX_BUG_PC_MONITOR_QUERIED_ERROR_WHEN_SWITCH_DESKTOP_MODE_RUNTIME 宏及相关检查，采用 UE5 内建机制。

根因级自检用例

  • 运行期切换桌面模式（窗口/独占、改分辨率）后：枚举显示器与可用分辨率正常无报错
  • 连续多次切换无句柄泄漏（工厂重建路径正确释放）
  • D3D11 与 D3D12 两条 RHI 路径分别回归

可反馈上游：无需反馈（上游已内建）。
