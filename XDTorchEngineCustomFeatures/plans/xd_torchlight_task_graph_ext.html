TaskGraph 扩展（新增任务类型/调度接口，供项目并行任务使用）

部分覆盖 接入点 需接入点 仅加接入点 工作量 M风险 中开发者 Cheng Zhi Jun主要模块 Engine

一句话结论：注意与 UE5 新增的 AsyncTick/PreEndOfFrameSync 机制对齐，避免重复生命周期

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：宏=1 时给 ParallelFor 加 CurrentThreadWorkToDoAfterHelping 形参，让主线程在帮助完并行任务后执行回调作为回调作为 GTEndWork，World 保存单一待同步组件，在并行 end-of-frame 更新结束后调用其 OnEndOfFrameSync。

上游引入：P4 副本无 git 历史；UBT 开关 XDBuildProjectFeaturesConfiguration.cs:26(注释 Submitted by Gong Bailiang，=1)；实现 Core/Public/Async/ParallelFor.h:273-343 与 :395-429、Engine/Classes/Components/ActorComponent.h:537 与 :821、Private/Components/ActorComponent.cpp:1782-1786、Engine/Classes/Engine/World.h:1386-1389、Private/LevelTick.cpp:935-943/994-1000/1171-1197

上游历史（是否修过）：UE5 5.8.2 Core/Public/Async/ParallelFor.h 已无 AfterHelping(rg 零命中)→ 原方案在 UE5 不可行；UE5 提供的是“并行之前”的钩子：OnPreEndOfFrameSync(ActorComponent.h:762，默认实现 ActorComponent.cpp:2808-2811 return false)与 RequiresPreEndOfFrameSync(:1160)、World.h:1647 ComponentsThatNeedPreEndOfFrameSync(TSet 而非单指针)，注册 LevelTick.cpp:1017-1019、执行 :1169-1195(:1183 调用)；该套机制上游 4.26(4.26.0-release ActorComponent.h:529/810、World.h:1357)就已存在，说明 XD 的 Ext 是与上游并存、语义不同的“之后”。

为什么可以断定不是「故意为之」3 条依据
  • 4.26 上游已有 OnPreEndOfFrameSync，XD 仍另起 OnEndOfFrameSync，说明要的是并行更新完成之后的时机，不是上游缺陷
  • XD 在 World.h:1388 用裸单指针并在 LevelTick.cpp:997 check(nullptr==ComponentsThatNeedEndOfFrameSync)：上游表达通用机制会用 TSet+标记(LevelTick.cpp:1169-1196)，不会用会崩的全局单指针
  • UBT 注释专门写 Submitted by Gong Bailiang，属个人提交的扩展

调用方契约：XD 游戏侧 UUserTickComponent 重载 RequiresEndOfFrameSync()/OnEndOfFrameSync()(UE_game/.../UserTick/UserTickComponent.h:17/19、.cpp:13/18-24)，在回调里驱动 UUserTickMgr::TickOnEndOfFrameSync(UserTickMgr.cpp:112)；引擎执行点 LevelTick.cpp:1175-1179，注册点 :995-999

内层真实语义：RequiresEndOfFrameSync 默认 false(ActorComponent.cpp:1782)→不上报，GTEndWork 变 no-op；有请求时并行体返回后调用一次并清空；组件在回调前析构靠 LevelTick.cpp:935-943 清悬挂指针；无返回值，失败只能表现为漏调或 check 崩

代码库惯例：上游对“需要同步的任务”统一用 Set + MarkedFor* 标记 + DrainSyncSet(LevelTick.cpp:1169-1196)，且把钩子放在并行开始之前，避免 WaitUntilTaskCompletes 与并行体竞争

为何长期未被发现：默认无人重载则整条路径等价 UE4 原版；只在开启异步 EOF 更新且 UUserTick 有挂载时才暴露，表现为等待/延迟一帧等时序问题无日志；check 仅在多组件同时请求时崩，且 Release 下可能被裁掉

XD 侧的做法与意图：让 XD 自己的 UserTick 在“本帧所有并行 end-of-frame 更新(骨骼推送等)都结束”后再 tick 一次，避免读到半成品数据

①照抄 AfterHelping 到 UE5：该形参已被删除，强行改回 Core 会扩大分叉；且 UE5 的 EndOfFrameUpdate 已有 Tasks 异步路径(LevelTick.cpp:1246-1280 bLaunchAsyncTask 分支)，漏掉该路径会时有时无；②改用 OnPreEndOfFrameSync 会让时序反过来(并行之前)却不报错；③把 check 换成集合时若不定义顺序，多组件回调先后不确定；④把回调放到 delete Context(LevelTick.cpp:1310) 之后会读到已释放内存。

迁移方案（按根因定）

①按 UE5 结构重接“之后”语义：ActorComponent 加 virtual void OnEndOfFrameSync(){} 与 RequiresEndOfFrameSync()(默认 false)，World 用 TSet/TWeakObjectPtr 保存待同步组件(替掉会崩的单指针)，在 LevelTick.cpp:1303 并行体返回后、:1310 delete Context 之前顺序调用；异步 bLaunchAsyncTask 分支需等价的等待点或强制走同步路径；②若业务其实只需“提前同步”，直接改用 UE5 原生 OnPreEndOfFrameSync，零引擎改动(最推荐)；③不要移植 ParallelFor 的 AfterHelping。

根因级自检用例

  • 无组件重载时与 UE5 原生逐帧一致、无额外等待
  • 单组件重载：回调恰好在并行 EOF 更新完成后一次
  • 两个组件同时请求：不崩且都收到回调(验证替换 check 的必要性)
  • 回调前组件被销毁：无悬挂指针
  • 同步与异步(bLaunchAsyncTask / CVarAllowAsyncRenderThreadUpdatesDuringGamethreadUpdates>0)两条路径语义一致
  • 待更新组件数为 0 时行为与原生一致

2. 修改步骤（接入点）

  1. 引擎侧只加接入点
    需要的接入点：ParallelForWithPreWork 增加 AfterHelping 回调、UWorld/ActorComponent 增加 EndOfFrameSync 广播与注册接口（机制：Delegate）。引擎改动应最小、稳定、无业务语义。
  2. 插件侧实现完整逻辑
    项目任务调度/并行逻辑放项目模块；引擎侧只需在 ParallelFor 与 LevelTick 留出回调扩展点
  3. 无插件时的行为
    未绑定接入点时应回退到官方默认行为（引擎侧不能假设插件存在）。

风险评估

原代码风险：AfterHelping 回调依赖 TaskGraph 帮助线程时序；用 check(nullptr==ComponentsThatNeedEndOfFrameSync) 强制唯一，多组件同时要求会直接崩。

移植风险：与 UE5 原生 AsyncTick/OnPreEndOfFrameSync 生命周期重叠，可能重复等待或漏同步，影响布料/骨骼等异步组件。

开发自检

  • 并行 end-of-frame 更新后 OnEndOfFrameSync 恰好一次
  • 多组件同时 RequireEndOfFrameSync 不触发 check
  • -nothreading 单线程路径也调用

结论置信度：medium — 是否必须“并行之后”同步（UE5 原生 OnPreEndOfFrameSync 在并行之前执行）需与项目并行任务使用方确认。
