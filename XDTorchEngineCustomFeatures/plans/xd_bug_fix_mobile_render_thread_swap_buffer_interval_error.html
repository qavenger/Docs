修复移动端帧率超过 60 时渲染线程可能多等一个 VSync 的问题

3. 代码级实现（开发用）

独立 Agent 审核并修正修正 3 处　提出问题 3 条　其中高风险 1 条

审核意见：UE4 宏位置与 CVar 均已核实（AndroidOpenGLFramePacer.cpp:300-321；XDConsoleVariables.inc:29-35 正是该 CVar 块），但把“照搬”误判成“已被 UE5 取代”，是本草案最实质的结论性错误。

简单移植 改动方式：UE5.8 该文件与 UE4 未打补丁版逐字相同（:390 硬编码 /60、:392-399 Under/Over 取近在 UE4:325-332 已存在），XD 针对 >60Hz 的 {60,90,120} 重算补丁未被 UE5 吸收，60Hz 假设导致的双倍等待仍存在，应照搬移植。

代码脉络：UE4 AndroidOpenGLFramePacer.cpp:300-321 当 DriverRefreshRate>60 且 xd.r.fixbug.mobileRTSwapBufferIntervalError=1(XDConsoleVariables.inc:29-35)时，把 SyncIntervalNanos 从 (30+1e9*SyncInterval)/60 重按 {60,90,120} 最近刷新率计算，避免 60Hz 假设引入多等一个 vsync。UE5 :390-401 改为用 DriverRefreshNanos 求 Under/OverDriverInterval 并取最近者，不再硬编码 60Hz。

风险评估

原代码风险：硬编码 60Hz 在高刷产生约 2 倍间隔，CVar 默认 1 全局生效无白名单。

移植风险：若真机仍见 >60Hz 双倍等待，需在 UE5 Under/Over 逻辑上补丁，RHI 帧节奏回归成本高。

开发自检

  • 90/120Hz 真机 60fps 时帧间距≈16ms 无 2 倍等待
  • GLES 与 Vulkan 路径一致
  • 无 30ms 抖动

结论置信度：medium — 无法从源码断定 UE5.8 在非整除刷新率下完全等价，需真机 trace 定论。
