PC 支持获取/切换硬件光标

UE5 已覆盖 删除 可工程化 无需改引擎 工作量 S风险 低开发者 Wang Xiao Bo主要模块 Engine

一句话结论：UE5 已覆盖，直接删除

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：宏只做一件事：在 protected 段内打开一行 GetHardwareCursors()，返回 protected 成员 TMap<EMouseCursor::Type, void*> HardwareCursors 的 const 引用（UE4 GameViewportClient.h:948 成员、:644 getter）；Engine 内无其它引用，消费者在项目侧子类（读平台硬件光标句柄）。

上游引入：XD fork（P4，无 git）。XDBuildMiscConfiguration.cs:450-451 注释 allow get hardware cursors on pc。

上游历史（是否修过）：已核实 UE5 5.8.2：GameViewportClient.h:1042 仍有 TMap<EMouseCursor::Type, void*> HardwareCursors（类型未改名），:645 SetHardwareCursor、GameViewportClient.cpp:4777 实现、:4811 HardwareCursors.Add、:4815 PlatformCursor->SetTypeShape 均在；但 GetHardwareCursors 0 命中。protected 段结构同 UE4（UE5 :687 UpdateViewportClientWindowDPIScale 位于 protected 段内）。上游无需修，也不存在「修过」。

为什么可以断定不是「故意为之」4 条依据
  • 纯新增 inline 访问器，未改上游任何逻辑，不可能被上游修掉
  • UE5 至今保留 HardwareCursors 成员（:1042），说明上游不反对该类暴露，只是没有需求
  • Engine 内 0 处消费，说明它服务的是项目侧扩展而非引擎功能
  • 原样一行、无行为副作用，宏开/关只影响项目侧能否编译

调用方契约：项目侧 UGameViewportClient 子类读 ViewportClient->GetHardwareCursors().Find(EMouseCursor::Default) 取平台句柄；Engine 内无调用方；宏关闭时项目代码无法编译。

内层真实语义：正常路径=getter 直接返回成员 const 引用（零拷贝）；失败路径=无返回码，找不到键返回 nullptr；空操作=宏关闭时 getter 整体不存在，签名与语义不变。句柄生命周期由 GameViewportClient 的 HardwareCursors 清空逻辑管理（UE4 GameViewportClient.cpp:875/928 遍历清理）。

代码库惯例：UE5 对「protected 成员给子类」的惯例是加 inline 访问器（如 LightSceneProxy.h:238 AffectsTranslucentLighting()）；同文件也有 HardwareCursorCache（UE5 :1039，TMap<FName,void*>）。

为何长期未被发现：无行为差异，宏关闭只影响项目编译，CI 若只编引擎不会发现。

XD 侧的做法与意图：让项目侧子类复用引擎已创建的硬件光标句柄（而不是重复创建或走 SWindow），减少闪烁/句柄泄漏。

看似无害但有害的修法：①把 getter 从 protected 挪到 public 段会扩大接口面，UE5 后续若再改 HardwareCursors 类型会伤到更多调用方；②改成按值返回 TMap 会每次拷贝整张表；③子类若在 Destroy 后仍缓存 Map 内 void* 会悬垂（原风险已注明）；④UE 未来若重命名/合并 HardwareCursorCache 结构，过度封装（比如自己加一层包装类型）会变成迁移负担，应保持一行薄封装。

迁移方案（按根因定）

方案A（推荐，port-as-is）：在 UE5 GameViewportClient.h:687（UpdateViewportClientWindowDPIScale）之后、protected 段内原样补回 getter，并与 XDBuildMiscConfiguration 的开关同步；方案B：若项目只需一个光标句柄，在项目侧自建缓存——不可行，因为唯一的创建点是 UGameViewportClient::SetHardwareCursor 内部（:4777/4811），除非项目改从 SWindow/平台层取句柄。取舍：A 一行、零风险。

根因级自检用例

  • 宏=1：UE5 编译通过且项目子类可调用 GetHardwareCursors()
  • 宏=0：引擎与项目（含 #if 分支）均编译通过
  • 返回 const 引用、Find 缺失返回 nullptr 不崩
  • GameViewportClient 析构后不再访问该 Map（悬垂回归）
  • SetHardwareCursor(:4777) 成功后能查到对应句柄（创建/读取顺序一致）

3. 代码级实现（开发用）

独立 Agent 审核通过提出问题 1 条

审核意见：全部关键点核实：UE4 GameViewportClient.h:643-645/#endif、protected 段 :639、成员 HardwareCursors:948；UE5 :687 UpdateViewportClientWindowDPIScale、:689 public:、成员 :1042、SetHardwareCursor:645。after 类型签名一致。

简单移植 改动方式：UE5 仍保留同名成员 HardwareCursors（GameViewportClient.h:1042）与 SetHardwareCursor（:645），函数体一致，只需补回同一行 getter。

代码脉络：宏只做一件事：在 GameViewportClient.h:643 打开 protected 段内的一行 getter（:644），把 protected 成员 HardwareCursors（UE4:948）暴露给子类；Engine 内无其它引用。

风险评估

⚠ 与早期迁移处置结论存在分歧：早期结论=UE5 已覆盖，代码级分析=仍需移植/改接口（需复核覆盖是否完整）。早期结论=删除，代码级分析=简单移植；建议以代码级分析为准并回写评估矩阵。

原代码风险：getter 暴露的是平台相关的 void* 句柄，子类若手动 Destroy 或跨 RHI 复用会造成悬垂指针；本身无内存/线程问题。

移植风险：改动面仅一个头文件的行内函数，风险极低；但若 UE5 后续版本 HardwareCursors 类型改名会编译失败。

开发自检

  • 编译 Editor 与 Shipping 两种配置（宏=1 与 =0 各一次），确认 protected 访问权限无回归
  • 运行时通过 getter 取到 Default 光标句柄非空，且与 SetHardwareCursor 设置的形状一致

结论置信度：high
