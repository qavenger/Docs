修改草案 · XD_BUG_FIX_TEXTURE_MIP_LOAD_CRASH_WHEN_NO_UBULK

修复没有 ubulk 时纹理 Mip 加载崩溃（TORCHLIGHT-251687）

待确认 移植 引擎内实现 结构性改动 工作量 S风险 中开发者 Yu Hang主要模块 Engine

一句话结论：先确认 UE5 BulkData 是否仍会在缺 ubulk 时崩；诊断逻辑可改名为项目 CVar（如 r.BulkData.Trace）

0. 根因溯源（这个宏为什么存在）

平台/工具链绕行

结论：Cooked 纹理某些高 mip 无可用 ubulk(热更差异包/裁剪产物)。UE4 UTexture2D::StreamIn 请求该 mip 时 FTexture2DStreamIn_IO 的 CreateStreamingRequest 返回 null，上游 4.26 无判空直接解引用→崩溃。XD 在 Texture2D.cpp:89-176 新增 XDShouldClampTextureStreamInMipCount/XDDoesTextureMipSourceExist/XDClampTextureStreamInMipCount，把 NewMipCount 夹到真实有源的最高 mip(:1304-1316)；并加 r.XD.TextureMipTrace 诊断日志。

上游引入：XD 自研，见 XDBuildFixBugConfiguration.cs:685(TORCHLIGHT-251687，默认1)。D:/Torchlight 为非 git 快照，无 XD 提交号可查。上游 CreateStreamingRequest API 引入 d2f9a61b0681(2019-11-25)/f1c85990a7e8(2020-01-24)，均无判空。

上游历史（是否修过）：上游 4.26.0-release 的 FTexture2DStreamIn_IO 同样无 null 判空。UE5 65c11839b64b(2024-07-19 per larsson) 改用 FBulkDataBatchRequest，Texture2DStreamIn_IO.cpp:100-107 遇 BulkDataSize<=0 置 bFailedOnIOError 并取消，不再崩但该 mip 永久流不进。5.8.2/ue5-main 无任何 clamp。

为什么可以断定不是「故意为之」4 条依据
  • 上游在 Texture2DStreamIn_IO.cpp:52 赋值 IORequests[MipIndex] 后 :72/:85 直接解引用，任何失败(文件缺失/off+size 越界)都崩，非故意
  • UE5 主动把 BulkDataSize<=0 规整为 bFailedOnIOError，说明该路径本应容错
  • 同目录 FTexture2DMipDataProvider_IO 对 GetBulkDataSize<=0 直接 continue 跳过，缺数据=跳过是既有惯例
  • 夹取只在找不到真实源时降 mip，完整 ubulk 的正常纹理不受影响

调用方契约：UTexture2D::StreamIn 的 RequestedMipCount 决定 CachedSRRState.StreamIn 的实际驻留 mip(UE5 Texture2D.cpp:1980)；失败路径返回 !PendingUpdate->IsCancelled()(UE4 :1453)。诊断 CVar r.XD.TextureMipTrace 被 CreateResource(:756) 与 IO 路径读取。

内层真实语义：正常：XDDoesTextureMipSourceExist 从 CurrentAssetFirstLODIdx-1 逐级下探，遇不存在即 break，返回可用范围(Texture2D.cpp:159-176)。空操作：Texture/PlatformData 为空直接返回 DesiredMipCount(:161)。失败：无源时回退 CurrentAssetFirstLODIdx，绝不升高。

代码库惯例：UE5 以 bFailedOnIOError/continue 容错缺 bulk(Texture2DStreamIn_IO.cpp:100-107、Texture2DMipDataProvider_IO)，不硬崩。

为何长期未被发现：仅当 cooked 后高 mip 无 ubulk 的少数纹理(热更差异包)触发；PC 编辑器走 DDC 不夹取，故只在特定 mobile 热更包偶发。

XD 侧的做法与意图：config:685；目的：热更/打包缺 ubulk 时不崩，并把可见画质停在真实存在的最高 mip。

看似正确：既然 UE5 不再崩(bFailedOnIOError)就删 clamp——但 XD 热更内容仍缺 ubulk，删除后这些纹理每次流送都失败并停在低 mip，画质回归。反面：无条件夹到 1 mip 会让所有 cooked 纹理锁低清。错误判据：用 GetBulkDataSize()>0 判有源会把 inline(包内)数据误判为可流送。

迁移方案（按根因定）

UE5 保留 clamp：插到 Texture2D.cpp:1978 之后、:1980 之前(勿放 :1968 VT 早退前)。方案A：完整移植三 helper(保留 cooked-only 与 bIsCookedForEditor 判断)并复用 UE5 的 bFailedOnIOError 语义；方案B：先只留 A 并观察 r.XD.TextureMipTrace。UE5 已无 IORequests 判空对应物，不要强搬。

根因级自检用例

  • 完整 ubulk 的 cooked 纹理：NewMipCount 不被夹，画质与无宏一致
  • 缺 ubulk 纹理：请求降到真实最高 mip，不崩且无 'not in bulk data' 日志(DEBUG=1 可验)
  • 编辑器 uncooked 且 bIsCookedForEditor=false：XDShouldClamp 返回 false，走 DDC 不夹
  • inline(IsInSeparateFile==false)bulk：视为存在，不误夹
  • bIsCookedForEditor=true 且缺源：仍夹取

可反馈上游：最小复现：cook 一张纹理后删/截断其最高 mip 的 ubulk(或令 BulkOffset+BulkSize>FileSize)，4.26 请求该 mip 时 IORequests[MipIndex]==null 解引用崩溃。建议上游在 SetIORequests 判空后走 bFailedOnIOError。

风险评估

原代码风险：stream-in 热路径上做 DoesExist/FileSize/GetFilename 判断有磁盘 IO 与字符串分配开销，且夹 mip 牺牲画质。

移植风险：改动所有 cooked 纹理的 mip 请求主流程，边界夹错会导致贴图永久低 mip。

开发自检

  • 删 .ubulk 的 cooked 包 StreamIn 不崩且降到安全 mip
  • r.XD.TextureMipTrace=1 的 ResidentLODs 夹取前后一致
  • 正常包 mip 数与无补丁一致（画质回归）

结论置信度：medium — UE5 缺 ubulk 失败点是否仍在 FTexture2DMipDataProvider_IO（:55 仍跳过 GetBulkDataSize()<=0）需实测
