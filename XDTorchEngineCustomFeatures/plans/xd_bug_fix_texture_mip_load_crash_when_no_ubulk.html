3. 代码级实现（开发用）

独立 Agent 审核并修正修正 6 处　提出问题 3 条

审核意见：clamp 主逻辑与 UE4 helper（Texture2D.cpp:90/109/159）核对无误、UE5 StreamIn 位置(:1962)与 BulkData.h:600/584 API 均真实存在，值得保留；最大问题是步骤 1 的 before 张冠李戴（BulkData2.cpp 里其实是 TextureMipTrace 日志），且 port-as-is 应改 api-adapt。

改接口/改名 改动方式：主补丁点 UTexture2D::StreamIn 在 UE5 仍在且签名一致（Texture2D.cpp:1962），但资源访问已由 Resource/PlatformData 改为 GetResource()/GetPlatformData()（Texture2D.h:85 确认存在），且诊断日志所在的 BulkData2.cpp 在 UE5 已拆分，故需按 UE5 API 调整而非原样搬运。

代码脉络：宏开启后在 Texture2D.cpp:89-175 新增 XDShouldClampTextureStreamInMipCount/XDDoesTextureMipSourceExist/XDClampTextureStreamInMipCount，并在 UTexture2D::StreamIn（:1301）入口把 NewMipCount 夹到真实存在 ubulk 源的最高 mip，CreateResource(:756) 与 Texture2DStreamIn_IO.cpp:55、Texture2DMipDataProvider_IO.cpp:31、BulkData2.cpp:992 加 r.XD.TextureMipTrace 诊断日志。UE5 UTexture2D::StreamIn 在 Texture2D.cpp:1962，签名一致。

风险评估

原代码风险：stream-in 热路径上做 DoesExist/FileSize/GetFilename 判断有磁盘 IO 与字符串分配开销，且夹 mip 牺牲画质。

移植风险：改动所有 cooked 纹理的 mip 请求主流程，边界夹错会导致贴图永久低 mip。

开发自检

  • 删 .ubulk 的 cooked 包 StreamIn 不崩且降到安全 mip
  • r.XD.TextureMipTrace=1 的 ResidentLODs 夹取前后一致
  • 正常包 mip 数与无补丁一致（画质回归）

结论置信度：medium — UE5 缺 ubulk 失败点是否仍在 FTexture2DMipDataProvider_IO（:55 仍跳过 GetBulkDataSize()<=0）需实测
