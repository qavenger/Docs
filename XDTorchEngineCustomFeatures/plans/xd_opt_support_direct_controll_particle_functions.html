修改草案 · XD_OPT_SUPPORT_DIRECT_CONTROLL_PARTICLE_FUNCTIONS

新增直接控制粒子的接口：生成/销毁/修改 Transform

未覆盖 移植 需接入点 结构性改动 工作量 M风险 中开发者 Ran Qing Sen主要模块 Engine

一句话结论：建议评估改用 Niagara 变量控制，避免为 Cascade 扩接口

背景：给游戏逻辑提供绕过组件生命周期、直接操作粒子实例的 API，便于大规模特效管理。

可主动舍弃性（UE5 架构更替）

需在新体系重做 Cascade 粒子 → Niagara

判定依据：UE5 特效体系已全面转向 Niagara，Cascade 仅保留兼容维护；项目迁移到 UE5 后特效会重做，针对 Cascade 运行时的定制可在迁移时直接不带过去。

舍弃前提：前提：迁移后在 UE5 用 Niagara 重做特效（不再走 Cascade 运行时）

UE5 替代能力：Niagara（NiagaraSystem / NiagaraComponent / NiagaraDataInterface）

相关文件：Source/Runtime/Engine/Classes/Particles/ParticleSystemComponent.h Source/Runtime/Engine/Private/Particles/ParticleComponents.cpp Source/Runtime/Engine/Private/Particles/ParticleEmitterInstances.cpp

0. 根因溯源（这个宏为什么存在）

上游缺失能力（UE5 可能已补）

结论：XD 为策划/程序提供了 4 个蓝图可调用的"直接操控粒子"接口：`BurstEmitterParticles`（指定发射器 burst N 个）、`SetEmitterParticlesTransform`（设定指定序号粒子的变换）、`KillEmitterParticle` / `KillEmitterParticles`（按序号杀粒子）。UE5 中这 4 个 UFUNCTION **均不存在**（全仓检索无命中），但底层能力仍在：`FParticleEmitterInstance::ForceSpawn(...)`（ParticleEmitterInstances.h:493）等内部 API 依旧存在；同时 Cascade **编辑器**已降级为插件（Plugins/FX/Cascade），而运行时（ParticleSystemComponent/FParticleEmitterInstance）仍在 Engine。因此：若项目仍以 Cascade 为主力，可按内部 API 重新包一层蓝图函数；若已转 Niagara（上游方向），建议直接放弃。

上游引入：XD 的粒子直接控制接口（宏开启后 UParticleSystemComponent 暴露 4 个 UFUNCTION（ParticleSystemComponent.h:1565-1577 一带），实现在 ParticleComponents.cpp:8371 起（BurstEmitterParticles(ForceSpawn)、:8397 SetEmitterParticlesTransform 等），依赖 FParticleEmitterInstance 的粒子数组/ForceSpawn 等内部状态）。

上游历史（是否修过）：已核实（rg 精确检索）UE5.8.2：①`BurstEmitterParticles`/`SetEmitterParticlesTransform`/`KillEmitterParticle(s)` 在 Source/Runtime/Engine 与 Plugins/FX/Cascade 内**均无命中**；②底层能力存在：`Source/Runtime/Engine/Public/ParticleEmitterInstances.h:493` `ENGINE_API virtual void ForceSpawn(float DeltaTime, int32 InSpawnCount, int32 InBurstCount, FVector& InLocation, FVector& InVelocity);`、:1005 `int32 ForceSpawnCount;`；③`SetEmitterEnable`（发射器开关）上游仍有（ParticleSystemComponent.h:431 基类虚函数、:1137 override）；④Cascade 编辑器已成为插件（Plugins/FX/Cascade 下有 CascadeParticleSystemComponent.h、CascadePreviewViewportClient、CascadeActions 等），运行时的 ParticleSystemComponent/FParticleEmitterInstance 仍在 Engine（即 Cascade 内容仍可运行，只是编辑器工具被插件化）。

为什么可以断定不是「故意为之」2 条依据
  • 上游未提供"按序号直接操控粒子"的蓝图接口，属 API 边界选择（这类操作会绕过粒子模拟的状态一致性，通常不建议从蓝图直接做）。
  • 上游以 Niagara 为粒子方向（并提供相应的 Spawn/Kill 节点），Cascade 仅维持兼容（编辑器已插件化），故不会为它补这类接口。

调用方契约：直接操控粒子必须保持粒子实例内部状态一致（索引有效、生命周期与碰撞/事件系统不冲突），并且只能在合法时机调用（通常需在游戏线程、模拟之后）。

内层真实语义：UE4（XD）：UParticleSystemComponent 暴露 4 个蓝图函数，内部查发射器实例、调用 ForceSpawn 或直接改写粒子数组/变换，或按索引杀粒子。UE5（上游）：不提供这些函数；内部仍有 ForceSpawn 等能力（ParticleEmitterInstances.h:493），但无蓝图出口。

代码库惯例：上游倾向让粒子的生成/销毁走模拟与模块系统（Cascade 的模块、Niagara 的节点），而不是暴露"按索引直接改粒子"的易错接口。

为何长期未被发现：属"内容/策划工具链"能力：不迁移不会崩，只在依赖这些蓝图节点的特效表现（爆裂、指定粒子位移、精确杀粒子）上体现；而且这些函数是按需暴露的 UFUNCTION，容易被遗漏在迁移清单之外。

XD 侧的做法与意图：XD 的目标是让特效能精确控制粒子（burst 数量、单个粒子位置、按序号销毁），用于表现层对战斗逻辑的精确配合。

⚠ 四点注意：①**不要以为 Cascade 被整体移除**——运行时仍在 Engine，仅编辑器插件化；否则会误判为"功能不可用而放弃"；②照搬 UE4 实现（ParticleComponents.cpp:8371+）会因粒子实例结构与相关 API 变化而失败，必须按 UE5 的 `FParticleEmitterInstance`（ParticleEmitterInstances.h）重写；③这 4 个 UFUNCTION 若已被蓝图/资产引用，**改名或改签名会影响现有蓝图资产**（引用丢失），需评估并保留同名同签名；④Niagara 已有等价的 Spawn/Kill 粒子能力——若内容已（或即将）迁 Niagara，优先引导迁移而不是为 Cascade 补接口。

迁移方案（按根因定）

先做取舍：①若项目 Cascade 仍是主力且确有需求 → 在项目侧按 UE5 内部 API（ParticleEmitterInstances.h 的 ForceSpawn 与粒子实例数据）重新实现 4 个同名 UFUNCTION，并保持签名不变以免破坏已有蓝图；②若已转 Niagara 或需求已消失 → 直接放弃该宏（删除 4 个函数与实现）；③无论哪条路径，都应在页面/清单中标注"这是内容工具链能力，需与特效团队确认"。

根因级自检用例

  • （若重做）蓝图节点可用：burst 指定数量、设定指定粒子变换、按序号杀粒子 均按预期生效
  • （若重做）粒子状态一致：无索引越界/崩溃，长时间运行稳定
  • （若重做）既有蓝图资产引用未破坏（同名同签名）
  • （若放弃）特效表现无回归（相关效果已用 Niagara 或其它方式实现）
  • 与 Niagara 混用场景正常（若项目两者并存）

可反馈上游：可向上游提议：为 Cascade 保留基本的"按发射器 burst/kill"蓝图接口（Niagara 已有等价能力，Cascade 侧缺）。

1. UE5 现状与证据

结论依据：UE5 Cascade 无粒子的生成/销毁/改 Transform 直接控制接口（UFXSystemComponent 只有 SetFloatParameter 等通用参数接口）

覆盖说明：无等价 Cascade 接口；Niagara 侧有变量直接控制

覆盖度：未覆盖  处置：移植

  1. 定位 UE5 对应文件

3. 代码级实现（开发用）

独立 Agent 审核通过

审核意见：全部核验通过：UE4 ParticleSystemComponent.h:1565-1577、ParticleComponents.cpp:8369-8443、ParticleEmitterInstances.cpp:2518-2592、ParticleEmitterInstances.h:533-548；UE5 UFXSystemComponent(ParticleSystemComponent.h:379)无这 4 个 API，ParticleEmitterInstances.h:493/521/528 仅有 ForceSpawn/KillParticle/KillParticlesFor

建议舍弃 改动方式：服务的是 Cascade(FParticleEmitterInstance) 直接操控；UE5 已把 Cascade 降级为 Plugins/FX/Cascade 并推 Niagara，UE5 UFXSystemComponent 无此 API，建议改 Niagara 变量控制。

代码脉络：宏开启后 UParticleSystemComponent 暴露 4 个 UFUNCTION（ParticleSystemComponent.h:1565-1577），实现在 ParticleComponents.cpp:8371 BurstEmitterParticles(ForceSpawn)、:8397 SetEmitterParticlesTransform、:8417 KillEmitterParticle、:8439 KillEmitterParticles；底层 FParticleEmitterInstance 新增 ForceKillParticles(ParticleEmitterInstances.cpp:2518) 与 ForceUpdateParticleTransform(:2560)，声明在 ParticleEmitterInstances.h:533-548。

步骤 1Runtime/Engine/Classes/Particles/ParticleSystemComponent.hUE4 ParticleSystemComponent.h:1565-1577

不在 UE5 UFXSystemComponent(ParticleSystemComponent.h:379) 上扩这 4 个 UFUNCTION

// XD_OPT_SUPPORT_DIRECT_CONTROLL_PARTICLE_FUNCTIONS - Begin

UFUNCTION(BlueprintCallable) void KillEmitterParticle(FName, int32 Index);

// 替代：改走 Niagara UNiagaraComponent SetVariable + 自定义 DataChannel/粒子读写接口
// （Plugins/FX/Niagara + Plugins/FX/CascadeToNiagaraConverter 已提供迁移工具）。

⚠ UE5 FParticleEmitterInstance 仍保留 ForceSpawn(:493)/KillParticle(:521)，若坚持 Cascade 可局部移植

步骤 2Runtime/Engine/Public/ParticleEmitterInstances.hUE4 ParticleEmitterInstances.h:533-548

放弃在 UE5 ParticleEmitterInstances 上加 Force* 虚函数

#if XD_OPT_SUPPORT_DIRECT_CONTROLL_PARTICLE_FUNCTIONS
virtual void ForceKillParticles(TArray<int32> Indices);
virtual void ForceUpdateParticleTransform(const TArray<int32>& Indices, const TArray<FTransform>& NewTransforms);
#endif
// UE5 ParticleEmitterInstances.h 无这两个方法（仅有 :493 ForceSpawn、:521 KillParticle、:528 KillParticlesForced）。
// 若必须保留：按原实现整体拷贝进 UE5 FParticleEmitterInstance（Burst 复用 ForceSpawn）

⚠ 原实现直接读写 ParticleIndices/ParticleData，依赖 Cascade 内存布局；Niagara 下语义不同

风险评估

⚠ 与早期迁移处置结论存在分歧：早期结论=要移植，代码级分析=建议舍弃。早期结论=移植，代码级分析=建议舍弃；建议以代码级分析为准并回写评估矩阵。

原代码风险：ForceUpdateParticleTransform 在 bUseLocalSpace 分支做矩阵求逆，且 NewTransforms 与 Indices 长度不校验，越界/索引错位会踩内存；循环内 O(n) 前移数组。

移植风险：为 Cascade 扩接口会被 UE5 弃用倒计时拖累；Niagara 改法需重做特效资源与调用点。

开发自检

  • 确认项目特效已/可转 Niagara（CascadeToNiagaraConverter）
  • 若保留 Cascade 路径，越界与 local space 分支单元测试
  • UFUNCTION 的 BP 暴露在 UE5 资产中不丢引用

结论置信度：medium — 项目是否已大规模转 Niagara 决定 abandon 是否可接受；Niagara 侧具体等价 API 行号未逐一核实。
