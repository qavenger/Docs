修改草案 · XD_BUG_FIX_ADD_ARRAY_ELEMENT_TO_SEQUENCER_TRACK

修复 TArray 属性元素无法添加到 Sequencer 轨道

待确认 移植 引擎内实现 仅加接入点 工作量 S风险 低开发者 Han Shu Bin主要模块 Editor/Sequencer

一句话结论：在 UE5 MVVM 下复测数组元素添加

0. 根因溯源（这个宏为什么存在）

上游缺陷（需上游修复或长期携带补丁）

结论：UE4 的 FSequencerObjectBindingNode::AddPropertyMenuItems 用「每轮重置 PropertyNameIndexEnd」（:1127-1135）、「仅 ArrayIndex==INDEX_NONE 才去重」（:1408-1412）、「MenuName 以 ] 结尾就传 -1 防止截断」（:1464-1474）三个补丁绕过数组元素 PropertyPath 的层级歧义——根因是菜单按 MenuName 字符串分组/去重，而数组元素的路径比同名字段多一层。另半是给 FParticleSysParam 各字段加 Interp，使其成为 Sequencer 可关键帧属性。

上游引入：Sequencer 半边：XD 4.26 fork 于 SequencerObjectBindingNode.cpp:1127/1133/1408/1464/1470，开关 XDBuildFixBugConfiguration.cs:252 = 1（「Fix a bug that TArray property's element can not add to sequencer's track」）。Interp 半边：ParticleSystemComponent.h:118-174（9 个属性，含 Name/ParamType/Actor/Material），同宏号。

上游历史（是否修过）：上游已修：75def5ebd389（2025-02-19 ludovic chabant，ue5-main CL 40157997，Jira UE-226713，「Sequencer: rewrite how the add track menu works for property tracks」）明确写「Keying struct properties for structs in arrays was broken」，并把 XD 打过补丁的那套 PropertiesTraversed/ArrayIndex 去重与 MenuName.EndsWith("]") 逻辑整体删除，改为 FObjectBindingModel 按 FPropertyPath 分组；`git merge-base --is-ancestor 75def5ebd389 HEAD` 通过 → 5.8.2 HEAD(16d75d847145) 已含（ObjectBindingModel.cpp:644-681、:755-765）。Interp 半边未上游化：5.8.2 ParticleSystemComponent.h:110-152 仍无 Interp。

为什么可以断定不是「故意为之」4 条依据
  • 上游自陈这是 bug（75def5ebd389 提交信息「Keying struct properties for structs in arrays was broken」+ 新增 MovieSceneTestObjects 自动化测试），而非设计；
  • UE4 原代码用 `EndsWith(TEXT("]"))` 猜语义、并在注释里写「if you modify the MenuName format, please also modify…」（fork :1417），是典型的临时绕过信号；
  • 去重逻辑依赖外部排序（KeyablePropertyMenuData.Sort）才能正确，属于隐式契约，重构后即消失；
  • UE5 重写后数组元素直接走同一 FPropertyPath 分组（ObjectBindingModel.cpp:665-673 用 PropertyInfo.ArrayIndex 生成「Name [N]」），证明正确做法不需要那些补丁。

调用方契约：菜单构建：SequencerObjectBindingNode.cpp:1464-1474 → FNewMenuDelegate::CreateSP(…, bIsArray ? -1 : PropertyNameIndexStart + 2)；Interp 半边：UE5 SequencerObjectChangeListener.cpp:35「Interp properties are always keyable」是唯一的可关键帧判定依据（CPF_Interp）。

内层真实语义：数组元素路径被截断时 PropertyNameIndexStart 越过元素层 → 菜单项缺失/层变浅；PropertyNameIndexEnd=-1 表示「不截断」；去重分支在 ArrayIndex==INDEX_NONE 时才 continue，否则元素被重复加入菜单。Interp 语义：有 CPF_Interp 的属性被 FSequencerObjectChangeListener 显式视为 keyable，无则落入 Unknown 由 CanKeyProperty 进一步判定。

代码库惯例：让属性可关键帧的官方做法是给 UPROPERTY 加 Interp：Epic 自身如 Scene.h:144-194（FPostProcessSettings 大量 `UPROPERTY(Interp, BlueprintReadWrite, …)`），而不是在 Sequencer 侧特判。

为何长期未被发现：只在「数组元素属性 → 添加轨道」这一条编辑路径上出现，PIE/打包完全无关；症状是菜单里元素不出现或与同名字段菜单合并，开发者会以为是属性不可关键帧。

XD 侧的做法与意图：ParticleSystemComponent.h:118-174 逐字段加 Interp（保留原 Category/BlueprintReadWrite），让粒子参数能在 Sequencer 里做轨道；Sequencer 半边是「先让它能用」的权宜补丁。

①把 UE4 那三处补丁直接搬到 UE5 是错的方向：5.8.2 已无 AddPropertyMenuItems/PropertiesTraversed 这套结构，落点会编译失败或重复分组；②给 FName/TEnumAsByte/Actor/Material 也加 Interp（fork 现状）会让 Sequencer 把这些不可插值字段当成 keyable，可能生成无意义的浮点通道或关键帧失败——最小正确改动是只给 Scalar/Scalar_Low/Vector/Vector_Low/Color 加 Interp；③UE5 的 FParticleSysParam 字段已改为 TObjectPtr（:110-152），照抄 UE4 的 `class AActor* Actor;` 会与 UE5 的 GC/TIsPODType 声明（:218）冲突。

迁移方案（按根因定）

Interp 半边迁：在 5.8.2 ParticleSystemComponent.h:110-152 只给数值/向量/颜色字段加 Interp（不动 Name/ParamType/Actor/Material），并确认 FParticleSysParam 的 TIsPODType 特化（:218）仍成立、序列化无变化。Sequencer 半边不迁：删除 UE4 的三处补丁，改用 UE5 的 FObjectBindingModel（:644-681/:755-765）行为，并以 75def5ebd389 新增的 MovieSceneTestObjects 测试覆盖「数组内结构体关键帧」。取舍：若只想尽快在 UE5 复现旧行为，可加 CVar 强制 bUseSubMenus=true（ObjectBindingModel.cpp:690 GSequencerObjectBindingShowNestedProperties），但那是掩盖而非修复。

根因级自检用例

  • 5.8.2 编辑器：对带 TArray<FStruct> 的对象在 Sequencer 加轨道，数组内每个元素的成员都能作为独立轨道加入；
  • 数组元素与同名字段（非数组）同时存在时不串味、不重复；
  • 粒子参数：给 ParticleSystemComponent 的 InstanceParameters 元素字段加轨道并打关键帧，PIE 中按轨道插值生效；Name/ParamType/Actor/Material 不出现在可关键帧菜单；
  • 旧 UE4 uasset 打开后序列化/GC 无差异（FParticleSysParam 布局与 TIsPODType 未变）。

审核意见：核实：UE4 SequencerObjectBindingNode.cpp:1127-1130 PropertyNameIndexEnd 重置、:1408-1415 `if (bFound && (ArrayIndex == INDEX_NONE))`、:1464-1474 bIsArray/-1 子菜单 均与 before 一致；UE5 ParticleSystemComponent.h:104-146 FParticleSysParam 字段、ObjectBindingModel.cpp:711/717/763（:711 GetNumProperties()==IndexStart+1、:

完全重构 改动方式：UE5 菜单逻辑已 MVVM 化，FSequencerObjectBindingNode 与 AddPropertyMenuItems 的 PropertyNameIndexEnd 参数都不存在，须按 FObjectBindingModel 新结构重写等价逻辑。

代码脉络：UE4 SequencerObjectBindingNode.cpp:1127-1135 每轮重置 PropertyNameIndexEnd，:1408-1412 仅 ArrayIndex==INDEX_NONE 才去重（数组元素不再被丢），:1464-1474 菜单名以 ] 结尾时给子菜单传 -1 防截断；ParticleSystemComponent.h:118-174 给 FParticleSysParam 各字段加 Interp 使其可被键控。

⚠ UE5 :763 只会传 PropertyNameIndexStart+1，无 PropertyNameIndexEnd，故用 ArrayIndex != INDEX_NONE 判定数组元素；:711 的 GetNumProperties()==IndexStart+1 判定保持不变

风险评估

原代码风险：数组元素与同名非数组属性共用 MenuName 比较，删除去重分支后循环内 MenuDataIndex 递增依赖外部排序，越界风险由 for 条件兜底但不显式。

移植风险：只影响编辑器 Sequencer 加轨道菜单；若判定错位会让子菜单层级变浅或数组元素仍不可加轨道，需人工回归 ParticleSystem 参数、结构体数组、InstancedStruct。

开发自检

  • 组件数组元素(DynamicMaterial 等)可从 Add Track 菜单直接加轨道
  • ParticleSysParam 数组元素可键控且曲线通道正确
  • 非数组结构体嵌套子菜单层级与 4.26 一致

结论置信度：medium — UE5 是否已通过 MVVM 路径(localize 后的 PropertyPath)顺带修好数组元素，需编辑器中实测：若已可加轨道，步骤 2 只需保留为防御性写法
