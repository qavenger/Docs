Patch ShaderLib 生成失败时返回错误标志（UE4.26 原实现恒返回 true）

部分覆盖 常开补丁 引擎内实现 结构性改动 工作量 S风险 中开发者 Yu Hang主要模块 RenderCore

一句话结论：修正外层 bOK 聚合（初值改 false 或返回单个失败）

0. 根因溯源（这个宏为什么存在）

上游缺陷（需上游修复或长期携带补丁）

结论：UE4.23 起 FShaderLibraryCooker::CreatePatchLibrary 的返回值恒为 true：局部 bool bOK = true 后用 |= 聚合子库结果，逻辑上不可能表达"有任一子库失败"。调用方 ShaderCodeLibraryToolsCommandlet 依赖该返回值决定退出码，于是 patch 流程失败时只留错误日志、退出码仍为 0。

上游引入：1eebce443b13（Mark Satterthwaite，2019-04-16，CL 5933354，"Initial work to support creating additive 'patch' shader libraries"），首个发布版本 4.23.0-preview-1；引入当天即为 bool bOK = true; bOK |= 形式。

上游历史（是否修过）：git log -S "bOK |=" 跨全部 ref 只命中该引入提交；此后 7 年无人改动语义，该行只因 2026-02-03 文件拆分（Laura Hermanns，ShaderCodeLibrary.cpp → ShaderLibrary/ 目录）被"路过"。当前 5.8.2 仍在 Runtime/RenderCore/Private/ShaderLibrary/ShaderCodeLibrary.cpp:2672/2677。ue5-main、ue6-main 同样保留 |=。

为什么可以断定不是「故意为之」4 条依据
  • "所有子库都成功才算成功"应写成 bOK &= f()（初值 true 才能成立）；true + |= 无法表达该语义。
  • "任一子库成功即成功"应写成 bool bOK = false; bOK |= f()；初值 true 会让结果恒真。
  • 若真想要"永远返回 true"，正常写法是 return true 或加注释，不会既保留 bool 返回值又让调用方判 0/1。
  • |= 常被辩解为"防短路、强制跑完所有 library"，但 |= 与 &= 都不短路（只有 ||/&& 短路），该理由不成立。

调用方契约：ShaderCodeLibraryToolsCommandlet.cpp:55 起即 return FShaderLibraryCooker::CreatePatchLibrary(...) ? 0 : 1;（4.26.2:49 / 5.8.2:55）。恒真 ⇒ "1" 分支成为死代码，commandlet 永远以退出码 0 结束，CI 无法据此判失败。

内层真实语义：内层 FEditorShaderCodeArchive::CreatePatchLibrary（UE4.26:1250 起 / UE5.8.2 EditorShaderCodeArchive.cpp:1235-1286）在 Load 失败、SaveToDisk 失败、PackageNativeShaderLibrary 失败时都会置 bOK=false 并打 UE_CLOG(..., LogShaderLibrary, Error, ...)；外层循环的唯一职责就是聚合它，|= 让聚合失效。

代码库惯例：整个 Source/Runtime 中 bOK |= 仅此一处；同类"累积成功"聚合惯用 &=（ShaderPipelineCache.cpp、PipelineFileCache.cpp）。

为何长期未被发现：这是 WITH_EDITOR 的 patch 专用路径，只有 -run=ShaderCodeLibraryTools 这类流程会走到；失败时 LogShaderLibrary 仍有 Error 日志，表象是"有错误日志但退出码正常"，不会归咎到返回值。

XD 侧的做法与意图：XD 在 UE4.26 fork 已认定该返回值不可用（XDBuildFixBugConfiguration.cs:616-620 注释明确："没有差异"与"真出错"都表现为 false），于是给 FShaderCodeLibrary::CreatePatchLibrary（ShaderCodeLibrary.cpp:2804）与 FEditorShaderCodeArchive::CreatePatchLibrary（:1550）增加 bool& bError：Load/Open 失败、Save/Package 失败才置 true（:1619/:1631），GetNumShaderMaps()==0（无差异）只打 Verbose；XDLivePatchPakUtil.cpp:692 用 bErrorOccured 判失败。

⚠ 不要裸改 &=：UE5.8.2 内层 EditorShaderCodeArchive.cpp:1256 在"没有可 patch 的 shader"时也返回 false（bOK = OutLibrary.SerializedShaders.GetNumShaderMaps() > 0;，只打 Verbose）。裸改 &= 会把每个"无差异"的子库都判成失败，XDLivePatch 里会直接 return false（误报）。

迁移方案（按根因定）

UE5 迁移按 XD 的 bError 语义做（推荐）：外层保持 |= 聚合（或改为显式逐项判断），把 bError 作为唯一失败信号；或先修正内层 no-op 语义（无差异视为成功）后再用 &= 聚合。二者择一，不要混用。

根因级自检用例

  • OldMetaDataDir 缺失或损坏 → 返回值/ bError 应为 false（失败）
  • 所有子库都无差异（no shader to patch）→ 应为 true（成功），且只打 Verbose
  • OutDir 只读导致 SaveToDisk 失败 → 应为 false，且 commandlet 退出码非 0
  • 多 library 场景：任一失败即整体失败，其余子库仍应跑完（不短路）

可反馈上游：可顺手给 Epic 报 bug：用 -run=ShaderCodeLibraryTools 构造一次保存失败，观察错误只出现在 LogShaderLibrary、退出码仍为 0——这就是最小复现证据。

3. 代码级实现（开发用）

独立 Agent 审核通过提出问题 1 条

审核意见：分类与证据吻合：内层 FEditorShaderCodeArchive::CreatePatchLibrary 已返回 bOK（EditorShaderCodeArchive.cpp:1235-1286），外层 bOK 初值 true 后 |= 恒真（ShaderCodeLibrary.cpp:2672/2677/2680），after 的 &= 修正正确，api-adapt 合理。

风险评估

原代码风险：外层恒真，Cook/Patch 出错被静默忽略，产出不完整 shader 库直到运行期才暴露。

移植风险：改为 &= 后任何单个 library 失败即整体失败，需确认多 library 部分成功场景是否可接受。

开发自检

  • 构造一个 OldMetaDataDirs 缺失的 patch，确认返回 false
  • 正常 patch 返回 true
  • 调用方 Commandlet 对 false 正确报错退出

结论置信度：high
