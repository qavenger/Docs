修改草案 · XD_PC_RENDERING_SUPPORT_HIDE_SECONDARY_DIRECTIONAL_LIGHTS_DEFERRED_SHADOWMASK

PC 支持被隐藏的次要平行光仍写入 Deferred ShadowMask（保留其阴影遮蔽）

未覆盖 移植 需接入点 结构性改动 工作量 M风险 中开发者 Wang Xiao Bo主要模块 Engine

一句话结论：与 XD CustomUnlit forward 路径绑定；UE5 下可先评估 LightingChannels 能否替代

0. 根因溯源（这个宏为什么存在）

XD 定制需求（非上游缺陷）

结论：FLightSceneProxy::IsHiddenThisLightInDeferredLighting()（UE4 SceneManagement.h:1585-1587，默认 false）由 FDirectionalLightSceneProxy 按 UDirectionalLightComponent::bHiddenThisLightInDeferredLighting（DirectionalLightComponent.h:266；cpp:593-595 override、:599 成员、:606、:1076 初始化、:1198 属性名匹配、:239 Proxy 拷贝）覆写；各处光照循环据此 continue 跳过直达光但保留阴影遮罩：LightRendering.cpp:1411/1432/1482/1510/1608/1723、TranslucentLighting.cpp:1664、TiledDeferredLightRendering.cpp:200。

上游引入：XD fork（P4，无 git）。XDBuildRenderingConfiguration.cs:165-166 注释 support hidden secondary directional light's deferred shadow mask on PC，作者段头 /* Wang Xiao Bo */。

上游历史（是否修过）：已核实 UE5 5.8.2：LightSceneProxy.h 中 IsHiddenThisLightInDeferredLighting 0 命中（:326 只有 GetUsePerPixelAtmosphereTransmittance）；DirectionalLightComponent.h/.cpp 0 命中。UE5 光照已 RDG 化：LightRendering.cpp:1730 循环 StandardDeferredStart→UnbatchedLightStart、:1735 RenderLight(GraphBuilder, Scene, View, SceneTextures, LightSceneInfo, ...)，另有 :1749/:1770 两个平行循环需同样加卫；TiledDeferredLightRendering.cpp 在 UE5 已删除（`rg --files` 无此文件），UE4:200 的补丁无处对应；TranslucentLighting.cpp 仍在但循环行号已变。UE5 仅原生提供 FLightSceneProxy::AffectsTranslucentLighting()（LightSceneProxy.h:238，成员 bAffectTranslucentLighting），语义为是否影响半透明，不等于隐藏直达光。

为什么可以断定不是「故意为之」4 条依据
  • UE5 LightSceneProxy.h 无该虚函数，属从未被上游吸收的 XD 定制，非上游缺陷
  • XD 同时补了 UPROPERTY（DirectionalLightComponent.h:266）、构造初始化（cpp:1076）、编辑器属性名匹配（:1198）与 Proxy 拷贝（:239），是成套有意设计
  • cs:166 注释明确说明用途（hidden secondary directional light + deferred shadow mask），是玩法需求
  • UE5 的 LightingChannels 只能按通道整体过滤（阴影一起去掉），达不到「留遮罩去直达光」语义，故非原生已有能力

调用方契约：勾选该属性的平行光在 deferred 下不可见直达光但保留阴影；LightRendering.cpp 六处 + TranslucentLighting.cpp:1664 + TiledDeferred 任一漏加即「部分 pass 可见」；漏 TranslucentLighting 会让半透明体积仍被照亮。

内层真实语义：失败路径=宏关闭时 override 不存在，走基类行为（等价 false）即正常照明；正常路径=返回 bHiddenThisLightInDeferredLighting（默认 0，不隐藏）；空操作=非平行光的 FLightSceneProxy 默认返回 false（SceneManagement.h:1586）不参与。

代码库惯例：UE5 惯例：用 LightingChannels（GetLightingChannelMask）做「部分物体不受光」、用 bAffectTranslucentLighting（LightSceneProxy.h:238）做半透明隔离、用 bCastShadows/bCastDynamicShadows 控阴影；单光「有阴影无直达光」无原生等价物。

为何长期未被发现：只有关卡中手动勾选且处于 deferred 的平行光才生效；漏加卫时主视图正常，仅在半透明/VSM/LPV 等次要 pass 表现为漏光，QA 难发现。

XD 侧的做法与意图：实现「副光只投影、不照明」的性能与美术双重诉求，避免用额外 pass 屏蔽直达光。

看似正确其实有害：①只补 LightRendering.cpp:1730 主循环而漏 :1749/:1770 两个平行分支与 TranslucentLighting，会出现半透明/次 pass 仍被照亮；②照搬 UE4 TiledDeferredLightRendering.cpp:200 找不到文件（UE5 已删），若新建文件反而把 UE4 tiled deferred 路径带回来；③continue 位置若落在 SortedLights 索引/批量光计数计算之前，会破坏 StandardDeferredStart/UnbatchedLightStart 语义；④UE5 RenderLight(GraphBuilder,...) 是 RDG 采集，continue 必须在 RDG 调用前，否则 GraphBuilder 已引用该光的 uniform buffer 会触发断言/use-after-free；⑤该标记仍会被 LPV/VSM/距离场收集（原风险已注明），期望「完全隐身」会误判已修好。

迁移方案（按根因定）

方案A（若语义可被原生替代）：LightingChannels + bAffectTranslucentLighting 组合表达（通常不行，会连阴影一起去掉）；方案B（推荐，语义对齐）：在 UE5 LightSceneProxy.h:326 GetUsePerPixelAtmosphereTransmittance 之后重加 `virtual bool IsHiddenThisLightInDeferredLighting() const { return false; }`，DirectionalLightComponent.h 加 bHiddenThisLightInDeferredLighting:1 与 cpp override，并在 UE5 全部 deferred 直达光循环（LightRendering.cpp:1730/1749/1770、TranslucentLighting 对应循环、以及新引入的移动/移动延迟路径）加 continue；方案C：改为自定义组件的 lighting channel 方案。取舍：B 保持既有资产语义，需维护多 pass 一致性；A 最小但要美术改关卡。

根因级自检用例

  • 勾选该属性的次级平行光：主视图无直达光、阴影遮罩仍在
  • 同一关卡半透明物体（TranslucentLighting 路径）不被该光照亮
  • 主循环与 :1749/:1770 三条路径行为一致（无部分 pass 可见）
  • 未勾选的光与非平行光行为与 UE5 原生完全一致（默认 false 回归）
  • LPV/VSM 行为已知并文档化（不因该标记改变，避免误报）

风险评估

原代码风险：该标志与 XD CustomUnlit forward 路径绑定，其它 pass 漏加会出现「部分 pass 可见」。

移植风险：影响 PC deferred 直达光与 translucency volume；隐藏光可能仍被 LPV/VSM 收集，需回归阴影遮罩与 LPV。

开发自检

  • 隐藏的次要平行光不贡献直接光但阴影遮罩仍在
  • 半透明/头发/LPV 一致跳过该光

结论置信度：medium — bHiddenThisLightInDeferredLighting 与 UE5 光照函数图集/聚簇剔除的交互需实测。
