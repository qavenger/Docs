0. 根因溯源（这个宏为什么存在）

上游缺陷（需上游修复或长期携带补丁）

结论：MountOBB 用 OpenReadInternal 打开外置 main/patch OBB，失败时 return nullptr（UE5 Source/Runtime/Core/Private/Android/AndroidPlatformFile.cpp:2274），紧随其后的是 check(nullptr != File)（:2865）。Development 下直接 fatal；Shipping 下 check 被裁掉后继续 MakeShareable(nullptr) 并进入 FZipUnionFile::AddPatchFile，那里第一句就是 file->Size()（:1034-1036）→ 空指针崩溃。外置 OBB 缺失/路径错/版本号不符是玩家环境常态，用 check 处理外部输入属上游缺陷。XD 在 UE4-5298 上只能插 LowLevelOutputDebugStringf 定位（fork 1036-1047/1679-1717/2299-2307）。

上游引入：上游：ffde9aa6b7cd，2014-11-17，Rene Rivera，UE-4398（Android Media plugin 与打包改造）。blame 显示 MountOBB 的 check 与 ZipResource.AddPatchFile 两行均指向该提交（当时文件名为 Source/Runtime/Core/Private/Android/AndroidFile.cpp:1788-1792）。

上游历史（是否修过）：git log -S "check(nullptr != File)" -- Source/Runtime/Core/Private/Android/ 只命中 ffde9aa6b7cd，说明该行 12 年未被改动；git show <ref>:Engine/Source/Runtime/Core/Private/Android/AndroidPlatformFile.cpp | grep -c 在 4.23.0/4.26.0/5.0.0/5.3.0/5.8.2-release 与 origin/ue5-main、origin/ue6-main 均为 1 → 至今未修。5.8.2 唯一变化是成功路径补了一行 Mounted OBB 日志（:2867，2ae7977cbb96e 2024-06-28）与 OpenReadInternal 重命名（391e5e4c93c10 2025-02-19），失败路径原样保留。

为什么可以断定不是「故意为之」4 条依据
  • check() 语义是内部不变量断言，OBB 打开结果是外部输入，作者不可能意在“打包后必崩”。
  • 同函数成功路径在 2024 年还专门补日志（2ae7977cbb96e），说明失败路径确实没被照顾，而非有意保持沉默。
  • 若真要 fail-fast 也应带可读信息（ensureAlwaysMsgf/UE_LOG），此处 check 无任何输出，无法定位是哪个 OBB。
  • XD 把 if (nullptr == File) 放在 check 之后，正说明“失败是可能的”这一认知；若上游认为不可能失败，XD 也不会加这段。

调用方契约：FAndroidPlatformFile::InitializeFileSystem 在 :1563/1569/1575/1590/1597/1625/1631 逐条 MountOBB(GOBBMainFilePath/GOBBPatchFilePath/Overflow1/2)；MountOBB 无返回值，失败无上报通道，后果由 ZipResource 上的所有 pak/资源查找承担。

内层真实语义：失败路径：OpenReadInternal 三条分支 IsLocal/IsResource/AAssetManager_open（:2243-2274）全部 return nullptr。正常路径：返回 new FFileHandleAndroid。不存在“空操作/无差异”路径——MountOBB 只有成功或崩。

代码库惯例：同文件对外部文件用 FileExists()/bool 而非 check；平台文件层惯例是失败返回 nullptr 并由调用方 UE_LOG + 降级，例如 OpenReadInternal 自身就 return nullptr。

为何长期未被发现：只在“外置 OBB 且打开失败”时触发（GPackageName/OBB 版本号不符、SD 权限、OBB 未下完）；Shipping 下 check 被裁掉，崩点显示在 FZipUnionFile 的 zip 解析里，堆栈与真因无关，容易被当成内存/包体问题。

XD 侧的做法与意图：fork：Source/Runtime/Core/Private/Android/AndroidPlatformFile.cpp:1036-1047 打印 OBBDir1/OBBDir2/Main/PatchOBBName；1679-1717 在 OpenRead 各分支打印 LocalPath/AssetPath/IsLocal/IsResource；2299-2307 在 check 后补 File 空判日志。开关：Source/Programs/UnrealBuildTool/Configuration/XDBuildConfiguration/XDBuildFixBugConfiguration.cs:166（注释 ANDROID MountOBB crash issue, UE4-5298）。意图是先拿到真机日志，未改行为。

⚠ 把 check 换成 if (!File) return; 会静默丢掉整个 OBB，上层继续跑但资源缺失（纹理/音频丢失、后段不可复现崩溃），比崩更难查；⚠ 只把日志挪到 check 之前也没用，check 仍会 fatal；⚠ 用 MakeShareable(File) 前不判空等于没修。

迁移方案（按根因定）

UE5 迁移保留诊断日志同时补真正的失败路径：方案A（推荐）MountOBB 改返回 bool，失败 UE_LOG(LogAndroid, Error, 明确路径与原因) 后 return false，InitializeFileSystem 汇总失败并降级；方案B 最低成本：check 改为 if (!File){ UE_LOG(...); return; }，但必须接受“静默丢 OBB”的副作用并在上层加 OBB 缺失标记；方案C 原样搬运宏（不做，问题仍在）。无论哪种，MakeShareable 前必须判空。

根因级自检用例

  • 正常：OBB 路径正确 → 读取 pak 成功，且有 OBBDir1/2 与目标文件日志。
  • 失败：故意改错 GPackageName → 不出现 check fatal，输出可直接定位的 Error 日志，函数可控返回。
  • 边界：Shipping 与 Development 下都不再崩在 AddPatchFile 的 file->Size()。
  • 边界：OBB 存在但 0 字节/不可读 → 同样走失败分支而非崩溃。
  • 回归：只加日志的版本不得改变成功路径行为（挂载数、pak 内容一致）。

可反馈上游：在 5.8.2 上：Android 打包并使用外置 OBB，令 main.<ver>.<pkg>.obb 的查找路径（GOBBFilePathBase 或 GPackageName）与实际不符，用 Shipping/Test 构建启动（check 被裁掉）→ 崩在 FZipUnionFile::AddPatchFile 的 file->Size()（AndroidPlatformFile.cpp:1034-1036），而报错点误导。建议 MountOBB 失败返回 false + UE_LOG，勿用 check。

风险评估

原代码风险：check(nullptr!=File) 会致命退出，外置 OBB 路径错误即崩。

移植风险：仅日志、不改功能；误把 check 换 return 会静默丢资源。

开发自检

  • 外置 OBB 启动，logcat 打出 OBBDir/main/patch 路径
  • 模拟器与真机都能挂载 main OBB

结论置信度：medium — UE5 是否已修 UE4-5298 崩溃点未确认；UE5 OBB/overflow 逻辑改动大，须实测。
