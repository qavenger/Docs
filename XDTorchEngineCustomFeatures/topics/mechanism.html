⚙️ 宏系统与构建机制

UBT 如何把 566 个特性宏注入到引擎

1. 这套机制是什么

XDBuildConfiguration 不是一个普通配置文件，而是构建期特性开关系统：UBT（UnrealBuildTool）在构建目标时用反射读取 7 个 C# 类里的 public static int 字段，把「字段名=值」注入编译环境的全局宏定义，最终写进每个模块的 Definitions.*.h。因此：

  • C++ 与 Shader（USF/USH）都可以直接 #if XD_XXX 使用，无需 include。
  • 宏是全局的——同一个宏在所有模块里取值一致，没有按模块区分的可能。
  • 修改宏的值会改变 Definitions.h 的内容，从而触发全量重新编译，所以不要把随平台/编辑器状态频繁变化的开关放在这里。

3. 构建流程（源码级）

  1. XDBuildConfiguration.ConfigurationClasses 列出 7 个类名。
  2. UEBuildTarget.SetupXDNewFeaturesGlobalMacros()（Configuration/UEBuildTarget.cs）在初始化全局编译环境时被调用。
  3. 先执行 XDBuildConfiguration.CheckDependencies()：串联调用 7 个类的 CheckDependencies()，失败即 throw new BuildException("Check XD Features Dependencies Error !!!")，构建直接中止。
  4. 遍历 7 个类，用 BindingFlags.Public | Static 反射所有字段，逐个 GlobalCompileEnvironment.Definitions.Add("字段名=值")；类名找不到时抛 BuildException。
  5. 构建系统把这些定义写进各模块的 Definitions.*.h（可在 Intermediate/Build/.../Definitions.XXX.h 中核对实际值）。

5. 使用建议

  • 新增 Feature：在对应类的 public static int 区域加宏 + 注释（作者/原因），并在引擎源码里用 #if 使用；如果与其它宏有依赖，补进 CheckDependencies。
  • 关闭 Feature：直接把值改为 0。注意值只有 0/1 两种语义（XD_TORCHLIGHT_SEASON 等为参数值）。
  • 改宏后的必做动作：全量编译 + 清理 Engine/DerivedDataCache 与项目 DDC 重新编译 Shader；PSO/DDC 相关宏还需要清理打包缓存。
  • 平台差异尽量下沉到 C++：宏是构建期全局值，团队约定不要把 IsWithEditor 之类的差异写进 UBT 逻辑，否则 Editor/Runtime 引擎会因 Definitions.h 不同而整包重编。
  • 验证宏是否生效：在 Intermediate/Build/<Platform>/<Config>/... 的 Definitions.*.h 里搜索宏名；构建日志中也会打印 Start/End Setup XD Features Macros 与依赖检查结果。

6. UE4.26 与 UE5.8.2 的构建体系差异

迁移前先把「宏系统赖以生存的那套机制」在两代引擎里的差异对齐。下表已按 UE4.26 定制引擎与 UE5.8.2 实际源码核对（路径均为引擎内相对路径）。

#维度UE4.26（XD 现状）UE5.8.2（目标）对宏系统的影响
1宏定义位置Programs/UnrealBuildTool/Configuration/XDBuildConfiguration/*.cs（7 个类）UBT 结构变化：Configuration/ 下新增 Rules/ 子目录（TargetRules.cs、ModuleRules.cs 移入其中）文件放置与命名空间按新结构组织；类/字段形态可沿用
2宏注入点侵入 UEBuildTarget.SetupGlobalEnvironment（UE4.26 L3399）→ 末尾调用 SetupXDNewFeaturesGlobalMacros（L3817），反射读取 7 个类字段写入 GlobalCompileEnvironment.Definitions官方在 UEBuildTarget.SetupGlobalEnvironment（UE5.8 L6164）第 L6179 行执行 Definitions.AddRange(Rules.GlobalDefinitions)可以完全不动 UBT：在 *.Target.cs 里向 GlobalDefinitions 添加即可
3作用范围反射注入即全局，对所有模块（含引擎模块）生效TargetRules.GlobalDefinitions（全体模块）与 ProjectDefinitions（仅非引擎模块，UEBuildModuleCPP.cs:2831 以 !Rules.bTreatAsEngineModule 判定）项目专有宏建议用 ProjectDefinitions，避免污染引擎/插件模块
4模块级宏ModuleRules.PublicDefinitions / PrivateDefinitions同左（ModuleRules.cs:1383 / 1388），并新增 bTreatAsEngineModule 等语义插件/模块自有的开关放模块级，不占全局宏
5配置文件BuildConfiguration.xml仍为 BuildConfiguration.xml；schema 由 UBT 反射生成（Configuration/Xml/XmlConfig.cs:163 CreateSchema），落盘到 Engine/Saved/UnrealBuildTool/BuildConfiguration.Schema.xsd；可配置类型 = 扫描 UBT 程序集（XmlConfig.FindConfigurableTypes）没有 <CustomConfig> 这种包裹节点（UE5 里 CustomConfig 是 ini 的 -customconfig= 概念）；在 UBT 里加带 [XmlConfigFile] 的类即可自动成为 XML 一节
6值应用方式XD 自写 CheckDependencies/SetupDependencies 在编译前改字段值XmlConfig.ApplyTo(实例)；注意它会跳过 static 成员（XmlConfig.cs:404），只有实例字段/属性会被赋值自定义配置类要用实例属性，再用 static Get() 缓存实例
7宏最终产物Intermediate/Build/<Platform>/<Config>/<Target>/Definitions.<Module>.h同左（UEBuildModuleCPP.cs:2319 生成 Definitions.h）宏值变化 → 该头文件变化 → 依赖模块全部重编（宏最昂贵的代价）
8Shader 宏各 ShaderType / Material 的 ModifyCompilationEnvironment 里 OutEnvironment.SetDefine(...)；C++ 宏不会自动进入 shader同左；新增 ini 机制 [GlobalShaderDefines]（Runtime/RenderCore/Private/GlobalShader.cpp:255）：+Definitions=(Shader=类型名,Define=名字=值[,ShaderFormat=][,PermutationID=])，仅对 FGlobalShader 子类生效，且各平台条目必须一致（否则 Fatal，提示 DDC 不一致）全局 Shader 的开关可配置化（不重编）；材质 Shader 仍需 C++ 桥接
9C++ 标准TargetRules.CppStandard = Default（4.26 实际 C++14/17）CppStandardEngine / CppStandard（C++20）老宏包裹的代码可能触发新警告/错误
10依赖校验无强制ModuleRules.bValidateCircularDependencies 默认 true（ModuleRules.cs:1496）以前「用宏绕开循环依赖」的写法会直接构建失败
11Unity 构建bUseUnityBuild同左 + bUseAdaptiveUnityBuild（默认 true，TargetRules.cs:1877）条件编译在合并单元中的可见性/顺序需要回归
12UHTUE4.26 的 UnrealHeaderToolUE5 重写版 UHT（C# 实现，规则更严）用宏包 UPROPERTY/UCLASS 更难迁移，必须走 CustomVersion
13UBT 自身UBT 源码随引擎，改后重编Engine/Build/BatchFiles/BuildUBT.bat；UBT 源码变化会触发自编译方案 A（改 UBT）有一次性成本，且所有模块 Definitions.h 会变化 → 全量重编
⚠ 修正一个常见误解：UE5 的 BuildConfiguration.xml 没有 <CustomConfig> 包装节点（那是 ini 的 -customconfig= 概念）。自定义 UBT 配置类的正确形态是：类 + [XmlConfigFile] 实例属性 + XML 里同名一节（<Configuration><你的类名>…</你的类名></Configuration>），schema 由 UBT 自动生成。

7. 适配 UE5 的三种方案

方案做法优点代价 / 风险适用
A. UBT 自定义配置类在 UBT 加 Configuration/TLBuildConfiguration/*.cs，字段标 [XmlConfigFile]；xml 控制默认值；在 Target.cs 或 UBT 注入点写入宏最贴近 XD 现状；xml 一键开关；可表达「引擎级」开关；既有依赖检查逻辑可平迁改 UBT → 自编译；宏值变化 = 全量重编；UE5 升级需跟 UBT diff必须编译期裁剪、且引擎模块也要用的开关（RHI/ABI/Shader permutation）
B. 工程侧 Target.cs / ModuleRulesGlobalDefinitions.Add(...)（全体）/ ProjectDefinitions.Add(...)（仅非引擎模块）；插件用 PublicDefinitions零引擎侵入；可在 Target.cs 里读环境变量/参数做灰度；升级成本最低开关分散在各 Target 文件；只影响该 Target 的模块项目/业务模块可见的迁移补丁（TL_MIG_*）
C. 去宏化（运行期化）CVar / ini / DeviceProfile / 插件 / Hook / CustomVersion不重编、可灰度、可回滚；把「功能存在性」与「是否启用」解耦需要改造调用点；有的能力天生要编译期裁剪策略、数值、画质、工具、平台行为、资产 schema

推荐：三层组合（L1 编译期 / L2 工程期 / L3 运行期）

层承载形式放什么对应迁移分析的处置
L1 引擎侧宏方案 A：UBT 配置类 + #if TL_MIG_*RHI/ABI 差异、Shader permutation、必须裁剪的极底层路径keep 14 项 + 部分 port 的 L2/L3 侵入项
L2 工程侧宏方案 B：Target.cs Global/ProjectDefinitions业务模块的迁移补丁、可灰度开关port 195 项中偏工程的部分
L3 运行期方案 C：CVar / ini / DeviceProfile / 插件 / Hook策略、数值、画质、工具、平台行为、错误提示config 66 + plugin 51 + hook 28
删除 / 补丁不迁移或常开补丁UE5 已覆盖，或已确认的 bugfixdrop 147（A1 98 + A2 49）+ patch 48

目标不是「把 549 个宏搬过去」，而是把它压缩成 少量 L1 编译期开关 + 一层工程定义 + 大量运行期配置/插件。

8. 落地步骤（含示例代码）

Step 1｜先建工程侧开关（方案 B，最快见效）

// Source/Torchlight_Migrate.Target.cs
public class Torchlight_MigrateTarget : TargetRules
{
    public Torchlight_MigrateTarget(TargetInfo Target) : base(Target)
    {
        // 全体模块可见（含引擎）：用于引擎侧迁移补丁
        GlobalDefinitions.Add("TL_MIG_RENDER_CUSTOM_SHADING_MODEL=1");
        GlobalDefinitions.Add("TL_MIG_UI_WORLD_KEEP_ALIVE=1");

        // 仅业务模块可见：项目自己的迁移补丁，不污染引擎/插件
        ProjectDefinitions.Add("TL_MIG_COOK_CHERRY_PICK=1");

        // 需要灰度时可在 Target.cs 里读环境变量决定是否添加（无需改 UBT）
        if (System.Environment.GetEnvironmentVariable("TL_MIG_STRICT_LOG") == "1")
        {
            GlobalDefinitions.Add("TL_MIG_STRICT_LOG_THROTTLE=1");
        }
    }
}

Step 2｜引擎侧开关用 UBT 配置类（方案 A，按需）

// Engine/Source/Programs/UnrealBuildTool/Configuration/TLBuildConfiguration/TLBuildFeatures.cs
class TLBuildFeatures
{
    // Desc: 迁移期着色模型容错：原工程有定制 MSM_CustomUnlit 枚举，UE5 无此枚举，
    //       资产加载会命中 check；开启后未知着色模型钳制为 Unlit。
    // 关闭条件: MSM_CustomUnlit 资产全部改造完成。
    [XmlConfigFile]
    public bool bMigRenderCustomShadingModel = true;

    static TLBuildFeatures? Cached;
    public static TLBuildFeatures Get()
    {
        if (Cached == null)
        {
            Cached = new TLBuildFeatures();
            XmlConfig.ApplyTo(Cached);   // 只应用实例成员
        }
        return Cached;
    }
}

<Configuration xmlns="https://www.unrealengine.com/BuildConfiguration">
  <TLBuildFeatures>
    <bMigRenderCustomShadingModel>false</bMigRenderCustomShadingModel>
  </TLBuildFeatures>

把值变成宏（二选一）：

  • 推荐：在 *.Target.cs 里 GlobalDefinitions.Add("TL_MIG_RENDER_CUSTOM_SHADING_MODEL=" + (TLBuildFeatures.Get().bMigRenderCustomShadingModel ? 1 : 0));
  • 或按 XD 原做法在 UBT 的 UEBuildTarget.SetupGlobalEnvironment（UE5.8 L6164，紧邻 L6179 的 GlobalDefinitions 合并处）追加注入，并保留 CheckDependencies 风格的依赖校验

Step 3｜Shader 侧桥接（不要把 C++ 宏当 shader 宏用）

  • 全局 Shader：优先 ini [GlobalShaderDefines]（无需重编；仅 FGlobalShader 子类；各平台条目必须一致）
  • 材质 / 后处理 Shader：在对应 ModifyCompilationEnvironment 里 OutEnvironment.SetDefine(TEXT("TL_MIG_X"), 1);
  • 插件 Shader：AddShaderSourceDirectoryMapping 映射虚拟目录 + 共享 include 里 #ifndef TL_MIG_X / #define TL_MIG_X 0 / #endif 兜底，保证 C++ 侧未定义时也能编译

Step 4｜建立「双构建」验收

  • 默认构建（迁移补丁全开）：保证能跑老资产 / 老逻辑
  • 全关构建（TL_MIG_*=0）：证明关闭后回到官方形态，用于归因「问题是不是迁移补丁引入的」

Step 5｜登记与淘汰机制

  • 每个 TL_MIG_* 定义处必须写：问题现象 / 修法 / 何时可以关闭（例：资产改造完成、插件上线后）
  • 建立「引擎改动 ↔ 宏名」索引（迁移工程的 MIGRATION_STATE.md 形态可延用）
  • 每完成一类资产/功能改造，把对应宏默认值改为 0，并记录关闭日期与依据

9. 常见坑

  • 宏值一变就全量重编：宏最终落进 Definitions.<Module>.h，任何值变化都会让依赖它的模块重编。因此不要把「每天都会变」的项目数值（赛季号、selector 数量）留在宏里——这也是迁移分析把这类标为 config 的原因。
  • 平台 / 编辑器差异不要放进宏：XD 已把 IsWithEditor 类判断下沉到 C++（否则 Editor/Runtime 会因 Definitions.h 不同而整包重编），UE5 继续遵守这条。
  • 改了 UBT 要有心理准备：UBT 自身会重新编译一次，首次构建变慢；UBT 升级时需要重新对齐 diff。
  • Shader 宏两条链路要同时改：C++ 宏 + Shader define（或 ini）缺一不可，否则会出现「代码走了新分支、Shader 还是旧分支」的诡异表现。
  • 反射 / 资产不要用宏包：UPROPERTY、资产字段、材质 schema 一律用 CustomVersion + 兼容读取；UE5 的 UHT 更严格。
  • 循环依赖：UE5 默认开启 bValidateCircularDependencies，以前靠宏绕过的循环依赖需要真正拆分。
  • 不要写 <CustomConfig>：按第 6 节第 5 条，直接加 [XmlConfigFile] 类即可；写 <CustomConfig> 会被 schema 校验报未知节点。
