结论先行：92 个宏属于「可以主动舍弃」——它们服务于 UE5 已经**架构性替换掉**的子系统，迁移到 UE5 后不需要把它们带过去。其中 49 个可以直接舍弃（连等价实现都不用做），12 个需要在新体系里重做等价能力，31 个需要先确认前提是否仍然成立。共涉及 6 个替代类别。

和「可丢弃清单」的区别：可丢弃清单（drop）是「UE5 自己已经修好了，所以宏可以删」；本页是可主动舍弃（reclaim）是「UE5 换了另一套子系统，这个宏服务的老对象已经不在迁移范围内，所以我们可以选择不做」。两者判断依据不同，但都落在迁移路线图的第 0 阶段（直接不处理）。

Cascade 粒子 → Niagara55 个宏

宏的作用对象是 Cascade 粒子运行时/编辑器。UE5 的特效体系已全面转向 Niagara（Cascade 只保留兼容维护），项目在 UE5 做特效时会用 Niagara 重做，针对 Cascade 的定制可以不带过去。

分级方式：工程化/侵入用「实心 → 底色 → 描边 → 虚线」四级形态表示程度递进（实心最强）。

UE5 覆盖度

UE5 已覆盖UE5.8 原生等价，可直接删除
部分覆盖UE5 有同类能力，只迁差异部分
未覆盖UE5 没有该能力，需迁移或补丁
待确认证据不足，迁移前需人工确认

落地位置（工程化可行性）

可工程化放项目/插件/配置即可，不动引擎
需接入点引擎留少量 Hook，逻辑在工程侧
引擎内实现必须改引擎核心
—处置=删除的行不适用（已删除/不迁移）

引擎改动方式

L0 无需改引擎纯工程/插件/配置即可（对应「可工程化」）
L0 引擎内补丁需改引擎源码，但不必新增扩展点（对应「引擎内实现」）
L1 仅加接入点引擎只需暴露 Delegate / Interface / CVar 等扩展点
L2 结构性改动枚举 slot / 新 Pass / schema 字段
L3 深度侵入核心结构/生命周期/序列化，慎入

迁移处置

删除UE5 已覆盖，直接删
常开补丁确认的 bugfix，作为 fork 常开补丁
配置化改为 CVar / ini / DeviceProfile / 命令行
插件化迁到项目模块 / 编辑器插件
接入点引擎只留 Hook，逻辑在插件
移植代码保留，适配后移植
保留引擎深度绑定，暂留并登记 Feature Card
