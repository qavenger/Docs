怎么用这份清单：这里的宏，是 UE5.8.2 已经原生提供等价（或更好）能力的部分。迁移时直接删除 UE4 fork 里的对应代码与宏，不要原样搬运。删除后如果发现行为确实不同，再按「partial」处理，把它登记到 工程化清单 或 接入点清单。

判定口径

  • covered：UE5.8 有等价实现（给出证据路径），可直接丢弃。
  • partial：UE5.8 有同类能力但语义/参数不同，只保留 XD 的差异部分（例如 UE5 有标准 TranslucencyAfterDOF，但没有 XD 的 TAA 后合成语义）。
  • 同一句「可丢弃」的前提是：迁移后项目实际使用 UE5 的原生路径（例如确定用 Niagara 替代 Cascade、用官方插件替代自研 DLSS）。如果项目仍沿用老路径，需单独评估。

标签说明

颜色规则：覆盖度=红绿灯 · 工程化=蓝色系 · 侵入=紫色系 · 处置=中性灰。
分级方式：工程化/侵入用「实心 → 底色 → 描边 → 虚线」四级形态表示程度递进（实心最强）。

UE5 覆盖度

UE5 已覆盖UE5.8 原生等价，可直接删除
部分覆盖UE5 有同类能力，只迁差异部分
未覆盖UE5 没有该能力，需迁移或补丁
待确认证据不足，迁移前需人工确认

落地位置（工程化可行性）

可工程化放项目/插件/配置即可，不动引擎
需接入点引擎留少量 Hook，逻辑在工程侧
引擎内实现必须改引擎核心
—处置=删除的行不适用（已删除/不迁移）

引擎改动方式

L0 无需改引擎纯工程/插件/配置即可（对应「可工程化」）
L0 引擎内补丁需改引擎源码，但不必新增扩展点（对应「引擎内实现」）
L1 仅加接入点引擎只需暴露 Delegate / Interface / CVar 等扩展点
L2 结构性改动枚举 slot / 新 Pass / schema 字段
L3 深度侵入核心结构/生命周期/序列化，慎入

迁移处置

删除UE5 已覆盖，直接删
常开补丁确认的 bugfix，作为 fork 常开补丁
配置化改为 CVar / ini / DeviceProfile / 命令行
插件化迁到项目模块 / 编辑器插件
接入点引擎只留 Hook，逻辑在插件
移植代码保留，适配后移植
保留引擎深度绑定，暂留并登记 Feature Card
