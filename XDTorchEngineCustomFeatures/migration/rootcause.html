这一步回答的是「这个宏为什么存在」——不是"UE4 有问题、UE5 这么改"这种表层描述，而要一路追到上游：它是谁引入的、上游后来修没修、调用方依赖什么语义、代码库惯例是什么、能不能反证"故意为之"，最后按根因决定迁移动作。

为什么值得花这个力气：抽样实证的结论是——大多数 XD 的 bugfix 补丁，UE5 上游已经自己修好了（等价重写、直接删除、或换成更完整的实现）。
这类宏不需要重新移植，直接从 UE4 fork 和迁移清单里划掉即可。已确认 27 个宏的根因，其中 24 个属于「上游已修 → 可直接删除」。

标签说明

颜色规则：覆盖度=红绿灯 · 工程化=蓝色系 · 侵入=紫色系 · 处置=中性灰。
分级方式：工程化/侵入用「实心 → 底色 → 描边 → 虚线」四级形态表示程度递进（实心最强）。

落地位置（工程化可行性）

可工程化放项目/插件/配置即可，不动引擎
需接入点引擎留少量 Hook，逻辑在工程侧
引擎内实现必须改引擎核心
—处置=删除的行不适用（已删除/不迁移）

引擎改动方式

L0 无需改引擎纯工程/插件/配置即可（对应「可工程化」）
L0 引擎内补丁需改引擎源码，但不必新增扩展点（对应「引擎内实现」）
L1 仅加接入点引擎只需暴露 Delegate / Interface / CVar 等扩展点
L2 结构性改动枚举 slot / 新 Pass / schema 字段
L3 深度侵入核心结构/生命周期/序列化，慎入

迁移处置

删除UE5 已覆盖，直接删
常开补丁确认的 bugfix，作为 fork 常开补丁
配置化改为 CVar / ini / DeviceProfile / 命令行
插件化迁到项目模块 / 编辑器插件
接入点引擎只留 Hook，逻辑在插件
移植代码保留，适配后移植
保留引擎深度绑定，暂留并登记 Feature Card
