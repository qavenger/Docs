结论先行：代码级草案在交付前由另一个独立 Agent 逐宏实证复核——打开 UE5 源码核对行号、函数、以及草案里 after 代码引用的类/函数/枚举是否真实存在。目前已审核 185 个宏：通过 94 个、判定需修正 88 个，共采纳 171 处字段修正，其中 51 个宏存在高风险问题（会导致编译不过或功能错误）。

为什么要单独审核：草案是给技术人员直接照着改代码的，一处编造的行号或一个 UE5 里不存在的 API，就会让开发在错误方向上浪费半天。
审核不是复述，而是去源码里验证：每条问题都必须带证据（文件:行），修正必须给出可直接替换的内容。

高频问题类型（已反哺生成规范）

审核暴露的问题有明显模式，已写回生成侧的作业规范（DRAFT_BRIEF.md「常见错误自查清单」），后续批次会先自查再提交：

  1. after 引用 UE5 不存在的符号：类 / 函数 / 枚举 / CVar / 宏没在 UE5 里核实就写进代码（例：EMaterialShadingModel::MSM_CustomUnlit 在 UE5 已移除；SetTranslucentPriority 实际叫 SetTranslucentSortPriority 且签名不同）。
  2. 编造宏名或文件：宏名前缀写反（XD_FIX_BUG_* 写成 XD_BUG_FIX_*）；目标文件在 UE5 已不存在（Particles/ 下已无 ParticleSystemRender.cpp 等，逻辑迁到 ParticleSystemSceneProxy）。
  3. 合并 #if/#else 时丢分支：只保留宏开启分支，丢掉 #else 的原行为；或在函数末尾提前 return，抹掉其它返回路径（例：Ribbon 的 DynamicData 判定会被永久置 false）。
  4. 循环边界错、造成泄漏：删除类循环没有从 Num-1 递减，或删完又调用 SetNumZeroed(N) 把仍在使用的元素截断。
  5. after 只有注释没有代码：写"同 UE4 写法"这类占位，无法实施。
  6. steps 之间守卫宏不一致：声明点用 #if XD_XXX、调用点用 #if WITH_EDITOR，宏为 0 时会编译/链接失败。
  7. 插入点落在错误分支：写"在 X.cpp:686 之后插入"，但那行处在 if (DeviceProfile…) 嵌套里。
