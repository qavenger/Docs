结论先行：549 个定制宏中，103 个 UE5.8 已原生覆盖（可直接丢弃）、215 个被部分覆盖（保留差异部分）、188 个需要迁移；其中 212 个可以完全工程化、129 个只需引擎留接入点；引擎改动方面，366 个无需新增扩展点（L0：不动引擎或引擎内自包含补丁），12 个属于深度侵入（须逐个评估）。

1. 这份分析解决什么问题

项目要从深度定制的 UE4.26 迁移到 UE5.8.2。之前的文档回答了「每个宏是做什么的」，这份文档回答迁移期的三个决策问题：

  1. 能不能不迁？——UE5.8 是否已经有等价能力（丢掉的优先），避免把 UE4 的技术债原样搬到 UE5。
  2. 能不能搬走？——与引擎不强绑定的部分，放进项目工程/插件实现，让引擎 fork 变薄。
  3. 必须留在引擎里的，最少留什么？——只留稳定接入点（Hook/Delegate/Interface/ModularFeature/Config），完整逻辑放工程侧。

判定标准与分层思路来自团队的《引擎二次开发治理与开发思路》：宏只做编译期裁剪，Hook/Plugin 做扩展与实现，CVar/Config 做策略，CustomVersion 做兼容。

4. 迁移路线（建议）

  1. 先丢（第 1 周）：把 UE5 已覆盖的宏标记删除，同步删除 UE4 fork 里对应代码，避免带着旧债升级。典型：Mimalloc、UE5 已上游的 Slate/Sequencer/网络修复、GLES 专属 workaround（如确认 UE5 不用）。
  2. 再搬（第 2–4 周）：把工具类、项目配置类、平台策略类迁到 Project/Plugin/Config。收益高、风险低（对应 disposition=plugin/config）。
  3. 后建 Hook（第 4–8 周）：为必须保留的能力设计最小接入点：渲染用 ISceneViewExtension、材质用 Shader Include Hook、资产管线用 Delegate/ModularFeature、编辑器用 ToolMenus/插件。
  4. 最后处理深度绑定项（持续）：反射 schema、Shader permutation、Cook/DDC、RHI 内部改动，按 Feature Card 逐个评估，能不进主干就不进。
⚠ 迁移期不要沿用「宏 = 万能开关」的做法。新改动一律先问：能不能做成插件？不能，才设计引擎 hook；再不能，才改引擎代码，并登记 Feature Card 与 CI 验证矩阵（见 最小侵入与接入点）。

7. 质量审核

本文档的迁移结论经过 6 组独立 Agent 抽样复核（复核样本累计约 478 个，含重复抽样），共提出并采纳 69 项修正，修正已合并进全量矩阵与各参考页条目。复核重点：UE5 覆盖证据是否真实、处置与侵入等级是否矛盾、高风险项（反射/资产/Shader/Cook）是否被低估。
