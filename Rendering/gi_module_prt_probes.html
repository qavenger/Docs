PRT · 预计算辐射传输 · 用一个能走进去的房间来讲

房间提前写好“收光清单”，太阳一动，马上就知道每个角落有多亮

这一页只讲一个方法：PRT（Precomputed Radiance Transfer，预计算辐射传输）。我们用同一个康奈尔盒房间——你可以用 WASD 走进去、鼠标环视、点选盒子并搬动它。先用能拖动的箭头把“方向”和“点乘”弄明白，再看 PRT 怎样把“房间怎么传光”提前算好，让换光变得几乎不花钱。

01 / 一句话看懂

PRT 就是给房间提前写好一张“收光清单”

先记住这个画面，后面所有公式都只是把它写清楚而已。

想象每一小块墙面、地板都提前填了一张表：「如果光从这个方向来，我能收到多少？那个方向被别的东西挡住了吗？」 这张表只跟房间长什么样有关，跟今天太阳在哪没关系。
所以太阳一移动，我们不用重新测量房间——只要把新的阳光“套进”每张表，立刻就能算出每个点有多亮。这就是 PRT： 慢的部分（房间怎么传光）提前算好存起来，快的部分（今天的光）每帧现算。

提前算好的（慢，只算一次）

房间的形状决定的东西：每个点朝哪、能看见天空的哪些方向、哪些方向被盒子或墙挡住、光在墙之间怎么反弹。几何不变，它就不用重算。

每帧现算的（快）

今天的天空/太阳长什么样——用 9 个数字概括。把这 9 个数字和每个点的“清单”一乘一加，就得到这一帧的亮度。

什么时候必须重来

只有几何变了（搬动盒子、改变房型）才需要重写清单。光变、颜色变、方向变，都只是换那 9 个数字，便宜得很。

02 / 2D 向量热身

亮度 = 能不能看见 × 光和法线有多“对齐”

PRT 里每张清单的两个关键词是点乘和可见性。这两个都能在 2D 里用箭头玩明白——全程只用向量，不背角度公式。拖动太阳 ☀ 和蓝色法线试试。

拖动看数字变化。
怎么读：法线 n 是“这个面朝哪”，阳光方向 s 是“光从哪来”。 两个箭头越指向同一边，点乘 n·s 越大、越亮；背着光就 ≤0，直接算 0。 如果中间有墙挡住，能看见=0，再亮也没用。
这就是清单里的一格：对某个方向，先问“看得见吗”（可见性 0/1），再问“有多对齐”（max(0, n·s)）。把天空所有方向的这两项加起来，就是这个点收到的总光。PRT 只是把“所有方向加起来”的结果提前存好。
03 / 用几个数字装下整片天空

不用存整张天空照片，存几个数字就够了

天空的每个方向亮度都不同。如果每个方向都单独记，数据太多。聪明的办法：用少数几个数字，概括“整体多亮、上面比下面亮多少、左边比右边亮多少……”。这套数字在 3D 里叫球谐（SH）；这里用它的 2D 版本先找感觉。拖动太阳，拉动滑块加数字。

拖太阳、拉滑块。
要点：数字越多，重建（紫色）越贴近真实天空（虚线），但也越贵。 3D 里常用 9 个数字就够表达柔和的环境光——这正是本页 3D 房间用的精度。
（这 9 个数字在专业书里写作“球谐到第 2 层”，记号 l=2；名字不重要，记住是“9 个数字”就行。）
为什么这招对 PRT 特别关键：每个点的“收光清单”也用同一套 9 个数字表示。 于是“这一帧天空的 9 个数字” × “这个点的 9 个数字”一乘一加，就是这个点的亮度——换光只是换 9 个数字，快到可以每帧做。想深入 SH 的旋转和推导，见 球谐 SH 模块。
04 / 走进房间（主实验）

康奈尔盒：走进去，动太阳，搬盒子

这是本页的核心。右上角的悬浮控制台管着太阳方向、相机和选中的物体，可以拖到任何地方。操作方式和游戏引擎一样：

相机WASD + 鼠标点一下画面，用 W/A/S/D 前后左右走，Q/E 上下，按住左键拖动环视，滚轮前进后退。
选择 + 变换左键点盒子选中后出现三色箭头 gizmo（红X/绿Y/蓝Z）。在控制台切换移动/旋转/缩放，拖动对应轴。
光照拖太阳方向控制台里改太阳的水平角（左右转）和仰角（上下抬）——两个滑块合起来就定出一个指向太阳的 3D 方向箭头，阴影和色渗实时更新。

05 / 把三步对上公式和真实代码

你刚才看到的，就是这三段代码在跑

现在把体验对上数学。下面每一块都有“直觉 / 公式 / 伪代码 / 实际代码”标签，实际代码就是本页 3D 房间真正执行的 gi_prt_lab.js，没有另写一套。

对每个表面点，向它头顶的半球撒很多条射线。射线飞出开口看到天空 → 把这个方向的 max(0,n·ω) 记进清单（用 9 个 SH 数字存）；射线撞到别的面 → 这个方向的直射天光被挡住，但它会在“反弹”那步派上用场。这一步只跟几何有关，所以叫预计算。

Tj(x) = Σ方向 ω 看得见(x,ω) · max(0, n·ω) · Yj(ω) · Δω
（j = 0..8，就是那 9 个 SH 数字；Δω = 把头顶半球切成很多小份，每条射线管一小份天空，Δω 就是“这一小份有多大”，乘上它才能把所有方向公平地加起来）
对每个表面点 x：
  清单 T = 9 个 0
  对头顶半球的每个方向 ω：
    余弦 = max(0, dot(法线, ω))
    if 余弦 <= 0: 跳过
    if 射线(x → ω) 撞到别的面: 跳过   // 天空被挡住
    T += 余弦 · SH9(ω) · Δω          // 记进清单
  存好 T
directTransfer(pos, nrm, occ, ignoreObj) {
  const basis = basisFromNormal(nrm);
  const out = new Float32Array(9);
  const w = (2 * Math.PI) / this.hemi.length;   // 每条射线代表的立体角
  const origin = V.add(pos, V.scale(nrm, 0.012));
  for (const h of this.hemi) {
    const dir = localToWorld(basis, h);
    const cosine = h[2];                          // 和法线的对齐程度
    if (cosine <= 0) continue;
    if (this.trace(origin, dir, occ, ignoreObj)) continue; // 被挡 → 看不到天空
    const Y = sh9(dir);
    for (let j = 0; j < 9; j++) out[j] += cosine * Y[j] * w;
  }
  return out;
}

康奈尔盒最好看的是红墙、绿墙把颜色“染”到白盒子上。这是因为光先照到彩色墙，再反弹一次到盒子。做法：每个点去收集它能看见的那些墙面小块（patch）的光，乘上那块墙的颜色再加进自己的清单。红墙的 patch 就带来红色。

T(x) += Σ可见的墙块 p 形状因子(x,p) · 墙块颜色/π · T直射(p)
形状因子 = 两块小面“互相照得到多少”的比例——正对、离得近就大，斜着、离得远就小：cosθx·cosθp / (π·距离²) · 面积（分母的距离² = 越远越暗）
对每个点 x：
  对每个墙面小块 p：
    if p 背对 x 或 x 看不见 p: 跳过
    形状因子 = cos_x · cos_p / (π·距离²) · p的面积
    // 把 p 的“直射清单”按 p 的颜色染色后加进来
    T(x) += 形状因子 · p颜色/π · T直射(p)
for (const patch of this.patches) {
  if (patch.obj === obj) continue;
  const toP = V.sub(patch.pos, pos);
  const dist = Math.sqrt(V.dot(toP, toP));
  const dir  = V.scale(toP, 1 / dist);
  const cosR = V.dot(nrm, dir);        if (cosR <= 0) continue;
  const cosP = -V.dot(patch.nrm, dir); if (cosP <= 0) continue;  // 墙块背对
  if (this.trace(origin, dir, occ, obj, dist - 0.02)) continue;  // 被挡
  // 形状因子（已含一个 /π = 墙块出射的 /π）
  const ff = (cosR * cosP) / (Math.PI * dist * dist) * patch.area;
  const k  = ff * this.bounceGain;   // bounceGain 默认 1.0 = 物理单次反弹
  for (let j = 0; j < 9; j++) {
    const src = patch.m0[j] * k;
    M[i*27 + j*3    ] += src * patch.albedo[0];   // 红通道带上墙块的红
    M[i*27 + j*3 + 1] += src * patch.albedo[1];
    M[i*27 + j*3 + 2] += src * patch.albedo[2];
  }
}

清单存好后，运行时超简单：把这一帧天空投影成 9 个数字 L，再对每个点做“清单 · L”一乘一加，乘上这个点自己的颜色，就是屏幕上的亮度。太阳一转，只有 L 变——所以便宜。

Lj = Σ方向 ω 天空(ω) · Yj(ω) · Δω　（把今天的天空变成 9 个数字）
亮度(x) = 颜色(x)/π · Σj=0..8 Tj(x) · Lj
每帧（太阳/天空变了就做）：
  L = 把当前天空投影成 9 个 SH 数字
  对每个点 x：
    e = 清单T(x) 点乘 L        // 一乘一加，9 项
    屏幕颜色(x) = 颜色(x)/π · e
  // 几何没变，完全不碰清单 T
relight() {
  const L = this.projectEnvironment();      // 天空 → 9 个数字（每通道）
  for (const obj of this.controller.objects) {
    const M = this.transfers.get(obj.id);   // 这个物体每个点的清单
    const out = new Float32Array(obj.vertexCount * 3);
    const a = obj.albedo, invPi = 1 / Math.PI;
    for (let i = 0; i < obj.vertexCount; i++) {
      let r = 0, g = 0, b = 0;
      for (let j = 0; j < 9; j++) {          // 清单 · L，9 项
        r += M[i*27 + j*3    ] * L[0][j];
        g += M[i*27 + j*3 + 1] * L[1][j];
        b += M[i*27 + j*3 + 2] * L[2][j];
      }
      out[i*3]   = Math.max(0, a[0]*invPi*r); // 亮度不为负
      out[i*3+1] = Math.max(0, a[1]*invPi*g);
      out[i*3+2] = Math.max(0, a[2]*invPi*b);
    }
    obj.setRadiance(out);                    // 送去 GPU 显示
  }
}
那 9 个 SH 数字怎么来的？就是把方向 (x,y,z) 代进 9 个固定的小多项式。这是全篇唯一“看起来吓人”的公式，但其实只是查表： 
sh9(d) {                       // d = 单位方向 (x, y, z)
  const x = d[0], y = d[1], z = d[2];
  return [
    0.282095,                  // l0：整体亮度
    0.488603 * y,              // l1：上下、左右、前后的偏亮
    0.488603 * z,
    0.488603 * x,
    1.092548 * x * y,          // l2：更细的方向变化
    1.092548 * y * z,
    0.315392 * (3*z*z - 1),
    1.092548 * x * z,
    0.546274 * (x*x - y*y),
  ];
}
06 / PRT 清单可以存在哪

清单存哪里，就有了不同的名字

“预计算传输”是同一个思想，只是清单挂在不同东西上。本页 3D 房间用的是最直观的一种：把清单存在每个表面顶点上。

存在表面上（本页用的）

清单挂在每个顶点 / 纹理像素上，有固定法线，天然带“可见性 × 余弦”。经典 Sloan PRT 就是这种。

存在空间探针上

清单挂在空间里的一格格探针上，动态物体走过去做插值。适合会动的角色。

都用 SH 系数

不管挂哪，清单本身几乎都用 SH 系数存——就是第 3 节那几个数字。换光只做系数点乘。

诚实说明：“PRT Probe”不是唯一标准术语。本页把清单存在表面接收点上（有固定法线），所以更接近 lightmap（光照贴图）/顶点 PRT，而不是能朝任意方向查询的通用体积探针。换成体积探针时，探针里存什么、怎么插值要另外定义。
07 / 和“每帧从头算”比

为什么不干脆每帧重新追光？

你完全可以每帧重新追踪所有光线（那是路径追踪/实时 GI 的路子）。PRT 的取舍是：用“只能改光、不能随便改几何”换来“换光几乎免费”。

PRT 擅长

  • 静态场景 + 会变的天光/环境光（白天黑夜、转 HDRI —— 预先拍好的全景天空照片）。
  • 柔和的漫反射间接光、自阴影、颜色反弹，全部离线烘好。
  • 运行时只做 9 项点乘，手机也扛得住。

PRT 的代价

  • 几何一变就要重烘（本页搬盒子时你看到的“几十 ms”）。
  • 低阶 SH 只擅长柔和的光，尖锐高光、清晰镜面存不下。
  • 清单要占内存；用的数字越多越准，也越占。
和 Irradiance Probe 的区别（一句话）：Irradiance Probe 存的是“上次那盏灯照出来的答案”，换光要重烘； PRT 存的是“这个房间怎么传光”，换光只换那 9 个数字。本页房间就是后者——转太阳不重烘，就是证据。
08 / 边界与去处

这个 Demo 做了什么、没做什么

做到了

漫反射、9 个 SH 数字、自阴影可见性、1 次漫反射反弹色渗（物理量级，用粗墙块近似形状因子）、可旋转的天空/太阳环境光、真实的“动光不重烘 / 动几何才重烘”。核心数学——SH 可见性传输（transfer）× 每帧环境 SH——与 RenderGraph 原生 prt 方案同源；本页额外加了教学用的一次反弹，规模也更小。

没有做

镜面/光泽 PRT、运行时多次反弹、近距离点光源的 PRT、SH 旋转的完整推导（见 SH 模块）、体积探针插值。这些都是清晰的下一步，不在本页范围。

想看这套思想在真实双后端管线（D3D12 / Vulkan）里怎么落地、怎么按 RenderGraph 组织 pass，去 RenderGraph GI 工作台 的 prt 方案。
