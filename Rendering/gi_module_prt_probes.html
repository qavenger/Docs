01 / one question first

移动灯以后，缓存要不要重建？

这是区分 Irradiance Probe 和 PRT 最简单、也最不容易错的方法。二者最后都可能给出 probe irradiance，甚至都可能用 SH；不同的是缓存的语义。

Irradiance Probe：缓存“上次的答案”

烘焙时，墙面哪些位置亮、地面 Probe 收到多少光，已经被积分成最终结果。移动灯后旧值不会自己改变；必须重新烘焙、切换预制场景，或像 DDGI 那样重新追踪并逐帧更新。

对应关系已并入 运行时 transport 可切换工作台 的“公式 / 代值 / 伪代码 / 实际代码”四个标签。

PRT：缓存“固定场景怎样传光”

离线只保存墙面 brick 到 Probe 的固定权重 W。运行时先求当前灯下每个 brick 的 radiance R，再执行 W·R。灯变了只更新 R；几何不变时 W 无需重建。

完整的 W·R 与 baked answer 对照已并入 运行时 transport 可切换工作台，不再在这里重复一块孤立公式。

动态的是

灯的位置、颜色、强度，以及它们让静态 surfels/bricks 产生的本帧 radiance。

预计算的是

brick 与 receiver 之间由距离、两个余弦、面积和可见性决定的几何 transport。brick 的静态反照率在运行时 relight 阶段写进 R，不在本 Demo 的 W 中重复保存。

输出仍然是

本帧 Probe irradiance。也就是说，“PRT Probe 最终产出 irradiance”并不等于“缓存本身就是 Irradiance Probe”。

术语边界：“PRT Probe”不是定义唯一的标准术语。本页 3D Demo 采用《The Division》Radiance Transfer Probes 的教学化一跳结构：动态重光照 bricks，再用预计算权重生成 Probe Irradiance。经典 Sloan PRT 常把 transfer 直接绑定到 vertex / texel，而不一定有空间 Probe。
本 Demo 的 120 个点严格说是 surface receivers：每个点绑定地面位置与朝上的表面法线，所以 W 里才有 cosθ_receiver；它们更接近 lightmap texel / vertex receiver，不是能向任意方向查询的通用体积 Irradiance Probe。本文保留“Probe”标签，是为了直观对比“旧 irradiance answer”与“当前 transfer answer”。生产中的 Radiance Transfer Probe 可以改存方向分布、SH 或局部重建系数；那时 probe payload 与插值规则必须另外定义。

04 / three concrete PRT payloads

Surface、Volume、SH PRT：共同点是 transfer，不是“都叫 Probe”

下面三个实验完全独立。每个实验先生成只依赖静态几何的 transfer，再让显式光源变化并在运行时点积。你可以直接看到“哪些数组固定、哪些数组每帧更新”。

Surface PRT

transfer 绑定 vertex / texel / surface receiver；有固定法线，天然出现 visibility × cosine。

缓存：T[surface, direction]

Volume / Probe-grid PRT

transfer 输出到空间 probe，再为动态接收者做网格插值；payload 可以是 RGB、方向 bins 或 SH。

缓存：W[probe, brick]

SH PRT

把入射光和 transfer 投影到同一组 SH 基。运行时不采方向积分，只做系数 dot。

缓存：Tlm[receiver]

function buildSurfaceTransfer(receiver, normal, useOccluder) {
  return surfaceDirections.map((direction) => {
    const cosine = Math.max(0, dot2(normal, direction));
    const visible = !useOccluder ||
      !rayHitsStaticBoard(receiver, direction);
    return visible ? cosine * surfaceSolidAngle : 0;
  });
}

function evaluateSurfacePrt(transfer, receiver, lightPosition) {
  const toLight = subtract2(lightPosition, receiver);
  const distance2 = Math.max(0.02, dot2(toLight, toLight));
  const direction = normalize2(toLight);
  const lighting = binDirectionalImpulse(direction, 2 / distance2);
  return dotArray(transfer, lighting);
}

function evaluateVolumePrt(lightPosition, queryPosition) {
  const brickRadiance = volumeBricks.map((brick) =>
    shadeBrick(brick, lightPosition)
  );
  const probeIrradiance = volumeProbes.map((probe) =>
    dotArray(probe.transport, brickRadiance)
  );
  const neighbors = findFourGridNeighbors(queryPosition);
  return neighbors.reduce(
    (sum, neighbor) =>
      sum + neighbor.weight * probeIrradiance[neighbor.index],
    0
  );
}

function realSh9(direction) {
  const [x, y, z] = direction;
  return [
    0.282095,
    0.488603 * y,
    0.488603 * z,
    0.488603 * x,
    1.092548 * x * y,
    1.092548 * y * z,
    0.315392 * (3 * z * z - 1),
    1.092548 * x * z,
    0.546274 * (x * x - y * y)
  ];
}

function evaluateShPrt(transferSh, lightDirection, coefficientCount) {
  const lightingSh = realSh9(lightDirection);
  let irradiance = 0;
  for (let index = 0; index < coefficientCount; index += 1) {
    irradiance += transferSh[index] * lightingSh[index];
  }
  return irradiance;
}

现在再看公式：每一项都能在 3D 场景里指出来

运行时：灯先照亮墙面 brick

Demo 的 每次滑杆变化都会执行。这里没有历史，也没有预烘焙灯光。

离线：固定几何决定 W

R 已经是墙面出射 radiance（albedo/π × incident），所以 radiance→irradiance 的几何项不再除 π。Demo 的 只在初始化时执行。黄色连线显示选中 receiver 的最大 W。

运行时：矩阵行与当前 radiance 点积

是一个真实的 matrix-vector multiply。场景很小，教学版用 CPU 便于查看；GPU 版见第 ⑥ 节。

左侧为什么不动？

左侧保存的是上次调用 时的最终 RGB 数组。移动灯不会再经过 W，因此它只能保持旧答案。

当前 brick radiance： Rᵦ = albedoᵦ · lightColor · [5.6·max(0,nᵦ·l)/(1+0.12·distance²)] / π + 0.006·albedoᵦ 固定 transport： Wₚ,ᵦ = visibility · cosθ_receiver · cosθ_brick · area_brick / distance² 当前 PRT 输出： Eₚ.rgb = Σᵦ Wₚ,ᵦ · Rᵦ.rgb 普通烘焙缓存： bakedEₚ = Eₚ(light at bake time)

取 cos_receiver=0.80、cos_brick=0.60、area=0.04、distance²=0.25 且可见，则 W=0.0768。

再取 brick albedo=0.60、灯通道值 1.00、n·l=0.75、distance²=4.00，本页实际式得到 power=2.83784、R=0.545587；若只有这一条连接，则 E=0.0768×0.545587=0.041901。灯移动后 R 与 E 同帧改变，而 bakedE 仍保留 0.041901，直到再次烘焙。

runtime each frame:
  R = shadeWallBricks(staticBricks, currentLight)
  currentE = matrixVectorMultiply(W, R)

when user explicitly rebakes:
  bakedE = copy(currentE)

06 / no mystery helpers

核心算法与渲染依赖，都能追到实际函数体

下面不是“类似代码”。3D Demo 直接调用这些函数；展开源码会按“transport / 小型数学 helper / WebGL2 可视化”三组列出浏览器当前执行的函数体。较简单的函数也可悬停名称查看输入、输出与算法。

segmentIntersectsAabb(a,b,min,max)

真实 slab test。把线段写成 a+t(b−a)，逐轴收紧 t∈[0,1]；区间为空即 miss。用于判断 brick→Probe 是否被静态箱子挡住。

buildTransferMatrix(receivers,bricks,aabb)

生成 Float32Array，行是 receiver，列是 brick。计算两个余弦、距离平方、brick 面积和 visibility。

shadeWallBricks(bricks,lightPosition,lightRgb)

计算当前帧 brick radiance。只依赖动态灯和静态 brick 属性；每次移动灯都会执行。

evaluateTransfer(W,R,receiverCount,brickCount)

计算 E=W·R。R 与 E 都是 RGB，所以对每个 W 标量分别累加三通道。

createProgram(gl,vsSource,fsSource)

编译两个真实 GLSL ES 3.00 shader，检查 COMPILE_STATUS / LINK_STATUS，失败时抛出浏览器给出的日志。

renderScene(viewport,mode)

设置 viewport/scissor、上传 view-projection 矩阵，依次绘制房间、bricks、地面结果、灯、Probe 与传输线。它调用的矩阵、mesh 更新与 draw helper 也都收录在源码包。

function buildTransferMatrix(receiverList, brickList, occluderAabb) {
  const matrix = new Float32Array(receiverList.length * brickList.length);
  for (let receiverIndex = 0; receiverIndex < receiverList.length; receiverIndex += 1) {
    const receiver = receiverList[receiverIndex];
    for (let brickIndex = 0; brickIndex < brickList.length; brickIndex += 1) {
      const brick = brickList[brickIndex];
      const receiverToBrick = sub(brick.position, receiver.position);
      const distanceSquared = Math.max(0.001, dot(receiverToBrick, receiverToBrick));
      const direction = norm(receiverToBrick);
      const receiverCosine = Math.max(0, dot(receiver.normal, direction));
      const brickCosine = Math.max(0, dot(brick.normal, direction.map((value) => -value)));
      const blocked = segmentIntersectsAabb(
        receiver.position,
        brick.position,
        occluderAabb.min,
        occluderAabb.max
      );
      matrix[receiverIndex * brickList.length + brickIndex] = blocked
        ? 0
        : receiverCosine * brickCosine * brick.area / distanceSquared;
    }
  }
  return matrix;
}

function shadeWallBricks(brickList, lightPosition, lightRgb) {
  const radiance = new Float32Array(brickList.length * 3);
  for (let brickIndex = 0; brickIndex < brickList.length; brickIndex += 1) {
    const brick = brickList[brickIndex];
    const toLight = sub(lightPosition, brick.position);
    const distanceSquared = Math.max(0.1, dot(toLight, toLight));
    const receiverCosine = Math.max(0, dot(brick.normal, norm(toLight)));
    const power = 5.6 * receiverCosine / (1 + 0.12 * distanceSquared);
    for (let channel = 0; channel < 3; channel += 1) {
      radiance[brickIndex * 3 + channel] =
        brick.albedo[channel] * lightRgb[channel] * power / Math.PI +
        0.006 * brick.albedo[channel];
    }
  }
  return radiance;
}

function evaluateTransfer(matrix, radiance, receiverCount, brickCount) {
  const irradiance = new Float32Array(receiverCount * 3);
  for (let receiverIndex = 0; receiverIndex < receiverCount; receiverIndex += 1) {
    for (let brickIndex = 0; brickIndex < brickCount; brickIndex += 1) {
      const weight = matrix[receiverIndex * brickCount + brickIndex];
      for (let channel = 0; channel < 3; channel += 1) {
        irradiance[receiverIndex * 3 + channel] +=
          weight * radiance[brickIndex * 3 + channel];
      }
    }
  }
  return irradiance;
}

07 / webgpu, d3d12, vulkan

为什么主 Demo 用 WebGL2，生产乘法可以进 compute shader

HTML 需要双击即可离线运行，而 WebGPU 的浏览器可用性和安全上下文仍需检测。因此本页用 WebGL2 负责可移植 3D 显示，并把小矩阵乘保留为可逐行阅读的 CPU 代码。真正的大规模 receiver×brick 运算可直接映射到 WebGPU compute；浏览器实现再映射到 Windows D3D12、Linux/Android Vulkan 或 macOS Metal。

WGSL compute 核心摘录（每个 invocation 处理一个 receiver）

本页没有创建 GPUDevice、compute pipeline 或提交 dispatch；因此下面是与 CPU 矩阵乘等价的生产迁移摘录，不标成“已在此页执行”。

struct Params { receiverCount:u32, brickCount:u32, _pad0:u32, _pad1:u32 }
@group(0) @binding(0) var<storage, read> W : array<f32>;
@group(0) @binding(1) var<storage, read> R : array<vec4f>;
@group(0) @binding(2) var<storage, read_write> E : array<vec4f>;
@group(0) @binding(3) var<uniform> params : Params;

@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) gid:vec3u) {
  let p=gid.x;
  if (p>=params.receiverCount) { return; }
  var sum=vec3f(0.0);
  for (var b=0u; b<params.brickCount; b++) {
    sum += W[p*params.brickCount+b] * R[b].rgb;
  }
  E[p]=vec4f(sum,1.0);
}

R/E 使用 vec4f 是为了满足 storage buffer 中自然的 16-byte 对齐。若接入 WebGPU，dispatch 数量应为 ceil(receiverCount/64)；本页当前实际执行路径仍是 CPU dot + WebGL2 显示。

08 / advantages and limits

什么时候它很合适，什么时候必须换方案？

优势

  • 动态灯同帧响应：核心一跳只读当前 R 与固定 W。
  • 无采样噪声和拖尾：没有 history rejection 或 hysteresis。
  • 复杂静态传输可离线：生产版可把更多遮挡与反弹烘入 W/T。
  • 动态接收者友好：角色可查询本帧 Probe Irradiance。
  • 成本可预测：主要是 relight、稀疏矩阵乘、插值与带宽。

限制

  • 几何变化会让 W 失效：移动墙、开门、破坏场景需要新 transport。
  • 输出通常低频 diffuse：锐利间接阴影和镜面另走反射/RT 路径。
  • 大量局部灯仍要 culling：重光照所有 surfels 不是免费。
  • 存储随连接数增长：生产实现需 bricks、稀疏索引、压缩和流送。
  • 可选多跳反馈会重新引入时序：一跳无历史不代表任意 bounce 都无历史。
