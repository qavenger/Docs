引擎二次开发治理与开发思路

面向长期维护自定义 UE 分支的侵入式修改管理、扩展点设计、风险控制与协作流程。

核心目标：不要只追求“宏关闭后等于原版源码”。更重要的是让每个引擎改动有清晰边界、明确 owner、可测试、可回滚、可升级。

1. 问题背景

引擎二次开发通常会从局部修复开始，逐渐演变成大量功能宏、项目特化逻辑、shader 分支、编辑器适配和资产 schema 变化。 如果缺少治理方式，几年后最大的问题不是“改了多少”，而是“没人知道这些改动的边界、依赖和关闭后的预期行为”。

当前常见做法是使用类似 XD_RENDERING_XXX、XD_OPT_XXX 的编译宏包裹修改。这个方案有价值，但它只能解决一部分问题。 当改动涉及 UCLASS、UPROPERTY、材质系统、shader permutation、Cook、DDC、序列化、MeshPass、渲染线程生命周期时，单纯靠宏会变得脆弱。

2. 管理目标

目标 说明
侵入边界小 Engine 源码里尽量只保留稳定扩展点，具体业务逻辑放到插件或独立模块。
功能归属清楚 每个 Feature 有 owner、文档、改动范围、依赖关系和回滚方式。
关闭行为可预期 明确关闭后是 fallback、no-op、隐藏 UI、还是不支持关闭。
升级成本可控 UE 版本升级时能快速判断冲突来自哪个 Feature。
副作用可验证 至少覆盖编译、shader 编译、Cook、资产加载、平台差异和关键运行路径。

3. 宏系统的正确定位

宏不是坏方案，但它应该是治理体系的一部分，而不是唯一手段。

适合用宏 不适合只靠宏
纯 C++ 实现分支 UCLASS / UPROPERTY / UFUNCTION 反射 schema
平台编译差异 资产序列化格式变化
性能敏感路径裁剪 材质 ShadingModel、MaterialProperty、Blueprint API
shader permutation define 需要运行时灰度、调试或配置切换的行为
第三方 SDK 是否参与编译 大规模渲染管线或编辑器工作流改造
原则：宏负责“编译期裁剪”，Hook / Plugin / CVar / Config / CustomVersion 负责“扩展、运行时策略和兼容性”。

4. 推荐分层架构

Engine Stable Hook Layer
  少量稳定扩展点、通用接口、schema 兼容层

Feature Plugin / Module Layer
  具体功能实现、shader、工具、editor UI、策略代码

Project Policy Layer
  平台开关、配置、CVar、Cook 策略、发布策略
层级 应该放什么 不应该放什么
Engine Stable Hook Layer 通用扩展接口、少量枚举 slot、渲染阶段 hook、材质编译桥、shader include hook 项目专用业务逻辑、大量 ifdef 分支、临时实验代码
Feature Plugin / Module Layer 功能主体、算法实现、shader 文件、editor 工具、调试视图 必须改变核心对象内存布局的内容
Project Policy Layer 平台启用规则、CVar 默认值、ini 配置、Cook 和发布策略 底层引擎流程硬编码

5. Hook 化思路

Hook 的思想类似引擎 delegate 或 extension point：引擎主流程在关键阶段调用扩展点，具体功能由插件注册。 

// Engine
FRenderExtensionRegistry::Get().RenderAfterBasePass(GraphBuilder, View);

// Plugin
FRenderExtensionRegistry::Get().RegisterExtension(MakeShared());
形式 适合场景 例子
Interface 复杂状态、生命周期明确、多个回调函数 ISceneViewExtension
Modular Feature 多个插件注册同一类能力，引擎枚举所有实现 IModularFeatures
Delegate 轻量事件，不需要复杂状态 Editor menu extension、资产事件
Shader Include Hook 插件提供 shader 文件，引擎保留虚拟路径 include 点 AddShaderSourceDirectoryMapping
FeatureMask 多个功能共享一条通用扩展数据通道 Light / Primitive / Material 自定义功能位

6. 反射与资产 Schema 策略

涉及 UHT 的改动必须单独看待。它们影响 generated code、Blueprint、序列化、Cook 和资产兼容性，不能用“宏关掉就没了”的心态处理。

场景 推荐做法
新增 UPROPERTY 尽量保持字段长期存在，关闭功能时隐藏 UI 或 no-op，不随宏消失。
新增 UFUNCTION 保持 API 稳定，功能关闭时返回默认结果或提示不可用。
资产序列化变化 使用 custom version / migration，不依赖宏切换处理兼容。
项目特化字段 优先放插件组件、扩展对象、FeatureMask 或 metadata，少往核心类塞专用字段。
编辑器 UI 通过 detail customization、metadata、config 控制显示，而不是改变 schema。
高风险信号：如果一个宏包裹了 UCLASS、UPROPERTY、UENUM、材质 ShadingModel、序列化字段，就应该进入 Feature 风险清单，而不是当作普通编译开关。

7. Shader 与渲染管线策略

Shader 和 Renderer 改动通常会同时影响 C++、HLSL、DDC、Cook、移动端预览和多平台差异，需要建立单独规则。

改动类型 推荐策略
新增 shader 文件 优先放插件 Shaders/，用 AddShaderSourceDirectoryMapping 映射虚拟路径。
引擎 shader 主文件改动 只保留薄 include hook，具体实现放插件或独立 include。
新增 permutation 明确 DDC key、shader version、平台范围和编译数量。
新增 MeshPass / RDG Pass 优先通过 renderer extension 注册，必须改 enum 时保持 slot 稳定。
移动端/PC 差异 避免两套算法长期分叉；能统一 LightGrid、IBL、BRDF 的尽量统一。

8. Feature 分类

所有引擎改动都应先分类，不同类型使用不同治理方式。

类型 例子 治理方式
A纯实现替换 性能优化、bug fix、算法分支 宏 + 单元测试 + 性能数据
B引擎扩展点 渲染阶段 hook、资源构建 hook、材质编译 hook Interface / Delegate / Modular Feature
C反射 API 新增 UPROPERTY、UFUNCTION、UENUM schema 稳定 + migration + UI 隐藏
D资产格式 材质属性、StaticMesh 数据、Cook 数据 CustomVersion + 资产升级验证
EShader 管线 新 shader、permutation、平台 define 插件 shader + DDC 策略 + 平台测试
F实验功能 验证阶段的大改动 独立分支 / patch stack，不急于进主干

9. 开发流程建议

  1. 立项前先写 Feature Card，明确目标、owner、影响范围和关闭行为。
  2. 先判断是否能做成插件或模块；不能插件化时，再设计最小 Engine hook。
  3. 涉及反射或资产 schema 时，先设计兼容策略，再写功能。
  4. 涉及 shader 时，同步设计 C++ define、shader define、DDC、Cook 和平台矩阵。
  5. 实现时优先把业务逻辑放在 Feature 模块，Engine 只留薄扩展点。
  6. 提交前跑打开/关闭两种配置，至少保证编译和关键路径可用。
  7. 合入后更新 Feature Registry，记录改动文件、验证方式和回滚方式。

11. CI 与验证矩阵

验证项 目的
Feature 开启编译 确保新功能路径可用。
Feature 关闭编译 确保关闭时没有漏包宏或未定义符号。
Editor 启动 验证 UHT、模块加载、反射和编辑器 UI。
Shader 全量编译或目标 shader 编译 验证 shader define、include 路径和 permutation。
Cook smoke test 验证资产序列化、Cook 数据和平台差异。
移动端预览 / SM5 对比 验证渲染路径一致性。
资产加载回归 验证旧资产、带新字段资产、关闭功能资产的兼容性。

12. 分支与补丁管理

对长期自定义引擎来说，建议把“功能是否进主干”和“功能是否启用”分开管理。

阶段 建议
实验阶段 独立分支或 patch stack，避免大量临时代码直接进入主干。
产品化阶段 设计 hook / plugin 边界，补齐 Feature Card 和验证用例。
稳定阶段 进入主干，但保留配置开关、owner 和回归测试。
废弃阶段 先关闭默认启用，再清理代码；反射字段需要迁移或长期兼容。

13. 推荐落地路线

  1. 建立 Feature Registry，先把现有 XD_ 宏按 owner 和影响范围登记。
  2. 标记高风险宏：反射、资产、shader、Cook、MeshPass、RHI、线程生命周期。
  3. 为新增功能设立准入规则：没有 Feature Card 不进主干。
  4. 把散落的大功能逐步收敛为少量 Engine hook + 插件实现。
  5. 先治理新功能，避免继续扩大债务；再逐步整理存量功能。
  6. CI 增加开启/关闭编译矩阵，至少覆盖高风险 Feature。
  7. UE 升级前，按 Feature Registry 分组处理冲突，而不是按文件盲合。

14. 总结

引擎二次开发的重点不是消灭所有侵入，而是让侵入可管理。 宏可以继续保留，但应该从“功能治理中心”降级为“编译期裁剪工具”。

更稳的体系是：宏做裁剪，Hook 做扩展，插件承载实现，Config/CVar 做策略，CustomVersion 做兼容，Feature Card 和 CI 保证可维护性。
