XDBuild 宏模块治理校对

范围：Engine/Source/Programs/UnrealBuildTool/Configuration/XDBuildConfiguration 与 UEBuildTarget.SetupXDNewFeaturesGlobalMacros

生成时间：2026-06-30；目的：把现有引擎二次开发宏按功能模块校对，给出更适合长期维护的收敛方式。

核心判断

当前 XDBuildXXXConfiguration.cs 的问题不是“宏不好”，而是很多不同性质的东西都被放进了同一种全局编译宏机制： bugfix、平台兼容、项目配置值、编辑器工具、接口扩展、渲染功能、cook/PSO 管线优化都混在一起。 这会导致关闭宏时难以保证回到源码一致，也会让新开发者很难判断一个宏应该怎么验证、由谁负责、什么时候可以移除。

推荐方向是：保留少量真正需要编译期裁剪的宏，把可运行时选择的内容迁到 CVar/配置，把工具迁到插件，把扩展能力沉淀为 Hook/Interface/Modular Feature， 把涉及资源格式和 UHT 的变更沉淀为稳定 schema 和 CustomVersion，把已经证明正确的 bugfix 收敛为常开补丁。

552当前扫描到的 public static int 宏/配置值
494+绝大多数默认开启，宏更像补丁清单而不是可选能力
7入口注册的配置类数量
1统一注入点：UEBuildTarget 的全局 Definition

宏注入原理

XDBuildConfiguration.ConfigurationClasses 注册了 XDRenderingFeatures、 XDOptimizationFeatures、XDToolsFeatures、XDFixBugFeatures、 XDNewInterfaces、XDFrontEndTools、XDCustomizedProjectFeatures。 构建时 UEBuildTarget.SetupXDNewFeaturesGlobalMacros 先执行依赖检查，再通过反射读取这些类里的 public static int 字段，并把 字段名=字段值 加入 GlobalCompileEnvironment.Definitions。

所以这些 C# 文件可以控制 C++，本质是 UBT 在编译 C++ 前生成了全局预处理宏。它控制的是编译期代码裁剪，不是运行时开关。 另外，C++ 宏不会自动进入 shader 编译环境，shader 侧仍需要 ModifyCompilationEnvironment、 OutEnvironment.SetDefine 或统一 shader include hook 来桥接。

治理分类

分类 适用对象 推荐处理方式
保留宏 必须编译期裁剪的 ABI、平台 SDK、RHI、shader permutation、极低层性能路径。 保留宏，但建立 feature card：负责人、依赖、默认值、验证场景、关闭时源码等价性。每个宏要有 owner 和失效条件。
CVar/Config 运行时策略、调试开关、平台策略、画质策略、项目数值。 迁到 DefaultEngine.ini、DeviceProfile、Project Settings、TargetRules 或 CVar。编译宏只保留“有没有这个能力”。
插件/模块 编辑器工具、菜单扩展、资源审计、dump/report、front-end 工具。 迁到 Editor/Developer 插件，通过模块启用、菜单 extender、命令行参数或 CVar 控制。Shipping 构建自然不带工具代码。
Hook/Interface 引擎需要留扩展点，但具体行为可由项目/插件绑定的功能。 引擎侧只放稳定事件、接口或 Modular Feature，例如 pak 挂载失败、低内存回调、异步加载 flush、PSO 接管点。
Schema/Version UFUNCTION、UPROPERTY、资产格式、序列化升级、DDC key、cook 确定性。 不要用宏包住反射字段和资产 schema。用 CustomVersion、版本化迁移、稳定字段、兼容读取来降低破坏性。
常开补丁 已验证正确、不会改变项目策略的 bugfix。 宏经过灰度后移除，作为引擎 fork 的常开补丁维护。否则默认开启的 bugfix 宏只是在制造伪开关。
临时隔离 XD_TMP_、XD_TRY_FIX_、_DEBUG、_TESTING 这类实验开关。 必须有过期时间、验证结论和删除计划。默认关闭，不能长期混在正式功能清单里。

按模块整理建议

1. Rendering：从“功能宏”收敛到渲染扩展层

代表宏 问题性质 建议整理方式
XD_RENDERING_CUSTOM_UNLIT、XD_PC_RENDERING_CUSTOM_UNLIT、XD_RENDERING_TOON_LIT_SHADING_MODEL、XD_RENDERING_CUSTOM_GI 新增 shading model 和 shader 路径，影响材质 schema、shader permutation、GBuffer/LightGrid。 HookSchema引擎侧保留最小稳定插槽：shading model ID、材质编译 hook、shader include hook、LightGrid/IBL 输入约定。具体 BRDF、ramp、GI、额外贴图逻辑放到插件或可替换 shader include 中。
XD_RENDERING_NATIVESTENCIL_SUPPORT_MATERIAL、XD_RENDERING_BASEPASS_RENDERING_PRIORITY、XD_RENDERING_DISABLE_COLOR_WRITE、XD_EXTRA_GBUFFER 改变 render pass 数据结构和排序规则，容易产生全局副作用。 保留宏Hook先按能力域合并成“Renderer Material Extension”层，统一管理 mesh batch flags、base pass priority、stencil/color write、extra GBuffer 通道，减少散落宏。
XD_RENDERING_CLUSTERED_LIGHTING、XD_CUSTOMUNLIT_SPOTLIGHT_SUPP、EXTRA_SSSHADOW_CHANNEL_FOR_CUSTOMUNLIT 局部光、shadow channel、LightGrid 数据读取路径。 Hook不要按 shading model 各自维护灯光列表。沉淀一个统一 LightGrid 访问约定，CustomUnlit 和 Mobile DefaultLit 都复用同一套 local light 数据结构和过滤规则。
XD_PC_SWITCH_DX_VERSION_AFTER_CRASH、XD_PC_FALLBACK_TO_DX11_WHEN_DX12_CRASH、XD_PC_GRAPHICS_DRIVER_VERSION_WARNING PC 平台兼容策略，不是渲染算法本身。 CVar/Config迁到 Platform Compatibility/Launcher 策略模块，使用配置、崩溃记录、驱动数据库控制。宏只保留 D3D11/D3D12 编译能力。
XD_RENDERING_ADJUST_BLOOM_MIN_RGB_VALUE、XD_BLOOM_CLAMP、XD_RENDERING_OPAQUE_UNLIT_DISABLE_FOG 画质/策略开关。 CVar/Config优先迁到 CVar 或项目渲染设置，方便不同平台和画质档切换。

2. Optimization：按“性能路径”和“策略路径”拆开

代表宏 问题性质 建议整理方式
XD_OPT_DONT_UPDATE_PRIMITIVE_UBO_WHEN_PARAMS_NOT_CHANGE、XD_OPT_SKELETAL_MESH_SKIP_CREATE_UNIFORM_BUFFER_EVERY_FRAME、XD_OPT_MEMORY_LIGHT_PRIMITIVE_INTERACTION_ALLOC 底层性能优化，关闭/开启会改变热路径。 保留宏常开补丁如果已经长期验证稳定，建议转为常开优化；若仍有风险，保留宏但补充性能基准和回归用例。
XD_OPT_MOBILE_UPSCALE_PASS_DISABLE_WHEN_SIZE_DIFF_LITTLE、XD_OPT_MOBILE_USE_COARSE_STATIC_SHADOW_MASK_TEXTURE、XD_OPT_MOBILE_LANDSCAPE_POINT_LIGHTING 移动端渲染策略。 CVar/Config迁到 DeviceProfile/RendererSettings。和 LightGrid、DefaultLit、CustomUnlit 的移动端光照路径一起定义平台策略。
XD_OPT_PARTICLE_INSTANCING、XD_OPT_PARTICLE_COMPONENT_INTERFACE、XD_OPT_FAST_PARTICLE_SYSTEM_COMPONENT、XD_OPT_LOCK_FREE_PARTICLE_MEMORY_POOL 粒子系统扩展和性能重构，既有接口又有内存池。 HookSchema拆成 Particle Runtime Extension。稳定接口和组件字段不要宏包裹，性能实现可以由插件/配置选择。
XD_OPT_PRECOMPILE_PSO_SMOOTHLY、XD_OPT_LOAD_PSO_CACHE_BY_QUALITY_LEVEL、XD_OPT_ITERATIVE_PAK、XD_OPT_SHADER_LIB_SRIP cook、pak、shader library、PSO 资产管线。 插件/模块Schema迁到 Build/Cook Pipeline 模块，以命令行、配置、cook profile 控制，增加 cook determinism 和 DDC key 验证。
XD_OPT_LLM_CSV_EXTENSIONS、XD_OPT_ANALYSIS_IOS_PLATFORM_UNTRACKED_MEMORY、XD_OPT_ANALYSIS_WIN_PLATFORM_UNTRACKED_MEMORY 分析与统计。 插件/模块迁入 Developer/Profiling 插件。Shipping 通过构建配置剔除，日常用 CVar/命令行打开。

3. Tools 与 FrontEnd：优先插件化

XD_TOOL_DUMP_XD_CONSOLE_VARIABLES、XD_TOOL_EXPORT_MATERIAL_ANALYZER_RESULT、 XD_TOOL_ASSET_AUDIT_EXT_COL、XD_FE_P4_SUBMITTER_TOOL、 XD_PRE_CHECKIN_EVENT_SEND 这类功能本质是工具，不应该依赖全局引擎宏。

子类 建议
Dump、Report、Profiler、Debug UI 插件/模块迁到 Developer 插件，用命令行/CVar/Editor 菜单启用。
编辑器菜单扩展 插件/模块用 Editor Module、ToolMenus、Extender 绑定，减少 Engine 源码改动。
XD_SERIALIZE_UPGRADE_FIXUP_STATIC_MESH_NONUSED_PROPERTY Schema/Version序列化升级不适合用宏长期包裹，应改为 CustomVersion 或一次性迁移命令let，并保留兼容读取。
Runtime/Editor delegates Hook例如 save delegate、Slate loading pre-tick delegate，可以沉淀为引擎扩展点，具体逻辑由插件绑定。

4. NewInterfaces/Misc：拆成平台、错误、资源、接口四个包

代表宏 建议归属 说明
XD_EXT_ADD_ON_LOW_MEMORY_DELEGATE、XD_EXT_ASYNC_LOAD_FLUSH_DELEGATE、XD_MISC_SKELETAL_MESH_COMPONENT_ADD_DELEGATES Hook/Interface 这类是好扩展点。引擎留空事件和接口，项目插件决定绑定什么逻辑。
XD_EXT_PLATFORM_UNWANTED_BEHAVIORS_TAKEOVER、XD_EXT_ANDROID_ALLOW_OPENGL_FALLBACK_TO_VULKAN、XD_MISC_ANDROID_EMULATOR_USE_NATIVE_RESOLUTION 平台策略配置 平台行为接管应集中到 Platform Policy 模块，避免散落在 Misc 宏里。
XD_EXT_OOM_POP_UP_TIPS_WINDOWS、XD_EXT_DX_ERROR_POP_UP_TIPS_WINDOWS、XD_MISC_NOTIFY_USER_ON_PAK_FATAL_ERROR 错误处理插件 错误弹窗、崩溃上报、用户提示应做成 Error Reporter/Crash Tools 插件，由产品配置决定是否启用。
XD_MISC_PAK_FILE_ENCRY、XD_PRE_MOUNT_PAK、XD_MISC_SUPPORT_MULTIPLE_PSO_CACHE_FILES、XD_MISC_CLEAN_OBSOLETE_PSO_CACHE_AND_PROGRAM_CACHE 资源管线模块 pak、PSO cache、program binary cache 建议统一进 Packaging/Runtime Asset Pipeline。
XD_MISC_LOG_SHADER_DETAILED_DDC_KEY、XD_MISC_SHADER_KEEPDEBUG_INFO、XD_EXT_OUTPUT_SHADER_LINK_HASH 诊断工具 诊断开关迁到 Developer 插件和命令行，减少全局宏污染。

5. FixBug：建立“补丁生命周期”，不要永久宏化

XDFixBugFeatures 有 172 项，是最需要治理的模块。这里建议按生命周期而不是按文件归类。

类别 例子 处理建议
已验证通用 bugfix XD_BUG_FIX_FONT_CACHE_MEM_LEAK、XD_BUG_FIX_GC_SYNCOBJ、XD_BUG_FIX_EDITOR_TRANSACTION_BUFFER_NULLPTR 常开补丁经过回归后移除宏，作为 fork 的稳定补丁。长期默认开启的 bugfix 宏价值很低。
平台/RHI workaround XD_BUG_FIX_VKACQUIRENEXTIMAGE_TIMEOUT、XD_BUG_FIX_VULKAN_TILE_FAST_CLEAR_ARTIFACT、XD_BUG_FIX_MSAA_CRASH_ON_MAC、XD_BUG_FIX_MUMU_GL_BACK_BUFFER_SAMPLE 平台策略配置放入 Platform Compatibility 层，结合设备、驱动、RHI、模拟器白名单配置控制。
Cook/DDC/PSO 确定性 XD_BUG_FIX_GENERATE_DETERMINED_MATSM_DDC、XD_BUG_FIX_COOK_DETERMINED_PSO、XD_BUG_FIX_KEEP_SAME_UBULK_FILE_WHEN_CHECK_COOK_DETERMINISTIC Schema/Version纳入 Build Pipeline 验证，配套 determinism 测试和 DDC key golden data。
编辑器交互修复 XD_BUG_FIX_ADD_ARRAY_ELEMENT_TO_SEQUENCER_TRACK、XD_BUG_FIX_ADD_TARRAY_ELEMENT_FAILED_IN_DETAIL_PANEL、XD_BUG_FIX_P4_SOURCE_CONTROL_PATH_CASE_SENSITIVITY 插件/模块常开补丁如果是工具行为增强，可插件化；如果是明确 bug，验证后常开。
临时尝试或测试 XD_TMP_FIX_MALLOC_ZERO_ISSUE、XD_TRY_FIX_BUG_SLATE_INVALID_TEXTURE_PTR、XD_BUG_FIX_VKACQUIRENEXTIMAGE_TIMEOUT_TESTING 临时隔离必须有删除日期和验证结论。长期存在会让宏清单失去可信度。

6. ProjectFeatures：不要让项目配置值污染引擎全局宏

XDCustomizedProjectFeatures 中有明显项目专有项，例如 XD_TORCHLIGHT_SEASON = 14、 XD_MATERIAL_SELECTOR_SWITCH_NUM = 7、XD_TORCHLIGHT_WIDGETBLUEPRINTEDITOR_PASTEWIDGET_LANHU_RULE。 这类内容不适合作为全局引擎二开宏。

类型 建议
项目数值 CVar/Config迁到项目配置、TargetRules、GameFeatureData 或 Project Settings。编译宏不适合表达赛季号、selector 数量这类数据。
项目 UI/编辑器规则 插件/模块迁到项目 Editor 插件，例如 TorchlightEditorExtensions。
项目运行时行为 Hook引擎提供通用 hook，项目插件绑定 Torchlight 逻辑。

建议的目标结构

目标包 吸收内容 落地形式
EngineExtensionCore 通用 Hook、Interface、Modular Feature、事件广播。 少量引擎侵入式补丁，必须稳定、低语义、可被多个项目复用。
RendererExtension 自定义 shading model 插槽、LightGrid 访问、extra GBuffer、stencil/material pass 扩展。 引擎侧提供最小扩展面，功能实现由插件或 shader include 组合。
PlatformCompatibility DX fallback、驱动警告、iOS/Android/Vulkan/Metal/模拟器 workaround。 平台配置、设备画像、崩溃记录、launcher 策略。
BuildCookPipeline cook determinism、pak、PSO、shader library、DDC key、program binary cache。 Commandlet、cook profile、CI 验证、golden data。
DeveloperTools dump、report、asset audit、profiling、material analyzer、debug UI。 Editor/Developer 插件，按构建配置剔除。
ProjectFeaturePlugins Torchlight 等项目专用 UI、运行时策略、资源规则。 项目插件、Project Settings、GameFeatureData。

迁移路线

  1. 先建台账。 给每个宏补上 owner、模块、默认值、依赖、验证方式、关闭后期望行为、是否影响资源格式。
  2. 先处理工具类。 Tools、FrontEnd、Debug、Report、Audit 优先插件化，收益高、风险低。
  3. 再处理项目专有配置。 把 Torchlight 项目项和数值项迁到项目插件或配置，减少引擎 fork 污染。
  4. 对 FixBug 做生命周期治理。 默认开启且稳定的 bugfix 转常开补丁；临时/try/testing 类宏限期删除；平台 workaround 迁到 PlatformCompatibility。
  5. 最后处理渲染和资源 schema。 这类风险最高，需要先定义稳定扩展面，再逐步减少散落宏。
  6. 建立双构建验证。 CI 至少保留“源码等价配置”和“项目完整配置”两套构建，避免宏关闭路径腐烂。

最值得优先行动的清单

优先项 原因 建议第一步
Tools/FrontEnd 插件化 侵入低，能快速减少全局宏数量。 从 dump/report/asset audit/P4/pre-checkin 菜单开始迁。
ProjectFeatures 外迁 项目策略不该进入引擎全局宏，尤其是数值型宏。 建立 TorchlightProjectExtensions 插件和项目配置对象。
FixBug 分类清理 172 项默认开启宏会显著增加维护成本。 按“常开补丁、平台 workaround、临时实验、cook 确定性”打标签。
RendererExtension 抽象 渲染宏最容易产生连锁副作用，但也是长期价值最高的扩展面。 先定义 Custom Shading Model、LightGrid、extra GBuffer、material pass flags 的统一扩展边界。
宏 schema 校验 现在用反射扫描字段，缺少元数据和约束。 给宏增加结构化描述，生成 HTML/Markdown 台账，并在 UBT 里校验依赖和废弃状态。

一句话落地原则

宏只应该回答“这段代码是否参与编译”；不要让宏同时承担项目配置、运行时策略、工具入口、平台黑名单、资产版本迁移和扩展机制。 对引擎二开来说，真正可长期维护的形态是：少量稳定引擎 hook，加一组可替换插件，再加清晰的配置和 CI 验证。
