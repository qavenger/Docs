Programming Paradigms / From Hardware to Abstractions

从硬件视角理解不同程序设计思路

所有高级语言最终都会落到 CPU 指令、寄存器、内存读写和分支跳转上。程序设计范式不是在否认这个事实，而是在硬件执行模型之上建立不同的组织方式，让人更容易描述复杂系统。

硬件视角 两个维度 统一示例 状态表达 数据组织 组合关系 选择方法

一、先从硬件视角看程序

如果把所有语法糖拿掉，计算机真正做的事情相当朴素：从内存取指令，把数据加载到寄存器，执行算术、比较、跳转、读写内存，然后继续执行下一条指令。无论是 C++、Verse、Python、SQL，最终都要被解释器、虚拟机或编译器转换成某种可执行的低层操作。

硬件关心什么

  • 指令顺序：下一步执行什么，是否跳转，是否循环。
  • 数据位置：数据在寄存器、缓存、内存、磁盘或网络上。
  • 数据布局：连续数组通常比零散对象更利于缓存。
  • 状态变化：某块内存里的值在什么时候被改写。
  • 并行和同步：多个核心、线程或任务是否会同时读写同一份数据。

人类关心什么

  • 意图：这段代码想表达什么规则。
  • 边界：哪些数据属于同一类问题。
  • 复用：相同逻辑如何避免重复书写。
  • 可维护性：需求变化时改哪里，风险有多大。
  • 正确性：怎样减少状态混乱和隐式副作用。

因此，程序设计思路可以理解为一层层抽象：越靠近硬件，越强调指令顺序、内存布局和显式状态；越靠近问题领域，越强调规则、对象、数据关系和结果描述。

二、两个核心维度

不同范式经常被混在一起讨论，但它们其实主要回答两个不同问题。

维度 它回答的问题 更贴近硬件的一侧 更贴近问题描述的一侧
计算和状态如何表达 程序是一步步修改状态，还是把计算组织成产生结果的表达式、函数或规则？ 指令式、过程式 表达式式、函数式、声明式
数据和行为如何组织 数据放在哪里，行为归属于谁，系统边界如何划分？ 面向内存布局、面向数据 面向对象、ECS、领域模型、关系模型
机器层：指令流操作寄存器和内存。它是所有程序的最终落点。
指令/过程层：程序员显式安排步骤、循环、条件、变量更新。
数据组织层：为了性能或领域建模，决定数据按数组、对象、组件还是表组织。
规则表达层：代码更像是在描述“要什么结果”，执行细节交给语言、编译器或引擎。

三、统一示例：玩家战斗结算

为了让不同范式可以横向比较，下面所有示例都实现同一个功能：给一批玩家做战斗结算。

  • 只处理仍然存活且已参战的玩家。
  • 得分公式：击杀 10 分，助攻 4 分，占点 25 分，存活额外 8 分。
  • 得分达到阈值的玩家获得奖励。
  • 最终生成战报：有效玩家数、总分、奖励列表。

这个例子不复杂，但包含了筛选、循环、计算、条件判断、聚合和结果构造，足够观察不同编程思路的差异。

四、维度一：计算和状态如何表达

这个维度最接近“硬件如何执行”。它关心的是：程序如何从旧状态走到新状态。

1. 指令式：明确写出每一步状态变化

贴近硬件流程清楚状态显式变化

指令式编程把程序写成一系列命令：先创建变量，再循环，再判断，再累加，再写入结果。这种写法和 CPU 顺序执行指令的模型最接近，所以直观、可控，也容易做底层优化。

它的代价是状态变化分散在流程中。代码一长，就需要非常小心地追踪变量什么时候被改过。

struct PlayerStats {
    bool active;
    int health;
    int kills;
    int assists;
    int objectives;
};

struct Reward {
    int playerIndex;
    int score;
};

struct BattleReport {
    int eligibleCount;
    int totalScore;
    std::vector<Reward> rewards;
};

BattleReport BuildReportImperative(
    const std::vector<PlayerStats>& players,
    int minScore
) {
    BattleReport report;
    report.eligibleCount = 0;
    report.totalScore = 0;

    for (int i = 0; i < players.size(); ++i) {
        const PlayerStats& player = players[i];

        if (!player.active || player.health <= 0) {
            continue;
        }

        int score = player.kills * 10;
        score += player.assists * 4;
        score += player.objectives * 25;
        score += 8;

        report.eligibleCount += 1;
        report.totalScore += score;

        if (score >= minScore) {
            report.rewards.push_back({ i, score });
        }
    }

    return report;
}

2. 过程式 / 模块化：把步骤拆成函数

仍然接近硬件复用流程降低主流程噪声

过程式编程仍然是指令式的，但它把重复逻辑封装成函数。它不强调对象是谁，也不要求所有代码都围绕类型建模；重点是把流程拆成清楚的子过程。

这种方式适合工具函数、算法、脚本、数据转换、引擎底层模块。它的优点是直接，缺点是当数据和行为关系变复杂时，函数之间可能缺少清晰归属。

bool IsEligible(const PlayerStats& player) {
    return player.active && player.health > 0;
}

int CalculateScore(const PlayerStats& player) {
    return player.kills * 10
         + player.assists * 4
         + player.objectives * 25
         + 8;
}

void AddPlayerResult(
    BattleReport& report,
    int playerIndex,
    int score,
    int minScore
) {
    report.eligibleCount += 1;
    report.totalScore += score;

    if (score >= minScore) {
        report.rewards.push_back({ playerIndex, score });
    }
}

BattleReport BuildReportProcedural(
    const std::vector<PlayerStats>& players,
    int minScore
) {
    BattleReport report{ 0, 0, {} };

    for (int i = 0; i < players.size(); ++i) {
        if (IsEligible(players[i])) {
            AddPlayerResult(report, i, CalculateScore(players[i]), minScore);
        }
    }

    return report;
}

3. 表达式式：让一段代码产生值，而不是只执行动作

减少临时状态结果导向适合 Verse 这类语言

表达式式编程的关键是：很多代码结构本身都能产生值。比如一个循环、条件、代码块不只是“做一些事”，也可以直接形成一个结果。这样可以把“计算新值”和“提交到外部状态”分开。

这类思路特别适合减少中途改写：先在局部范围内构造结果，最后一次性赋给更外层变量。它比纯指令式更强调值的流动，但通常不要求完全无副作用。

player_stats := struct:
    Active:logic
    Health:int
    Kills:int
    Assists:int
    Objectives:int

reward := struct:
    PlayerIndex:int
    Score:int

battle_report := struct:
    EligibleCount:int
    TotalScore:int
    Rewards:[]reward

ScoreOf(Player:player_stats):int =
    Player.Kills * 10 + Player.Assists * 4 + Player.Objectives * 25 + 8

BuildReportExpression(Players:[]player_stats, MinScore:int):battle_report =
    Entries :=
        for (Index -> Player : Players, Player.Active?, Player.Health > 0):
            Score := ScoreOf(Player)
            reward{ PlayerIndex := Index, Score := Score }

    battle_report:
        EligibleCount := Entries.Length
        TotalScore := Sum(for (Entry : Entries): Entry.Score)
        Rewards := for (Entry : Entries, Entry.Score >= MinScore): Entry

4. 函数式：把计算看成值到值的转换

强调不可变数据组合小函数副作用集中管理

函数式编程会尽量避免在原地修改状态，而是把输入数据转换成新的输出数据。常见操作是筛选、映射、折叠：先过滤有效玩家，再映射成得分条目，最后归约成战报。

这种方式的优势是容易推理和测试，因为函数输出主要由输入决定。代价是如果语言或运行时没有做好优化，可能产生更多中间数据；在性能敏感代码里需要配合惰性求值、迭代器或专门的数据结构。

type PlayerStats = {
  active: boolean;
  health: number;
  kills: number;
  assists: number;
  objectives: number;
};

type Reward = { playerIndex: number; score: number };
type BattleReport = { eligibleCount: number; totalScore: number; rewards: Reward[] };

const scoreOf = (player: PlayerStats) =>
  player.kills * 10 + player.assists * 4 + player.objectives * 25 + 8;

function buildReportFunctional(players: PlayerStats[], minScore: number): BattleReport {
  const entries = players
    .map((player, index) => ({ player, index }))
    .filter(({ player }) => player.active && player.health > 0)
    .map(({ player, index }) => ({ playerIndex: index, score: scoreOf(player) }));

  return {
    eligibleCount: entries.length,
    totalScore: entries.reduce((sum, entry) => sum + entry.score, 0),
    rewards: entries.filter(entry => entry.score >= minScore),
  };
}

5. 声明式：描述想要的结果，让执行引擎决定怎么做

离硬件更远规则优先执行计划交给引擎

声明式编程不重点描述“先做什么再做什么”，而是描述结果必须满足什么条件。SQL 是典型例子：你写的是筛选、分组、聚合规则，数据库引擎会决定索引、扫描顺序和执行计划。

它的好处是表达领域规则非常直接，尤其适合查询、约束、布局、配置、构建规则。缺点是当性能异常或执行顺序很重要时，需要理解背后的引擎。

WITH eligible AS (
  SELECT
    player_id,
    kills * 10 + assists * 4 + objectives * 25 + 8 AS score
  FROM player_stats
  WHERE active = true AND health > 0
),
summary AS (
  SELECT
    COUNT(*) AS eligible_count,
    SUM(score) AS total_score
  FROM eligible
),
rewarded AS (
  SELECT player_id, score
  FROM eligible
  WHERE score >= :min_score
)
SELECT
  summary.eligible_count,
  summary.total_score,
  rewarded.player_id,
  rewarded.score
FROM summary
LEFT JOIN rewarded ON true;

五、维度二：数据和行为如何组织

这个维度关心的是：数据在程序里被摆成什么形状，逻辑围绕什么边界展开。它既影响可维护性，也影响性能。

1. 面向数据：先考虑内存布局和批量处理

接近缓存和内存适合游戏和引擎强调批处理

面向数据设计从硬件角度出发：CPU 不理解“玩家对象”，它只读取内存。若同一类字段连续存放，循环处理时缓存命中更好，也更容易向量化或并行化。

它常用于游戏引擎、渲染、物理、粒子、动画、服务器批处理等场景。缺点是领域语义可能没有对象模型那么直观，代码需要更自觉地维护数据列之间的对应关系。

struct PlayerColumns {
    std::vector<bool> active;
    std::vector<int> health;
    std::vector<int> kills;
    std::vector<int> assists;
    std::vector<int> objectives;
};

BattleReport BuildReportDataOriented(
    const PlayerColumns& players,
    int minScore
) {
    BattleReport report{ 0, 0, {} };
    int count = static_cast<int>(players.health.size());

    for (int i = 0; i < count; ++i) {
        if (!players.active[i] || players.health[i] <= 0) {
            continue;
        }

        int score = players.kills[i] * 10
                  + players.assists[i] * 4
                  + players.objectives[i] * 25
                  + 8;

        report.eligibleCount += 1;
        report.totalScore += score;

        if (score >= minScore) {
            report.rewards.push_back({ i, score });
        }
    }

    return report;
}

2. 面向对象：把数据和行为放到同一个概念边界里

领域建模封装状态适合复杂业务对象

面向对象把程序看成一组对象，每个对象持有自己的状态，并提供行为。它的核心价值不是“把函数塞进类里”，而是用对象边界表达领域概念：玩家知道自己是否可结算，结算器负责生成战报。

这种方式适合有清晰身份、生命周期和行为边界的系统。风险是对象太多、继承过深、状态分散后，程序会变成大量对象之间的隐式协作，调试和性能都可能变难。

class Player {
public:
    Player(bool active, int health, int kills, int assists, int objectives)
        : active(active), health(health), kills(kills),
          assists(assists), objectives(objectives) {}

    bool CanBeSettled() const {
        return active && health > 0;
    }

    int Score() const {
        return kills * 10 + assists * 4 + objectives * 25 + 8;
    }

private:
    bool active;
    int health;
    int kills;
    int assists;
    int objectives;
};

class BattleSettlement {
public:
    BattleReport BuildReport(const std::vector<Player>& players, int minScore) const {
        BattleReport report{ 0, 0, {} };

        for (int i = 0; i < players.size(); ++i) {
            if (!players[i].CanBeSettled()) {
                continue;
            }

            int score = players[i].Score();
            report.eligibleCount += 1;
            report.totalScore += score;

            if (score >= minScore) {
                report.rewards.push_back({ i, score });
            }
        }

        return report;
    }
};

3. ECS：实体是 ID，组件是数据，系统是批量逻辑

游戏常用组合优于继承兼顾结构和性能

ECS 可以理解为面向数据和领域组织之间的一种折中。实体只是 ID，组件存放数据，系统处理拥有某些组件的一批实体。它避免把所有能力塞进继承层级，也比传统对象更容易批处理。

它适合游戏玩法、模拟、编辑器场景和大量实体同时更新的系统。代价是单个实体的行为不再集中在一个对象里，阅读代码时需要沿着组件和系统关系理解整体流程。

struct Entity {
    int id;
};

struct CombatStats {
    int kills;
    int assists;
    int objectives;
};

struct Health {
    int value;
};

struct BattleSettlementSystem {
    BattleReport Update(World& world, int minScore) {
        BattleReport report{ 0, 0, {} };

        world.ForEach<Health, CombatStats, ActivePlayer>(
            [&](Entity entity, const Health& health, const CombatStats& stats) {
                if (health.value <= 0) {
                    return;
                }

                int score = stats.kills * 10
                          + stats.assists * 4
                          + stats.objectives * 25
                          + 8;

                report.eligibleCount += 1;
                report.totalScore += score;

                if (score >= minScore) {
                    report.rewards.push_back({ entity.id, score });
                }
            }
        );

        return report;
    }
};

4. 关系模型：把数据看成表和关系

数据系统常用规则清晰天然适合查询

关系模型不把重点放在对象或内存数组上，而是把数据组织成表、字段、约束和关系。它更接近“业务数据事实”的表达：哪些玩家存在，哪些字段参与结算，哪些记录满足奖励条件。

它非常适合持久化、统计、报表、后台系统和跨维度查询。缺点是它通常不是最自然的实时玩法逻辑表达方式，需要和内存中的运行时模型相互转换。

CREATE TABLE player_stats (
  player_id INTEGER PRIMARY KEY,
  active BOOLEAN NOT NULL,
  health INTEGER NOT NULL,
  kills INTEGER NOT NULL,
  assists INTEGER NOT NULL,
  objectives INTEGER NOT NULL
);

CREATE VIEW battle_scores AS
SELECT
  player_id,
  kills * 10 + assists * 4 + objectives * 25 + 8 AS score
FROM player_stats
WHERE active = true AND health > 0;

六、它们不是互斥选项，而是可以组合

很多误解来自把范式当成互相排斥的阵营。实际项目里，常常是多个思路同时存在，只是不同层级的主导思路不同。

组合 常见场景 理解方式
面向对象 + 指令式 传统游戏玩法类、业务服务、编辑器工具 对象负责封装状态，方法内部仍然一步步修改状态。
面向数据 + 指令式 渲染、物理、动画、粒子、批量服务器逻辑 数据按缓存友好的方式排列，循环显式处理每个元素。
ECS + 面向数据 大量实体同时更新的游戏系统 组件提供数据布局，系统按组件组合批量执行逻辑。
函数式 + 过程式 数据转换、编译器管线、构建工具、前端状态计算 外层流程仍然有步骤，内部尽量用纯函数组合计算。
声明式 + 引擎执行 SQL、正则、UI 布局、构建配置、规则系统 程序员描述规则，由执行引擎把规则转成具体步骤。

七、实践中的选择方法

性能和数据量优先

先看数据布局和访问模式。大量同类数据、频繁循环、缓存敏感的系统，通常更适合面向数据或 ECS。

领域概念优先

如果问题天然由有身份、有生命周期、有行为边界的对象组成，面向对象会让模型更贴近人的理解。

规则和结果优先

如果重点是描述筛选、约束、变换、聚合或配置，函数式和声明式通常比手写流程更清楚。

一个更稳定的理解

硬件最终执行的一定是低层指令，但人写程序不必停留在指令层。指令式让你控制“怎么做”，表达式式和函数式让你更关注“值如何得到”，声明式让你描述“结果满足什么规则”。面向对象、面向数据、ECS、关系模型则是在回答另一件事：数据和行为应该以什么形状组织起来。

所以，程序设计思路不是从低级到高级的单向替代关系，而是不同抽象层的工具箱。越理解底层，就越能知道什么时候该贴近硬件；越理解抽象，就越能知道什么时候该让代码贴近问题本身。
