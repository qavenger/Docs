虚幻引擎（UE）多项目源码仓库管理方案

面向中等规模团队 · N 个不同类型项目 · 各自有定制需求

核心思想是「分层 + 单向上游 + 定制下沉」：把"通用引擎改动"和"项目专属改动"在物理上分离，让改动只沿一个方向合并，避免 N 个项目各自魔改引擎后无法收敛、无法升级。

二、三层各自的职责

① 上游层Epic 官方源码

  • 直接镜像 Epic 的 UnrealEngine 仓库，作为一个只读的 upstream remote，任何人都不在这一层提交。
  • 只用于定期把官方的新版本（如 5.4 → 5.5）合并进公司基线层。

② 公司基线层Engine-Base（一个公司级 Fork）

  • 这是全公司唯一的引擎主干，放所有项目都受益的东西：通用 Bug 修复、公共插件、统一的构建/打包/CI 工具链、美术导出管线、性能补丁等。
  • 用 release/5.x 分支锁定大版本，配合 main 滚动。由专门的引擎组（Engine Team）维护，对外发布编译好的 二进制 Installed Build。
  • 这样大多数不需要改引擎源码的项目，直接用二进制版本即可，无需本地编译整套引擎，省下大量构建时间。

③ 项目层每个项目按需选择三种模式之一

项目类型引擎使用方式定制落点
不改引擎直接用基线的二进制 Installed Build全部定制做成插件 / Game 模块，放在游戏仓库里
少量改引擎从基线拉 project/X 分支能下沉到插件的下沉，少量必要的源码改动留在分支
深度改引擎独立 project/X 长期分支，定期从基线 merge down平台/渲染等深度定制留分支，通用部分上提回基线

三、关键规则：改动只能单向流动

▼ 向下（下发）：Epic → 基线 → 项目。新版本和公共修复，由上层定期合并下发，项目只负责"接收并解决冲突"。

▲ 向上（回流）：当某项目做出的引擎改动是通用的（别的项目也能用），必须通过 PR / cherry-pick 上提回基线层，而不是各自留在项目分支里。

最重要的一条原则：定制尽量「插件化」。能用插件、Game 模块、配置（DefaultEngine.ini）解决的，就绝不直接改引擎源码。引擎源码改得越少，跟官方升级的成本就越低。直接魔改源码是后期无法升级引擎的头号原因。

四、版本控制工具选型

内容推荐工具说明
引擎源码Git + Git LFS便于 fork/分支/PR/cherry-pick，天然支持上述分层模型
游戏资产Perforce (Helix Core)大二进制资产 + 美术协作 + 文件独占锁，UE 生态事实标准
二进制引擎分发制品库（Artifactory / 内网共享）引擎组产出 Installed Build，项目按版本号拉取，不用本地编译
若团队已重度使用 Perforce，可用 Streams 实现同样的分层：//engine/upstream → //engine/base → //engine/project-X，逻辑与上图一致。

五、落地清单

  • ✅ 设立独立的引擎组，专职维护基线层、合并官方版本、产出二进制构建。
  • ✅ 基线层固定大版本节奏（如每个 UE 大版本评估一次升级），项目按窗口期跟随。
  • ✅ 制定「定制优先级」：配置 > 插件 > Game 模块 > 引擎源码（万不得已）。
  • ✅ 引擎源码改动强制走 Code Review，并标注「项目专属 / 可上提通用」。
  • ✅ CI 对基线层做编译 + 打包 + 多平台冒烟测试，保证下发版本可用。
