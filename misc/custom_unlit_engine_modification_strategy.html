Custom Unlit 与引擎侵入式修改治理方案

面向长期维护自定义 UE 分支的宏治理、Hook 化与插件化改造思路。

核心结论：不要追求所有改动在宏关闭后“字节级等于原始引擎”。更现实、更稳的目标是：让侵入边界尽量小，让副作用可见、可测、可回滚。

1. 当前宏方案的定位

当前项目里的 XDBuildXXXConfiguration.cs 本质上是一套基于 UnrealBuildTool 的全局 Feature Flag 系统。 C# 在 C++ 编译前运行，通过 GlobalCompileEnvironment.Definitions.Add() 把配置字段注入成 C++ 预处理宏。 

XDBuildRenderingConfiguration.cs
  public static int XD_RENDERING_CUSTOM_UNLIT = 1;

UnrealBuildTool
  GlobalCompileEnvironment.Definitions.Add("XD_RENDERING_CUSTOM_UNLIT=1");

C++ 编译期
  #define XD_RENDERING_CUSTOM_UNLIT 1

这类宏适合处理纯 C++ 编译裁剪、平台差异、性能敏感路径和 shader permutation 控制。 但它不适合作为所有引擎侵入式修改的唯一治理手段。

2. 宏方案的主要风险

风险 表现 原因
漏包宏 关闭宏后编译失败，或行为仍残留 大功能通常散落在多个模块、shader、editor、runtime 里
反射系统不可干净裁剪 UCLASS、UPROPERTY、UFUNCTION 很难被宏安全包裹 UHT、generated header、资产序列化依赖稳定 schema
资产兼容性变化 关闭宏后旧资产无法加载、字段丢失、材质编译异常 材质 ShadingModel、属性、表达式节点进入资产数据
Shader DDC 不一致 shader 结果异常或缓存污染 C++ 宏、shader define、DDC key 没有统一管理
升级困难 UE merge 时冲突多，难判断功能边界 功能逻辑直接散布在引擎主流程中
反射层建议：不要追求 UPROPERTY / UFUNCTION 随宏开关完全消失。更稳的方式是保持 schema 稳定，关闭时只关闭行为。

3. Custom Unlit 当前侵入点

当前 CustomUnlit 已经不是单一 shader 功能，而是一套完整的新 shading model 管线。

层级 当前内容 侵入程度
材质类型 在 EMaterialShadingModel 中增加 MSM_CustomUnlit 很高
材质节点 MaterialExpressionCustomUnlit.h 增加多组 UCLASS 节点 中高
HLSL 翻译 FHLSLMaterialTranslator 增加 GetDynamicLighting、GetIBL 等接口 高
Shader Define MATERIAL_SHADINGMODEL_CUSTOM_UNLIT、MATERIAL_SHADINGMODEL_CUSTOM_UNLIT_SM5 中
PC 渲染路径 独立 CustomUnlitPass、FCustomUnlitMeshPassProcessor、EMeshPass slot 高
Mobile 渲染路径 独立 MobileBasePassCustomUnlit* shader 中高
灯光数据 GatherAndSortCustomUnlitLights、CustomUnlitLocalLightBuffer 中高
LightComponent bUsedForCustomUnlit、IsUsedForCustomUnlit() 高
Editor 适配 PreviewMaterial、MaterialGraph、DebugViewMode 等特殊处理 中

4. 推荐的总体架构

对于 CustomUnlit 这类新 shading model，不建议追求完全插件化。更现实的目标是： 

Engine 保留稳定 schema 和少量扩展点
Plugin 承载具体功能逻辑
Project Policy 决定平台、开关和策略
层 建议承载内容
Engine Stable Hook Layer MSM_CustomUnlit、MeshPass slot、材质编译通用桥、renderer RDG hook、shader include hook、light feature mask
XDCustomUnlit Plugin 材质节点、shader 文件、CustomUnlit pass processor、IBL/light 算法、editor 调试工具
Project Policy 哪些平台启用、是否走 LightGrid、是否启用独立 pass、光源筛选规则

5. Hook 思路

Hook 可以理解为引擎主流程提供事件或接口，插件在外部注册实现。引擎只关心“这里允许扩展”，不关心具体功能。 

// Engine
FRendererExtensionRegistry::Get().RenderAfterBasePass(GraphBuilder, View);

// Plugin
FRendererExtensionRegistry::Get().RegisterExtension(MakeShared());
形式 适合场景
Interface 复杂状态、生命周期明确、需要多方法协作，例如 ISceneViewExtension
Modular Feature 多个插件注册同一类能力，引擎枚举所有实现
Delegate 轻量事件，不需要复杂对象生命周期
Shader Include Hook 插件提供 shader 文件，引擎只保留虚拟路径 include 点
CVar / Config 运行时灰度、调试和平台策略，不适合结构性裁剪

6. Custom Unlit 改造建议

6.1 统一灯光路径到 LightGrid

当前最应该优先收敛的是 CustomUnlit 专用灯光路径。 如果 CustomUnlit、移动端 DefaultLit 都统一使用 LightGrid，则可以逐步移除：

  • GatherAndSortCustomUnlitLights
  • CustomUnlitLocalLightData
  • CustomUnlitLocalLightBuffer
  • FForwardLocalLightCustomUnlitData

之后 CustomUnlit shader 只读取标准 forward light grid 数据： 

ForwardLightData.ForwardLocalLightBuffer
ForwardLightData.CulledLightDataGrid

6.2 Shader 文件迁入插件

使用插件 shader 虚拟目录映射： 

AddShaderSourceDirectoryMapping(
    TEXT("/Plugin/XDCustomUnlit"),
    PluginShaderDir);

引擎 shader 中保留薄 include： 

#if MATERIAL_SHADINGMODEL_CUSTOM_UNLIT
#include "/Plugin/XDCustomUnlit/Private/CustomUnlitCommon.ush"
#endif

6.3 Renderer pass 改为扩展点

当前 PC 路径直接在 DeferredShadingRenderer.cpp 调用 RenderCustomUnlitOpaquePass()。 推荐改成固定渲染阶段 hook，例如：

  • AfterBasePass
  • AfterLighting
  • BeforeTranslucency
  • AfterForwardShadow

插件注册自己的 renderer extension，在指定阶段提交 RDG pass。

6.4 MeshPass slot 的现实处理

EMeshPass 是静态 enum，纯插件动态扩展成本很高。建议保留一个稳定 slot，但把具体实现迁到扩展模块。

方案 评价
保留 EMeshPass::CustomUnlitOpaquePass 最现实，性能路径和 cached mesh command 容易保留
增加通用 ExtensionPass0/1 多个功能可复用，但语义较弱
完全走动态 RDG draw 引擎侵入少，但性能和缓存路径需要重新评估

6.5 材质节点迁插件，保留通用编译桥

当前每个 CustomUnlit 节点都会要求 FMaterialCompiler / FHLSLMaterialTranslator 增加专用接口。 更好的方式是保留一个通用 external expression hook： 

CompileExternalMaterialExpression(FunctionName, Inputs, Options)

插件节点调用这个桥，具体 HLSL 输出由 CustomUnlit 扩展实现。这样新增节点时不用继续污染材质编译器核心类。

6.6 LightComponent 属性改为通用 FeatureMask

不建议继续往核心 LightComponent 塞 bUsedForCustomUnlit 这类项目特化属性。 更推荐引擎提供通用能力： 

FLightSceneProxy::GetCustomLightingFeatureMask()

CustomUnlit 只是其中一个 bit。以后 Toon、Stylized、GameplayLight 等都能复用。

7. 迁移顺序建议

  1. 统一 CustomUnlit 与移动端 DefaultLit 的 local light 到 LightGrid。
  2. 移除 CustomUnlit 专用 light gather、light buffer 和 shader 数据结构。
  3. 把 CustomUnlit HLSL 移到插件 shader 目录，引擎保留薄 include hook。
  4. 把 CustomUnlit 材质表达式类迁到插件，先保留现有 compiler 接口。
  5. 把多个 compiler 专用接口收敛成一个通用 external material expression hook。
  6. 把 CustomUnlit renderer pass 迁成 renderer extension，Engine 保留 pass slot 或 extension slot。
  7. 把 bUsedForCustomUnlit 收敛为通用 light feature mask 或插件 tag 方案。

8. 每个 Feature 应该维护的元信息

对长期维护自定义引擎来说，真正重要的是让每个改动有明确边界。

字段 说明
Feature 名称 / Owner 谁负责，出了问题找谁
改动文件列表 升级和回滚时快速定位
是否影响反射 涉及 UHT、Blueprint、资产 schema 的风险
是否影响序列化 是否需要 custom version / migration
是否影响 shader permutation / DDC 是否需要更新 shader version 或清缓存策略
是否支持运行时关闭 用 CVar / config 控制行为
是否支持编译期关闭 用宏裁剪代码和依赖
关闭时预期行为 明确是 fallback、隐藏、no-op，还是不支持关闭
验证用例 打开/关闭、PC/移动、Cook、Shader 编译、资产加载
回滚方式 出现问题时能否快速撤回

9. 最终判断

CustomUnlit 不适合追求完全插件化。它已经触及 UE 的静态 shading model、材质编译、MeshPass、shader permutation 和资产 schema。

更推荐的路线是：核心 schema 留在 Engine，具体功能逻辑进入插件；Engine 中只保留少量稳定 hook。 这样既不和 UE 的静态系统硬碰硬，又能显著降低后续维护和升级的冲突成本。
