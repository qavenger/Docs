工程概况

引擎被直接魔改，且与项目同仓P0

问题描述

Engine/Plugins 混入公司自定义插件：XDCacheLog、XDTextureCompress、XGEController、AliCloundLog、MultiPlatformLightControl、PowerAnalysisPlugin、BlueprintAssetBreakerTools，Engine/Kantan 还有自定义配置。定制散落在原生引擎目录、与 Epic 原始代码无法区分；引擎与游戏共用一个 VCS 根。
影响：UE 版本几乎无法干净 rebase波及：升级、复用、独立发版
▎可选整改方案
1引擎独立成「公司基线 Fork」+ 二进制分发推荐

把 Engine/ 拆为独立仓库 Engine-Base（公司唯一引擎主干），由引擎组维护、编译出二进制 Installed Build 发到制品库；项目仓库只用引擎版本号引用，不再内嵌引擎源码。

代价：需建引擎组 + 制品库 + CI；首次拆分有一次性成本。

优点：彻底解耦、可升级、可复用到下个项目工期：1–2 月风险：中
2定制插件迁出原生目录 + 源码改动补丁化

过渡方案：暂不拆仓，但把 XD*/Ali*/XGE* 等自定义插件从 Engine/Plugins 迁到独立的「公共插件集」目录，与原生 UE 物理分离；必须改引擎源码处用集中补丁(patch set)管理，每处标注原因，便于未来 rebase。

代价：引擎仍在同仓，未根治；补丁需人工维护。

优点：成本低、可立即开始、为方案1铺路工期：2–3 周风险：低
3定制能力尽量「插件化/配置化」下沉

逐项审查每处引擎源码改动，能用插件、模块、DefaultEngine.ini 或编译开关实现的，全部下沉，把"必须改源码"的集合压到最小。优先级：配置 > 插件 > 引擎源码。

代价：需逐项评估，周期长，部分深度改动无法下沉。

优点：从根上降低升级成本，是长期正解工期：持续风险：低

巨石主模块（Monolith）P0

问题描述

UE_game 单模块装下全部：Core / Fight / Game / Net / View / Windows / Editor / AutoTest / LuaApi / Utils（7000+ 文件）。改任意一处近乎全量重编；模块内无边界、任意互相引用；编辑器代码 Private/Editor 塞进了 Runtime 模块，靠 bBuildEditor 散落分支隔离。
影响：迭代编译慢、耦合失控、有随包误发编辑器代码风险
▎可选整改方案
1按现有目录边界渐进拆分多模块推荐

沿用 Private/ 的天然边界拆模块，依赖单向向下：
GameCore(Utils/基础) ← GameNet ← GameFight ← GameUI(View/Windows) ← GameLua(LuaApi)。一次拆一个、独立验证。

代价：需先理清并切断反向依赖，过程中接口要反复调整。

优点：增量编译大幅提速、耦合显式化、风险可控工期：2–4 月持续风险：中
2优先剥离 Editor 与 AutoTest（最高性价比的第一刀）

先把 Private/Editor 抽成独立的 Editor 类型模块 GameEditor，AutoTest 抽成独立测试模块。这两块与运行时耦合最浅，收益（消除误发风险、隔离编辑器依赖）最直接。

代价：仅解决一部分，主运行时仍是巨石。

优点：见效快、风险低，适合作为拆分起点工期：2–3 周风险：低
3功能模块插件化（GameFeature）

把相对独立的玩法（如战斗、特定系统）逐步迁成 Game Feature Plugin / 独立插件，按需加载，进一步降低主模块体量与耦合。

代价：改造量大，需配套加载流程，建议在方案1完成后做。

优点：边界最清晰、可按需裁剪、利于复用工期：长期风险：中高
配套：随拆分逐步把 bUseUnity 全量编译替换为模块级增量；用模块依赖图持续校验"Core 不依赖上层"。

99 个插件平铺、职责混杂、无分类P1

问题描述

一个目录混放四类完全不同的东西，无分层/无 owner/无 license：三方 SDK(Tap*/XDG*/LeanCloud/Wwise/Spine/Houdini)、编辑器工具(约 30 个 *Editor/*Tool)、引擎级能力(TorchLightHotUpdate/UEBackgroundDownload)、玩法功能(Arc/Narwhal…)。无法快速回答"哪些外购、哪些随引擎升级、哪些本项目专属"。
▎可选整改方案
1按职责分类目录化 + Owner/License 清单推荐

分四类归档：Plugins/ThirdSDK(外购)、Plugins/EditorTools(工具)、Plugins/GameFeature(玩法)、Plugins/Engine(引擎级)。每类维护一张表：owner、license、版本、更新方式。

代价：移动插件需同步改引用路径与 CI。

优点：归属清晰、升级路径明确、成本低工期：1–2 周风险：低
2通用插件上提到引擎基线层

与"引擎拆分"联动：把跨项目通用的插件（热更、下载、SDK 接入层等）上提到 Engine-Base 的公共插件集，随引擎统一分发；项目目录只留本项目专属插件。

代价：依赖引擎层先拆好(见标签①方案1)。

优点：消除跨项目重复、便于统一升级工期：随引擎拆分推进风险：中
3外购 SDK 统一接入层封装

为 Tap*/XDG* 等渠道 SDK 建一层薄封装(adapter)，业务只依赖封装接口，不直接依赖具体 SDK；换渠道/升级 SDK 时改动收敛在一处。

代价：需设计统一接口，初期有封装成本。

优点：渠道解耦、降低 SDK 升级波及面工期：中风险：中

构建产物 & 第三方库入库P1

问题描述

根目录 .ue4dependencies(15MB)、code_mark_file.cs、server_build.cs(670KB)、client_dll_submit_mark_file.txt(592KB) 等构建标记文件直接入库；ToolsEx 签入二进制 checkout.exe/merge.exe/ui.exe；三方源码(Lua/Zstd/SoftFloat/ProtoBuf)嵌进主模块 Public/Third 用 IncludePath 引入，无版本隔离。
▎可选整改方案
1构建产物/缓存移出版本管理推荐

把 *_mark_file.*、.ue4dependencies、DerivedDataCache/、Intermediate/、Saved/ 移出 VCS，改由共享 DDC 服务器 / 制品库 / CI 产物承载。

代价：需搭 DDC/制品库并改 CI 流程。

优点：仓库瘦身、拉取加速、消除"产物冲突"工期：1 周风险：低
2二进制工具改为制品拉取或源码现编

ToolsEx 里的 *.exe 不再入库：要么把对应 py 源码留库、运行时现编/直接跑 py，要么发布到内网制品库由脚本按版本拉取。

代价：需补齐工具源码与构建说明。

优点：可审计、可追溯版本、避免黑盒 exe工期：1–2 周风险：低
3第三方库独立化并锁版本

把 Lua/Zstd/Berkeley-SoftFloat/ProtoBuf 从主模块 IncludePath 抽成独立 ThirdParty 模块或插件，标注来源版本号，集中升级。

代价：需重整包含路径与链接配置(见 Build.cs L38-52,148-175)。

优点：版本可控、与业务解耦、降低主模块耦合工期：2–3 周风险：中

Build.cs 不可维护 / 发行逻辑耦合编译期P2

问题描述

依赖列表超长且有重复项(XDEMoreTickGroupEvent 写了两遍，见 Build.cs:25)；CN/海外通过在 Build.cs 里读 ini 再换模块实现(L110-142)；区域/平台/编辑器分支全手工硬连，脆弱易错。
▎可选整改方案
1发行差异迁到 Target.cs + 编译开关/配置推荐

CN/海外、平台差异从 Build.cs 移到对应 Target.cs 与配置/宏开关；Build.cs 只描述"我依赖谁"，不承载发行策略。

代价：需梳理现有分支语义并迁移。

优点：职责清晰、发行策略集中、易扩展新区域工期：1–2 周风险：低
2依赖清单去重 + 自动校验

清理重复/失效依赖项，加一条 CI 检查（脚本扫描重复模块名、未使用依赖），防止再次劣化。

代价：需写校验脚本。

优点：立即见效、防回归工期：数天风险：极低
3渠道/区域包用插件集 + Feature 开关

把 CN/Overseas 的差异封装为可插拔的渠道插件集，配合 Feature 开关在打包阶段选择，而非编译期硬切模块依赖。

代价：改造较大，依赖渠道接入层(见标签③方案3)。

优点：多区域扩展性最好、解耦彻底工期：中风险：中

工具链散乱、硬编码、命名随意P2

问题描述

Tools/ ToolsEx/ 内大量临时 py/bat，中文命名(同步数据.bat/启动全功能个人服.bat)，职责混杂(导表/合并/校验混在一起)，无统一入口与配置，强依赖本地路径。
▎可选整改方案
1统一 CLI 工具入口 + 子命令推荐

收口为一个有文档的工具入口（如 tools <导表|合并|校验|起服>），英文规范命名，统一参数与日志；旧 bat 作为薄封装过渡。

代价：需重整脚本并补文档。

优点：可发现、可维护、降低上手成本工期：2–3 周风险：低
2路径/环境配置外置

把硬编码路径抽到统一配置文件 / 环境变量，工具从配置读取，消除"换台机器就跑不起来"。

代价：需逐个脚本改造。

优点：可移植、CI 友好工期：1–2 周风险：低
3导表/数据管线独立成服务

把 Excel 导表、校验、合并(export_tables/validate_excel/auto_merge)整合为独立的数据管线，接入 CI，本地与服务器共用同一套逻辑。

代价：改造量中等，需与策划流程对齐。

优点：一致性强、可自动化、减少人工失误工期：中风险：中

分阶段整改路线图

最大杠杆点是 阶段1（抽离引擎） 与 阶段2（拆巨石模块）：前者决定能否跟上 UE 升级、能否复用到下个项目；后者直接决定迭代编译效率与耦合度。
阶段 0 · 止血（1–2 周，零风险）
① 构建产物/缓存/标记文件移出 VCS；二进制 exe 改制品拉取 [标签④]
② 明确"引擎=Git / 资产=P4"边界，停止双轨混用
阶段 1 · 抽离引擎层（核心，1–2 月）
③ Engine/ 拆为独立公司基线 Fork + 二进制分发，项目按版本号引用 [标签①方案1]
④ Engine/Plugins 自定义插件迁出原生目录、源码改动补丁化 [标签①方案2]
阶段 2 · 拆解巨石模块（持续，2–4 月）
⑤ 先剥离 Editor 与 AutoTest [标签②方案2]
⑥ 按 Core→Net→Fight→UI→Lua 渐进拆分多模块 [标签②方案1]
阶段 3 · 治理插件与第三方（持续）
⑦ 插件四类目录化 + owner/license 清单 [标签③方案1]
⑧ 第三方独立化锁版本、通用插件上提引擎层 [标签④方案3 / 标签③方案2]
阶段 4 · 构建与工具链规范（持续）
⑨ 发行差异迁 Target.cs + 依赖去重防回归 [标签⑤]
⑩ 工具链统一 CLI 入口、路径外置、导表成管线 [标签⑥]
阶段目标产出验证标准
阶段0干净仓库 + 单一 VCS 策略新克隆体积显著下降、无产物冲突
阶段1独立引擎基线 + 二进制分发项目可用二进制引擎构建、引擎可独立升级
阶段2多模块 + 独立 Editor 模块单模块改动增量编译、运行时无编辑器依赖
阶段3分类插件库 + 锁版本第三方每个插件可溯源 owner/license/版本
阶段4规范构建 + 统一工具链CI 全流程跑通、换机即用
