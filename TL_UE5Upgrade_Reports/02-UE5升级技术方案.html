火炬之光 · UE5 升级技术方案

面向制作人 / 策划 / 美术（通俗版）· 引擎 UE 5.8.4 · 更新日期 2026-10-30
一句话结论：把游戏从「原版 UE4.26 + 大量引擎定制」搬到「官方 UE5.8」，本质上不是"换个引擎版本"， 而是把引擎定制能力、工程代码、Lua 逻辑、26 万份美术资产、几十份配置一起搬过去，并且要保证 以后还能持续跟上游开发线同步。我们为此建了一条可重复执行的“迁移流水线”。

二、为什么这件事比“升级引擎”复杂

难点具体是什么规模
原版引擎是“改过的” 原版在 UE4.26 上做了大量定制（额外着色模型、Slate 交互修正、打包/热更能力等）， 官方 UE5 没有这些改动 ⇒ 直接换引擎会大量功能失效 9 项定制能力
Lua 与资产是“两套独立内容” Lua 逻辑有 8000+ 文件，美术资产 26 万+，两者必须同时对齐才能跑起来 8,272 / 268,800
上游还在继续开发 迁移不是一次性交付：上游每天都在改，必须能“反向同步”回来 持续
UE5 行为与 UE4 不同 同样的代码/资产，在 UE5 里行为可能不同（控件失效、动画不播、材质报错）， 这类问题不会自己暴露，需要专门手段发现 162 条记录

三、方案总览：分成五层处理

① 引擎层官方 UE5.8.4 为基座；原版定制能力逐项判定：能还原就还原，不能还原就看影响决定是否投入
② 工程代码层C++ 只做“UE5 API/行为差异”适配，不改业务逻辑；共 8,267 个源文件
③ Lua 逻辑层与上游做“三方合并”，保留双方改动；配套强制门禁防破坏
④ 资产层26.8 万资产做批量体检 + 定点修复 + 规则化重存
⑤ 配置层ini/表配置做键值级合并，避免“整份覆盖”丢设置
原则：优先级从高到低永远是 改配置 > 改资产 > 改工程代码 > 改引擎。 只有“引擎版本导致的 API 差异”才允许动引擎代码，且必须逐条登记、可随时回退。

四、迁移流水线（可重复执行）

阶段做什么为什么需要
S0–S1取上游快照、建立逐字节对照基线后面所有判断都要靠“和基线比对”，没有基线就只能猜
S2盘点差异，自动分类把成千上万个差异分成“可直接复制 / 需要合并 / 需要重做”三类
S3–S4文本做三方合并（ours / theirs / base）上游和我们各改过同一份文件时，必须合并而不是互相覆盖
S5二进制资产按分类处理（覆盖 / 重存 / 重新迁移）二进制没法合并，只能选“保留哪一版 + 怎么改造”
S6重存与格式升级（资产升到 UE5 格式）老格式资产 UE5 读不了或读出错，必须按新规则重存
S7–S8定点修复（脚本/工具批量）处理“能读但不对”的问题：贴图发暗、材质报错、控件丢失等
S9自动门禁 + 体检用机器把“不该犯的错”提前挡掉，而不是靠人肉试玩
S10产物归档、登记、知识库记录每条问题都留档，避免同一个坑踩第二次

五、四类关键技术（通俗解释）

1. Lua：三方合并 + 强制门禁

问题：上游和我们改过同一份 Lua，直接覆盖会丢别人的改动；直接回滚会丢自己的修复。
做法：像 Git 一样做三方合并（上游版 / 我们版 / 共同祖先），冲突处人工裁决；
合并后必须通过一套自动门禁才允许进游戏或提交：语法检查、模块解析、入口全局函数、注册表指向、行数基线。
门禁检查挡住什么事故
语法检查（全量 8000+ 文件）合并残留冲突标记、写坏的 Lua
模块解析 / 注册表指向类/页面注册丢失 ⇒ 界面点了没反应
入口全局函数关键入口被误删 ⇒ 登录/选角/加载直接不进
行数基线文件被“整段吞掉”（合并时误删大段逻辑）

2. 资产：批量体检 + 定点修复

问题：26 万份资产里，有大量“能加载但表现不对”的（贴图发暗、材质报错、控件丢失、动画丢失）。
做法：先做规则化体检把问题分类，再用定点工具批量修（每一批都带备份、回读校验、分批验证）。
典型问题处理方式
贴图发暗 / 色彩不对修正编码与尺寸规则，批量重存（约 7.6 万张被规范，1,164 张修复、5,419 张冗余删除）
界面发灰 / 图片不显示修正图片类型标记（Brush 不绘制问题），运行时自动生效
控件丢失 / 白块按 C++ 声明重建控件 + 审计工具校验
材质报错 / 崩溃定制着色模型统一改为标准光照；材质实例的遗留覆盖批量清理
动画不播（怪物攻击）修复“异步加载完成后动画实例为空”的链路（本次重点修复）

3. 引擎定制能力：逐项判定，能还原就还原

判定结果例子
可还原在工程侧补齐，不改引擎界面缩放规则、输入分帧、打包配置
需引擎修改公版 UE5 没有，需排期镜头动画、点击命中时机、SButton 悬停丢点击
放弃影响可控，直接不做纯诊断功能、上游已由 UE5 原生替代的能力
当前引擎侧已尽可能回到官方原版：源码改动从最初的 8 处收敛到「2 处临时容错 + 1 个配置项」， 其余问题全部在工程/资产侧解决。这保证了将来升级 UE5 小版本时不会卡在“本地魔改”。

十、工程效能：这次升级里被忽略的"另一半"

前九节讲的是"让游戏跑起来"。但一个升级计划要能长期运转，还需要打包提速、包体控制、与上游持续同步、自动检查。 这部分工作在本次升级中实际一直在做，只是之前没有写进文档——这里补齐。

10.2 实测数据（这些数字比描述更有说服力）

指标实测值说明 / 结论
Development 包大小 37 GB 含 Torchlight_Migrate.pdb 调试符号 2.8 GB（发布包不需要）、exe 437 MB、两个 pak 共 2.6 GB
Shipping 包大小 75.72 GB 21 个 pakchunk；最大的是 pakchunk999 28.76 GB、pakchunk101 15.57 GB、pakchunk2 7.54 GB
打包清单条目 1,174,108 条 / 未压缩 161.86 GB 去重后只有 554,434 个文件 / 68.77 GB
重复拷贝浪费 93.09 GB 超过一半的体积是同一文件在不同分块里的重复拷贝——这是包体偏大的头号原因
pak 压缩 配置未生效 UE5 把配置键名从 PakFileCompression* 改成 PackageCompression*，旧键被静默忽略 ⇒ Shipping 实际跑的是 4 级，不是配置里的 5 级
打包格式 传统 pak 工程关着 IoStore（沿自 UE4 配置）。UE5 已默认推荐 IoStore + Zen 加载，切换收益明确但需评估热更链路
着色器编译速度 约 280 个/分钟（仅 1 个核） 本机 XGE 分布式分发每批失败 ⇒ 回落单进程。几千个着色器要编十几分钟
出包结果 BUILD SUCCESSFUL Development / Shipping 均可成功产出并启动
两个"一分钱不花就能拿回来"的收益：
  1. 包体去重（可省约 93 GB）：方案已明确——加一个打包开关让"每个文件只进第一个分块"，不用改代码，重出包即可验证效果。
  2. 压缩等级修复：把压缩配置改成 UE5 的新键名，Shipping 压缩从 4 级提到 5 级，包体还能再降一截。只改 ini。
这两项加起来，Shipping 包有机会从 75.7 GB 降到 60 GB 以内——对下载/安装成本影响很大。
一个需要 IT 配合的收益：恢复着色器分布式编译（XGE 或 UBA 分布式）。当前单核 280 个/分钟，恢复到多机并行后 首次进图/改材质后的等待时间能缩短一个数量级，直接改善全员迭代体感。

10.3 与上游（UGS / P4）的持续同步

能力实现方式关键设计
固定 CL 拉取脚本先记录"我们有的是哪个版本"，再按固定 CL 拉；自动排除 3.7TB 素材库与 0.5TB 设计目录（否则磁盘直接爆）
差异分类脚本文本 / 二进制 / 新增 / 删除四类分开走不同策略
三方合并脚本 + 人工裁决base 必须选"UE5 内容真正派生自的版本"（宁旧勿新），否则会静默回退上游改动
存量差距盘点脚本回答"本批之外还差多少"，避免"以为追平了其实没有"
与国服测试服对齐脚本API 扫描 + Lua 绑定审计 + 帧哈希逐帧比对 + 参考重放
为什么这块值得单独说：升级不是"一次性交付"。上游每天都在改，能不能低成本地把上游改动接回来，决定了这个 UE5 分支能活多久。 目前这条链路已实跑 13 个批次，含一次 3 天内上千个改动块的批量合并。
